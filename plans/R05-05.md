What is left, and what this task delivers, in my words:

1. **Registration can be exercised.** No schedule on the tree carries a `fee_version_number` other than 1, and the number-1 arm of `consume_to_fees_v0` never reads the history map (`packages/rs-drive/src/fees/op.rs:280`). Every registry, hook, saved-state and refund path for a second generation is therefore dead code with no coverage. Deliver a test-only fee-history generation with a doubled storage rate and a mock protocol version that carries it, resolvable through the real registry, real `PlatformVersion::get`, the real epoch-change hook, the real saved-state store and load, and the real block loop. Production registries and every shipped `PLATFORM_V*` stay byte-identical.
2. **The genesis generation is registered.** `PlatformState::default_with_protocol_versions` (`packages/rs-drive-abci/src/platform_types/platform_state/mod.rs:126-155`) starts the fee history empty, and the hook (`upgrade_protocol_version/v0/mod.rs:96-116`) only records a generation on the first non-genesis epoch change. Bytes stored in epoch 0 of a network whose genesis generation is not number 1 would be refunded at number-1 rates forever (`active_fee_version` falls back to `FeeVersion::first()` below the earliest entry). Seed the genesis entry. Unobservable on every existing network (section 5).
3. **Replay coverage.** A chain that upgrades across a fee-generation boundary, and a chain that starts at a non-1 generation, produce the same app hashes, transition results, identity balances and fee-history map whether run continuously from genesis or stopped, reopened from the persisted state and continued; the validator path agrees with the proposer path on every block. Exact refund vectors at the boundary go through `process_raw_state_transitions` with the real history map: bytes stored after the boundary refund at the new rate, genesis-epoch bytes at the genesis rate, and (part 2, on top of R12-01) bytes stored before the boundary and removed after it refund at the rate they were stored at.
4. **Ordering.** Part 2 lands on `v5.0-dev` only after R12-01 has merged forward; part 2's implementer checks `git log origin/v5.0-dev` for R12-01's commit and stops if it is absent. This is the "before infrastructure merges" gate for the DashVM fee tasks (R12-03, R12-05, R12-09, FIX-08).

## 3. Design decisions

**D1. A test-only fee generation, not a renumbered `FEE_VERSION2`.** R12-01 decided not to renumber (the number keys storage-refund behaviour and storage rates never changed; renumbering flips PV9 to PV14 onto the history-driven path in shipped code). Agreed. The only way to exercise a real boundary without a consensus change is a generation that exists only under `mock-versions`, numbered in the same shifted range the mock protocol versions use so it can never collide with a production number and is rejected by a production build.

**D2. Seed the genesis generation in the unversioned state constructor, with an unobservability proof, rather than behind a new `init_chain` generation.** A versioned gate would need a protocol version that does not exist yet (allocation A01 belongs to R05-03; no `PLATFORM_V15` on the tree). The seed changes the fee history of a freshly initialised chain from `{}` to `{0 → registry entry of the genesis schedule's number}`. Every network that exists today (mainnet, testnet, every devnet) has genesis generation number 1, `FeeVersion::get(1)` is `FEE_VERSION1`, and an empty map resolves every epoch to `FeeVersion::first()`, the same constant. So every `KnownCostItem` lookup, every refund and every root hash is identical before and after the change for every reachable input, by construction (R12-01's registry tests pin that the registered entry agrees with every referenced schedule on every `KnownCostItem`). Saved-state bytes of a replayed-from-genesis node gain one map entry; the map lives in GroveDB aux, not in the app hash. Existing saved states are untouched (init chain does not rerun). The first network whose genesis schedule carries a new number is the explicit boundary at which the seed becomes observable, and it is correct from block 1 there. This goes in the PR body under "Breaking changes: none observable", mirroring R12-01's argument for the storage-epoch rate fix.

Seed value: the registry entry `FeeVersion::get(number)`, not the schedule reference, so the in-memory map after init equals the map after a store/fetch round trip (which maps numbers to registry entries), and so R12-01's planned full-equality round-trip test still holds with the extra entry.

**D3. Mock protocol version built on the latest shipped tables.** `TEST_PLATFORM_V4 = PlatformVersion { protocol_version: TEST_PROTOCOL_VERSION_4, fee_version: TEST_FEE_VERSION_DOUBLED_STORAGE, ..PLATFORM_V14 }`. Every dispatch slot equals PV14, so an upgrade PV14 to the mock changes nothing but the fee generation and `perform_events_on_first_block_of_protocol_change` fires no migration (`previous_protocol_version < N && current >= N` is false for every `N <= 14`). Doc comment says the base must be moved to the newest shipped table when a protocol version is introduced. Const struct update over a non-`Copy` const base compiles on the workspace toolchain (probed with a standalone `rustc` program during planning; precedent in-tree at `drive_abci_query_versions/v3.rs:32`).

**D4. Doubled storage rate only.** `TEST_FEE_VERSION_DOUBLED_STORAGE = FeeVersion { fee_version_number: TEST_FEE_VERSION_NUMBER_DOUBLED_STORAGE, storage: FeeStorageVersion { storage_disk_usage_credit_per_byte: 54_000, ..FEE_STORAGE_VERSION1 }, ..FEE_VERSION2 }`. Processing, hashing and signature rates are unchanged, so any fee difference across the boundary is storage, and a refund priced at the wrong generation is off by a factor of two.

**D5. Part split.** Part 1 (prep slice, 43-FEES branch): the mock generation, the mock protocol version, the genesis seed, the boundary harness, the vectors that hold on the current refund rule, the parity strategy tests. It compiles and passes alone and does not depend on R12-01. Part 2 (`v5.0-dev`, after R12-01 merged forward): the pre-boundary-bytes vector (only R12-01's storage-epoch rule makes it pass), the rework of the "increasing fees" test, the book refund note. Rationale for landing part 1 early: R12-02 and FIX-08 need a live boundary to test against; the harness should exist before they plan their tests.
