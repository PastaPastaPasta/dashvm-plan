## 1. Acceptance in my words

**Q11, the part this task owns.** Every timestamp the mechanism uses is `block_info.time_ms` of
the block that commits the fact: `accepted_at_ms` (the block whose transition opened the round,
R06-04), `crossing_ms` (the block whose event completed the validated walk, R08-12) and
`activated_at_ms` (this task). The additional wait is `clamp(crossing_ms - accepted_at_ms,
readiness_additional_wait_min_ms, readiness_additional_wait_max_ms)` with the two `SystemLimits`
rows at 120,000 and 3,600,000 (confirmed policy, placement a choice), `deadline_ms = crossing_ms
+ wait` checked. **The activation boundary** is the readiness block event of the first block
whose `time_ms >= deadline_ms` (inclusive), which runs after the block's membership update and
before the block's transitions, so a cancellation or replacement carried by that block's
transitions cannot undo the activation, while one committed in any earlier block removed the
deadline entry and no activation happens. The boundary needs no membership: there is no second
gate, and a membership change after the crossing moves nothing. At most
`maximum_readiness_activations_per_block` rounds activate per block, oldest deadline first, the
rest in the following blocks. Activation is one atomic batch per round: unlink the round from its
contract, retire it (queued for cleanup, deadline entry and its emptied time bucket gone, fund
emptied, cleanup reserve to the epoch processing pool, remainder refunded to the payer), write
the contract's activation record, and run the routing hook whose body R10-11 fills.

**Q10, restated for what this task must not break.** The count tree is not eligibility proof and a
`Crossed` round is never re-evaluated: the walk skips non-pending rounds, so a later report,
prune, ban or growth of the evonode set cannot un-cross or move a deadline ("threshold
persistence"). The below and at 80 percent vectors, duplicate votes and pruning are R08-12 part 2's
tests (its plan, section 6) and are referenced, not duplicated.

**Named-module scope.** Activation installs the whole bundle the round bound (contract, version,
bundle digest, preparation profile); there is no per-module activation. The activation record
carries exactly the round's binding so R10-11's routing and R08-06's "follow the active state"
preparation read one fact.

## 3. Design

### 3.1 The activation step inside `process_compilation_readiness` v0 (in place; protocol 17 unreleased, no v1)

Order inside the event, the A11 intra-event convention (provisional, ratified by the tests of
section 6 and documented in the book):

0. **Due activations** (this task). `fetch_readiness_rounds_due(block_info.time_ms,
   maximum_readiness_activations_per_block)`; entries come oldest deadline first and contract id
   order within a deadline. For each entry:
   - `fetch_readiness_round(contract_id)`. **Live** when `Some(round)`, `round.round_id() ==
     entry.round_id` and `!round.is_pending()`. Otherwise **stale**: the entry is removed in its
     own small batch through the new `remove_readiness_deadline_entry_operations(deadline_ms,
     contract_id)` (3.3), with a `tracing::warn!`; no activation, no refund, no error. A stale
     entry cannot be produced by part 1's primitives (every retirement removes its entry); the
     branch exists because the alternative is `CorruptedDriveState` through `?`, which halts every
     node (memory: reference-platform-halt-model), and dropping it is what the DIP requires of a
     deadline whose round was replaced or cancelled. A stale entry counts toward the per-block
     bound (the query's limit counts entries; simpler and still bounded).
   - Live: `activate_readiness_round_operations(contract_id, round_id,
     fee.dashvm_readiness.round_cleanup_reserve, block_info, &mut None, transaction,
     platform_version) -> (round, ops)`; build `ReadinessActivation::from_round(&round, block_info,
     platform_version)` (3.2); `ops.extend(self.on_readiness_round_activated(&activation,
     block_info, transaction, platform_version)?)` (3.4); apply `ops` as **one batch** through
     `apply_batch_low_level_drive_operations` (the retirement's pool rewrite and the payer's balance
     rewrite are absolute, so one activation per batch; the hook must not write identity balances
     or the processing pool, stated in its doc comment). `tracing::debug!` with contract, version,
     round, deadline and block time.
   - Why before the cleanup step and the walk: a due round is a *prior* decision (DIP: "apply due
     prior activation decisions"); handling it first means this block's walk never visits a round
     that is being activated, the fairness cursor spends no visit on it, and the retired queue the
     cleanup step reads already contains this block's retirements, so the queue order is decided
     by the same block that produced the entry. The order cannot change *which* rounds activate: a
     crossing recorded by this block's walk has `deadline_ms >= time_ms + 120_000`, so it is never
     due in the block that records it (tested).
1. Retired-round cleanup step (R08-12 part 2, unchanged).
2. Fairness walk, gate, paged validation, crossing (R08-12 part 2, unchanged). `Crossed` rounds are
   skipped there already, which is the threshold-persistence property this task tests.

Errors: every `?` is a node fault exactly like the vote poll event; nothing is swallowed per
round. Determinism: every read is Drive state inside the block transaction; order is deadline
then contract id; the per-block bound is a table constant.

Why a record and not only a deletion: activation must be a *defined, observable boundary*
(Q11). Without it "activated" and "cancelled" leave identical state (round gone, payer
refunded), nothing on chain says which version of a contract is live or since when, R10-11 has
no fact to install routing from, R08-06 cannot tell which version a restarted node must prepare,
and the query layer has nothing to prove. The record is the readiness module's durable output;
the EXEC namespace (R08-03, R06-04) will hold the contract's routing pointer that the hook
installs from this record, and if the owner prefers, the whole `[112, r]` family moves under EXEC
before release with the same Drive API (R08-12 plan 3.1 already says so). Why its own tree and
not the contract's readiness tree: cleanup deletes the contract tree when the pointer is gone, and
the fairness walk pages over `[112, r, 0]`, so a record there would either be deleted by cleanup
or make every contract that ever activated cost a visit per block forever.

Drive (`packages/rs-drive/src/drive/votes/readiness/`), all `#[cfg(feature = "server")]`, each
with `mod.rs` dispatch on a new `DriveVoteReadinessMethodVersions` slot (`Some(0)` amended into

### 3.7 Consensus-time and activation-block conventions (the A11 document)

Book: `book/src/drive/compilation-readiness.md` gains two sections after "Cursors, crossings and
deadlines": **"Consensus time and the activation boundary"** and **"Activation"**; the layout
section gains the `4` line; the Cleanup section's sentence on stale entries is corrected to say
retirement removes the entry and the event drops a leftover one. The phase document says, with
the source positions as they are on the base:

1. Time is `block_info.time_ms`, the committed block time Tenderdash agreed on; no node reads a
   clock. Every readiness timestamp names the block that committed the fact.
2. Membership phase: `update_core_info` applies the block's core-chain-locked height before any
   readiness work; the view is `block_platform_state`'s HPMN list (R08-12 3.2).
3. Lifecycle phase: `run_dao_platform_events` after removed-masternode votes and ended vote polls
   runs compilation readiness in the order due activations, cleanup step, evaluation walk.
   Transitions run after it, so a report, cancellation or replacement accepted in block `H`
   takes effect in the event of `H + 1`; a transition in block `H` cannot undo an activation the
   event of `H` performed; one committed in `H - 1` or earlier removed the deadline entry and
   no activation happens. Scheduled work (DVM-08) and governance outcomes (DVM-09) run after this
   phase when they exist (FIX-03's hook position), so scheduled execution never observes a
   report that appears later in the same block.
4. Crossing time is the time of the block whose event completed the validated walk; `T =
   crossing_ms - accepted_at_ms` (saturating), `wait = clamp(T, 120 s, 3,600 s)`, `deadline =
   crossing_ms + wait` (checked). Vectors: T of 30 s waits 120 s, 600 s waits 600 s, 7,200 s waits
   3,600 s; total from deployment is 2T inside the bounds, not 3T.
5. Activation boundary: the readiness event of the first block with `time_ms >= deadline_ms`
   (inclusive; the due query reads `..=deadline`). No block lands exactly on most deadlines, so
   activation time is that block's time, which may exceed the deadline by up to one block
   interval. At most `maximum_readiness_activations_per_block` per block, oldest deadline first;
   a backlog drains over following blocks in deadline order.
6. No second gate: membership at the boundary is not consulted; a change after the crossing
   neither moves nor cancels the deadline. A crossed round is never re-evaluated by the walk.
7. Same-block impossibility: `wait >= 120_000` and block time is non-decreasing, so a crossing is
   never activated in the block that records it.
8. Atomicity: one batch per activation (unlink, retire, refund, record, hook); a rejected
   proposal rolls all of it back with the block; a restarted node resumes from Drive state (the
   deadline queue is state), so a deadline survives a restart.
9. What remains for the DIP editor (dashpay/dips PR 190, DVM-03 "Timing and block phases"): the
   PR body carries this list as the proposed A11 text, and the allocation register row A11 moves
   from "source-level ABCI vectors required" to "vectors in `process_compilation_readiness/v0/
   activation_tests.rs` and `run_block_proposal/mod.rs`" once merged. The DIP repository is not
   touched by a platform PR.

`book/src/versioning/platform-version.md`: the V11 sentence R08-12 adds gains "and the number of
activations per block".

## 6. Tests and where they live

All at `PlatformVersion::latest()` unless the test is about the version boundary; names start
with `should`; every timestamp is a `BlockInfo` value, never a clock.

**rs-dpp** (`voting/readiness/activation/mod.rs`): round trip through serialization; `from_round`
of a crossed round carries every binding and the block's time and height; `from_round` of a
pending round is `CorruptedCodeExecution`; unknown structure version rejected.

**rs-drive** (`drive/votes/readiness/tests.rs`): latest genesis has `[112, r, 4]` and 14 has not
(extend R08-12's two structure tests); store then fetch a record, a second store for the same
contract replaces it, fetch of an unknown contract is `None`; remove a hand-made stale deadline
entry and its emptied bucket, keep a bucket shared with a live entry; retire still removes the
deadline entry (R08-12's tests, unchanged, prove the refactor); an estimated store is at or above
the applied cost for a record with maximal varints; `structure::tests` fixture reaches
`votes.readiness.activations.contract`.

**rs-drive-abci** (`process_compilation_readiness/v0/activation_tests.rs`, platform from
`TestPlatformBuilder`, `set_genesis_state_with_activation_info`, rounds opened and crossed through
the Drive API with chosen `accepted_at_ms` and `crossing_ms`, the event called directly with a
`BlockInfo`, the payer a funded identity):

- Timing vectors: accepted at `t0`, crossing at `t0 + 30 s`: the event at `crossing + 119_999 ms`
  activates nothing, at `crossing + 120_000 ms` activates (record `activated_at_ms` equals that
  block time, `deadline_ms = crossing + 120_000`); the same for `T = 600 s` (deadline at
  `+ 600 s`) and `T = 7_200 s` (deadline at `+ 3_600 s`); one millisecond before each deadline
  nothing happens.
- No block at the deadline: events at `deadline - 1` and `deadline + 50_000`: the second activates
  and the record's `activated_at_ms` is `deadline + 50_000`, `deadline_ms` unchanged.
- Membership change after the crossing: cross with `n = 5`, `Y = 4`; before the deadline ban two
  reporters (eligible now 2 of 3) in one variant and add ten evonodes (4 of 15) in another; the
  round stays `Crossed` with the same deadline, the walk does not touch it, and it activates at
  the deadline.
- Threshold persistence: a crossed round with a duplicate report inserted and one report pruned
  by hand keeps its deadline; the platform reopened from its tempdir between crossing and
  deadline activates at the deadline (the queue is state).
- Same block: a round whose walk crosses in block `B` (R08-12's helper) is not activated in `B`
  even when `B`'s time is huge relative to acceptance, because `deadline >= time_ms + 120_000`.
- Bound: five contracts due in one block with the table's bound of 4: the four oldest deadlines
  activate, the fifth in the next block; with equal deadlines the order is contract id.
- Effects of one activation: pointer gone, record and count tree unreachable through the
  pointer, retired queue holds the round, deadline entry and its bucket gone, fund emptied,
  reserve in the epoch processing pool, remainder on the payer, `calculate_total_credits_balance`
  balances, `fetch_readiness_activation` returns the record with the round's binding; a later
  round of the same contract that activates rewrites the record; the cleanup step drains the
  retired round in the following blocks.
- Stale entry: a hand-made entry for a contract without a round, one whose id differs from the
  current round, and one naming a pending round: each is dropped, nothing activates, no refund,
  the event returns `Ok`, the bucket is removed when emptied.
- Order inside the event: a block whose event both activates round A and completes the walk of
  round B (crossing B) leaves B `Crossed` and A activated; the fairness cursor did not visit A.
- Gate: at `PlatformVersion::get(16)` on a genesis-16 platform `run_dao_platform_events` is `Ok`
  and no readiness path runs (R08-12's test, kept); at latest a due round activates through the
  dispatcher; the latest table's activations bound is non-zero by behaviour (five due, four
  activate).

**Block-proposal path** (`execution/engine/run_block_proposal/mod.rs`, beside R08-12's seeded
helper; `fast_forward_to_block(.., true)`, one seeded validator set, per memory
run-block-proposal-unit-test-needs-seeded-state; the mock Core RPC serves a constant masternode
diff):

- A round crossed at proposal time `t`; a proposal at `t + wait - 1` leaves it `Crossed`, the next
  at `t + wait` activates it; `run_block_proposal` returns a valid outcome both times.
- Rollback and retry: the activating proposal's transaction is rolled back; pointer, fund, pool,
  payer balance, deadline entry, record and root hash equal the pre-proposal values; the same
  proposal run again in a fresh transaction yields the same root hash and record.
- `FullAbciApplication::process_proposal` at candidate rounds 0 and 1 for the activating height:
  `ProposalStatus::Accept` both times, equal app hashes.
- Boundary versus transitions: the activating proposal also carries an ordinary transition (a
  document create) so the test pins that the event ran first (the activation record's height is
  the proposal height and the transition result is unaffected). A cancellation transition does
  not exist yet (R08-14); the "cancelled in an earlier block removes the deadline" case is covered
  through `cancel_readiness_round_operations` applied between two proposals.

No strategy test: reports do not travel as transitions until FIX-09; the proposal tests above
exercise the same path.
