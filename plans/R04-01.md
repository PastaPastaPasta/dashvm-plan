## 1. Acceptance restated

The owner-confirmed policy (section 4.2): ordinary contracts are not identities and stay that way; contract credits live in a separate sum balance tree with several credit buckets per contract and matching token buckets; each bucket carries spending rules; every bucket balance is included in credit and token conservation and reachable through query and proof paths; the ACL work planned for 4.3 is coordinated, not pre-empted.

The engineering recommendation this task adopts: an ordinary `SumTree` for the contract-credit root and for each contract's bucket subtree. A single bucket is proven as a `SumItem` under an authenticated parent; the whole per-contract total is the parent `SumTree` element's stored sum, proven against the Platform root. Live versus wiped is a property of that parent element: a wiped contract's subtree is wrapped in `Element::NotSummed`, its inner sum is retained for cleanup but contributes nothing to the root aggregate and is never reported as available credit. Range-sum proofs stay with specialized collections (`ProvableSumTree`), which this task does not touch.

Concretely, when the four parts are merged:

1. A new root tree holds contract credits: `[ContractCredits] / contract_id (SumTree) / bucket_key (SumItem)`. It exists from the 5.0 protocol version on fresh genesis and on upgrade, and it is the sixth term of the credit conservation equation.
2. DPP defines the bucket identifier (`ContractCreditBucketPosition = u16`, key codec big-endian two bytes), the bucket spending and deposit rules built on the existing `ChangeControlRules` and `AuthorizedActionTakers` (identity, contract owner, group), the lifecycle enum (`Live`, `Wiped`) and the proof result types. No keyless contract identity anywhere.
3. Drive has the storage primitives R04-02 and CAP-08 will call: create the per-contract tree, add to and remove from a bucket with checked arithmetic, read the tree state and a bucket, estimation, and refusal of every write against a wiped tree.
4. Drive has the query builders, provers and verifiers for one bucket and for the whole total, both reporting live, wiped or absent, with `FeatureVersion` slots in the verify tables and a clean verify-only build.
5. Contract token holdings extend the per-token ledger `[Tokens, 128, token_id]` through a reserved one-byte holder branch: `[holders] (SumTree) / contract_id (SumTree) / bucket_key (SumItem)`. Token supply conservation and the existing total-supply proof keep holding without code changes because the branch sums propagate into the per-token `SumTree`.

Out of scope, with the owning task named so nobody looks for it here: the wipe transition that flips a populated live tree to `NotSummed` (FIX-07, allocation A22; the pinned GroveDB has no primitive for it, see section 5.3); credit and token transfers, deposit checks, payouts (R04-02, R10-02, CAP-08); bucket declarations inside the data contract and the executable contract kind (CAP-02, R08-03); the gRPC, DAPI, proof-verifier `FromProof`, SDK and wasm surfaces (R13-14, CAP-12); the ACL primitive and its contract stub (EXT-ACL, STUB-ACL, INT-ACL); contract-held frozen token status and vestige custody (CAP-08, FIX-07); scheduled-job prefunds (R12-10).

|---|---|---|---|
| D1 | New root tree `RootTree::ContractCredits = 100`, an ordinary `SumTree`. | Provisional root allocation (register A09 says new root values are unallocated; collision-checked against `RootTree`, `TryFrom<u8>` and `KnownPath`: 100 is free). | Adjacent to `Balances = 96`; the credit trees (`Balances`, `AddressBalances`, `ShieldedBalances`) are all root-level `SumTree`s read by the conservation calculator. |
| D2 | Per-contract subtree at `[100] / contract_id` is an ordinary `SumTree`; buckets are `SumItem`s keyed by the two-byte big-endian bucket position. | Engineering recommendation from the issue, adopted. | Individual balance proven normally; total proven from the parent element; no provable-sum cost for a query nobody makes as a range. |

| D4 | Wiped state is `Element::NotSummed(SumTree(..))` at `[100] / contract_id`. | D5 | The per-contract tree is created lazily by the first deposit; the depositor pays its storage. | Provisional. | No contract-declaration surface exists yet; identity token balances are created on first credit the same way. |

| D9 | Token holder branch key `TOKEN_CONTRACT_HOLDERS_KEY: u8 = 0` under `[Tokens, TOKEN_BALANCES_KEY, token_id]`; nested `contract_id (SumTree) / bucket_key (SumItem)`. | Provisional key value; branch shape follows the storage DIP. | One byte cannot collide with a 32-byte identity id; nested trees give a per-contract token total as an authenticated element, symmetric with credits. |

## 3. Storage layout (final shape after all parts)

```text
Root Merk (18 keys after this change)
  100  ContractCredits                       SumTree      new, 5.0
    contract_id (32 bytes)                   SumTree      live contract; sum = live total
    contract_id (32 bytes)                   NotSummed(SumTree)   wiped contract; inner sum retained, contributes 0
      bucket_key = position u16 big-endian   SumItem(i64) one holding, 0 <= value <= MAX_CREDITS

  16  Tokens
    128  TOKEN_BALANCES_KEY                  BigSumTree   unchanged
      token_id                               SumTree      unchanged; sum now covers identity and contract holders
        identity_id (32 bytes)               SumItem      unchanged
        [0]  TOKEN_CONTRACT_HOLDERS_KEY      SumTree      new, 5.0, created lazily
          contract_id (32 bytes)             SumTree      per-contract holding total
            bucket_key (2 bytes)             SumItem      one holding
```

Conservation from protocol 17:

```text
total_credits_in_platform == total_in_pools + total_identity_balances + total_specialized_balances
                           + total_in_addresses + total_in_shielded_balances + total_in_contract_credits
```

`total_in_contract_credits` is the root `SumTree` aggregate, so wiped subtrees are excluded by construction. The wipe that moves a live total into the processing pool exactly once is FIX-07's; the equation above is what it must preserve.

Token conservation (`TotalTokensBalance`, `TotalSingleTokenBalance`) needs no change: contract holdings are part of supply and their sums propagate into the per-token `SumTree` and the `BigSumTree` above it.
