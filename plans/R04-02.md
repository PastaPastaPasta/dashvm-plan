## 1. Acceptance restated

Owner-confirmed policy (section 4.2 and the Q07/Q22/Q30 answers) as this task reads it:

1. A contract holds credits in buckets of its own credit tree, holds tokens in the reserved holder branch of each token ledger, and holds documents by being their owner. A contract is never an identity: nothing here creates an identity record, a key, or an identity balance for a contract id.
2. The contract declares, in its signed contract, the rules of each holding: who may move assets out (an identity, the contract owner, a group or nobody, with the group multi-party flow the token model already uses), who may deposit (anyone, only the spenders, nobody), which tokens it accepts, and whether it takes documents into custody. Native validation evaluates those rules on every move; guest code cannot bypass them and, in this task, does not run at all.
3. Deposits are checked on the receiving side. A payout may target one or many identities in one transition, each recipient must exist, and the sum is bounded and checked. A transfer between two contracts needs both permissions: the source bucket's spending rule for the signer and the target bucket's deposit rule for the same signer.
4. There is no path from a contract holding to Core. The holdings transitions have no withdrawal, address or script output; a contract id presented to any existing withdrawal path fails as an unknown identity or address. Outward movement always passes through an identity recipient under the existing identity withdrawal rules and limits.
5. Q07: every validator distinguishes the signer of the transition from the principal whose rules are evaluated. In this task the signer and the immediate caller are the same identity (ordinary signed transitions); the validators take the principal explicitly so the guest call path added later cannot pass signer authority by accident.
6. Q22 and Q30: a frozen contract may receive credits, tokens and documents; it may not spend, pay out or transfer them. A wiped contract may do neither. The matrix is a pure function in DPP; the storage that produces the frozen state belongs to the governance work, so in this task the Drive reader yields only live or wiped and the frozen branch is exercised through the pure function.
7. Every native asset rule keeps applying: token pause, frozen token accounts on either side (with the existing allow-transfer-to-frozen flag), destroyed issuers, credit and token conservation, one canonical amount per holding, checked arithmetic.

Out of scope, with the owning task named: the storage primitives and rule types (R04-01 parts 2 and 4; this task consumes them), guest-initiated moves and their action conversion (R10-02), the freeze state and its votes (R11-10), the wipe transition and vestige custody (FIX-07), contract-only create/replace/delete of documents (R04-03), contract-held token freeze (CAP-08), the gRPC, proof-verifier, SDK and wasm query surfaces for holdings (R13-14, CAP-12), refunds to buckets (FIX-08), the executable contract kind and its manifest (CAP-02, R08-03; they amend the contract generation introduced here in place).

## 2. What the tree looks like today (drift and seams)

- `DataContract` is `V0 | V1`; `DataContractV1` carries `groups`, `tokens`, `keywords`, `description`. `DataContractInSerializationFormat` is `V0 | V1` (bincode, positional). Adding a field to V1 changes the bytes of every stored contract, so holdings need a new generation. Fan-out counted: 72 `DataContract::V1` mentions in rs-dpp (accessor and conversion matches plus fixtures), 61 in rs-drive (all test literals, unaffected), 2 in rs-drive-abci, 1 exhaustive match in wasm-dpp2 (`model.rs`, sets tokens); `DataContractInSerializationFormat::V1` 57 in rs-dpp, 6 in rs-drive-abci, 4 in wasm-dpp2, 1 reference in rs-platform-wallet. `CONTRACT_VERSIONS_V6` (protocol 14) has `contract_structure_version: 1` and serialization bounds `0..=1` default 1.
- `BatchedTransition` is `Document | Token` (serde tag `$transition`, bincode positional, append-only). `TokenTransition` carries the group multi-party flow through `TokenBaseTransitionV0.using_group_info`, resolved in `TokenBaseTransitionActionV0::try_from_base_transition_with_contract_lookup` (Drive) into `store_in_group` and `perform_action`, converted to `GroupOperationType::AddGroupAction` and gated by `TokenBaseTransitionAction::validate_group_action` (ABCI). Match sites on the umbrella: `BatchedTransition::Token` 16 files, `BatchedTransitionRef/MutRef::Token` 13 files, `BatchedTransitionAction::TokenAction` 22 files (the transformer, advanced structure, state, conversion, security level, tests, strategy verify, wasm-dpp2, wasm-dpp, wallet FFI, proof verify of executed transitions).
- `GroupActionV0 { contract_id, proposer_id, token_contract_position, event: GroupActionEvent }`, `GroupActionEvent { TokenEvent(TokenEvent) }`. The group actions gRPC handler maps token events only and returns `None` for the transfer, purchase and claim events, so an unmapped event is already a silent filter there.
- `BatchTransitionActionV0::all_used_balances` sums purchases and contested collateral into `ExecutionEvent::Paid.removed_balance`; that is the hook for a deposit paid from the signer's balance.
- Document transfer today: the transformer sets `owner_id = recipient_owner_id`, removes the price and bumps the revision; the ABCI transformer rejects a signer that is not the stored owner (`DocumentOwnerIdMismatchError`); there is no recipient existence check of any kind. Purchase pays the original owner through `AddToIdentityBalance`, which would create a phantom identity balance for a contract owner; it is unreachable for contract-owned documents because a price can only be set by the owner's signature.
- `SystemLimits` is at V4 (protocol 14). Two open lanes each add a `SYSTEM_LIMITS_V5` for protocol 17 with different fields (computation limits on #4705, contract code limits on #4717); the second to land amends in place.
- Consensus error codes: state band token 40700 to 40721 (FIX-07 part 2 takes 40722), group 40800 to 40804, shielded 40900 to 40904, nothing at or above 41000. Basic band: data contract 10200 to 10276, state transition 10600 to 10603 (R06-05 takes 10604), nothing in 10900 to 10999. `wasm-dpp`'s consensus error mapping is exhaustive over `StateError`.
- Drive validators that return `SimpleConsensusValidationResult` exist (`validate_document_transfer_transition_action_uniqueness`), so shared stateful holdings checks can live in Drive with thin ABCI adapters, which is what the NATIVE_VALIDATE module asks for.
- `DriveLowLevelOperationConverter::into_low_level_drive_operations` has no pending-operations parameter on this base; FIX-07 part 1 adds `previous_batch_operations` and R04-01 part 2 threads it through the bucket writers. Whichever shape is on `v5.0-dev` when a part starts is the one the new operation types implement.

| D4 | Authorization semantics. Contract-to-contract transfer: source bucket spending rule for the signer AND target bucket deposit rule for the same signer. | Provisional reading of "both contracts permit the transfer". | The signer is the only principal a native transition has (Q07: signer and caller are the same identity here and are passed separately so the guest path cannot conflate them). | D7 | Group flow reuse: `GroupActionEvent::ContractHoldingsEvent(ContractHoldingsEvent)` appended; `GroupActionV0.token_contract_position` carries the bucket position for holdings actions (documented on the field; the name is shipped). Holdings group actions are not mapped by the group actions gRPC handler in this task (it already filters unmapped events); the query surface is R13-14's. | Provisional. | No second group action store; append-only enum. |
| D8 | Stateful holdings validation lives in Drive, `packages/rs-drive/src/drive/contract/holdings/validation/`, as versioned methods returning `SimpleConsensusValidationResult` plus recorded costs (`FeeResult`), with an explicit `HoldingsPrincipal { signer, caller }` input. | D9 | Lifecycle matrix in DPP: `ContractHoldingsStatus { Live, Frozen, Wiped }` with `can_receive()` (Live, Frozen) and `can_spend()` (Live only). The Drive reader `holdings_status` maps R04-01's credit tree state (absent or live tree to `Live`, not-summed tree to `Wiped`) and, once FIX-07's issuer record is on the base, a destroyed issuer to `Wiped`; nothing produces `Frozen` until the governance work adds the source and a reader generation.
