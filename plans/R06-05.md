# R06-05 plan: large bounded contract create/update envelopes

Working artifact. Never staged, never committed. Delete when the task ships.

Base `v5.0-dev` (tip `5f1e0ccdce`, protocol tables identical to `v4.2-dev` and `v4.3-dev`,
`LATEST_VERSION = 14` on the base; the sibling PR #4705, R06-01, introduces `v15.rs`, `v16.rs`,
`v17.rs`, `SYSTEM_LIMITS_V5`, `FEE_VERSION3` and `LATEST_VERSION = 17`). Two sequential parts,
both on `v5.0-dev`, part 2 stacked on part 1. Tier stays `xhigh`: the work changes the wire shape
of two state transitions, the consensus size limits, fee operations, the Tenderdash block
consensus parameters and the decode path every block runs.

## 1. Acceptance, restated

Q39 (confirmed direction) says: extend the existing contract create and update transitions so they
can carry large canonical code and declarations; apply larger, bounded limits consistently on every
ingress path (DAPI, mempool CheckTx, proposal, block validation, replay, proof requests, clients);
do not add a separate upload route. The single-transition form and the sizes are engineering
proposals. Q40 delegates the numbers: take the register's provisional values now, measure, revise
before activation. Allocation A17 (this task) says: prototype one bounded upload; chunking only
with a complete separate design.

Concretely this task delivers:

1. A new wire generation of both transitions, `DataContractCreateTransitionV1` and
   `DataContractUpdateTransitionV1`, appended to their enums, carrying the existing fields plus an
   optional bounded code bundle (`CodeBundleSubmission`). The bundle is signed with the rest of
   the transition (whole execution intent signed, DVM-01).
2. Family-specific size caps: ordinary transitions keep 20 KiB; the two contract families in their
   V1 form get a protocol-versioned cap (provisional 32 MiB) that every ingress path reads from
   the same table and that is enforced before the large decode.
3. Native validation of the envelope: cheap structural bounds at basic structure (CheckTx and
   block), exact-bytes hash binding of every supplied module at transform time in the block (paid,
   nonce bumped on failure), consistent with how full contract schema validation is already
   block-only.
4. Costs: the hashing the node performs for a V1 envelope (signature hash over the signable bytes,
   one SHA-256 per module) is charged through the existing hashing fee group, plus one provisional
   base admission fee from the register, added in both CheckTx and block so the CheckTx
   affordability estimate covers the actual charge.
5. Transport and execution paths: the block decode generation, CheckTx, proposal, `getProofs`,
   rs-dapi request caps, the Tenderdash mempool and RPC configuration, the Tenderdash block size
   consensus parameter pushed by Drive at activation, the Drive gRPC server caps, the Rust and
   JavaScript client builders.
6. A benchmark of the proposed sizes and a decision on chunking (section 3, D1: no chunking).

Explicitly not here (owned elsewhere and stated in the PR body): persistent storage of accepted
modules and the contract executable namespace (R06-04, R08-03), the manifest and method or
capability declarations inside the contract (R08-03), WASM parsing, feature allowlist and
per-operator pricing (R08-02, R08-01, R12-03), deployment readiness and activation (R08-12),
SDK deployment builders across Rust, WASM, JS and mobile (R13-08), the smart-contract error
taxonomy for execution outcomes (R12-07). Section 3, D2 explains how the code bundle stays
dormant on the 5.0 protocol version until R06-04 lands storage, with one table flip.

## 3. Decisions

- **D1. One bounded transition; no chunking.** The benchmark shows a 32 MiB envelope decodes in
  under 2 ms and hashes twice (module hash and signature hash) in about 110 ms on this machine,
  well inside a CheckTx or a block slot; Tenderdash's hard block cap is 100 MB and its ABCI socket
  reader accepts 100 MB, so a 32 MiB transaction needs only configuration, no protocol work.
  Chunking would add staging state, expiry, cleanup fees and refunds that the owner asked to
  specify only if measurements require it (section 6.2, A17). They do not. The remaining transport
  cost is bandwidth: at the dashmate default of 5,120,000 bytes per second per peer, a 32 MiB
  transaction takes about 7 seconds per hop to gossip, so the plan raises the p2p rate defaults
  (D12) and records the measured gossip time as the one number the testnet rehearsal (R14-04) must
  confirm before the cap is final. Recorded in the PR body as the chunking decision, with the
  table above.
- **D2. The code bundle is a wire-level optional field that the 5.0 protocol version admits only
  when its storage exists.** `DataContractCreateTransitionV1` and `DataContractUpdateTransitionV1`
  carry `code_bundle: Option<CodeBundleSubmission>`. This task lands the envelope, its limits and
  its validation; R06-04 lands the permanent module storage and the 0..4 namespace. Until R06-04
  merges, a V1 transition with `Some(bundle)` is rejected at basic structure with
  `CodeBundleNotSupportedError` under every protocol version, through one table slot
  (`DPPStateTransitionSerializationVersions.contract_code_bundle: Option<FeatureVersion>`, `None`
  everywhere until R06-04 sets `Some(0)` on the 5.0 tables). A V1 transition with `None` behaves
  exactly like a V0 one apart from the larger byte cap. This keeps part 2 mergeable and testable
  without R06-04 while the bundle format, limits and hashing are exercised end to end in tests
  through a test-only table override (section 7).
- **D3. Two new wire generations, appended.** `DataContractCreateTransition::V1` and
  `DataContractUpdateTransition::V1` under the existing `$formatVersion` tags (`"1"`), new
  `v1/` directories cloned from `v0/` (files `mod.rs`, `identity_signed.rs`,
  `state_transition_like.rs`, `types.rs`, `v0_methods.rs` renamed `v1_methods.rs`, `version.rs`).
  The serialization table's `contract_create_state_transition` and
  `contract_update_state_transition` bounds become `max_version: 1, default_current_version: 1`
  only on the 5.0 tables (`STATE_TRANSITION_SERIALIZATION_VERSIONS_V4`, new, referenced by
  `PLATFORM_V17`); V1 to V3 keep `0/0/0`. `active_version_range()` gains arms: create or update
  `V1(_)` is `PROTOCOL_VERSION_17..=LATEST_VERSION` (the constant R06-01 introduces), so a V1
  envelope decoded under an older active version is not active, exactly like the format-V1
  contract at protocol version 9. D4 fixes how that rejection is classified.
- **D4. Not-active is an unpaid consensus rejection, never an internal error.** Today
  `StateTransitionIsNotActiveError` comes back as `ProtocolError::StateTransitionError` and the
  decoder puts it in `FailedToDecode`, which the block loop turns into an `InternalError` result
  and `process_proposal` rejects the whole block. A pre-activation V1 envelope must not have that
  power. The new decode generation (D5) maps it to
  `BasicError::StateTransitionNotActiveError` (existing, code 10603) as `InvalidEncoding`, so a
  proposer drops it and a validator rejects only that transaction. Same shape as the oversized
  case.
- **D5. Family-specific size limits live in `SystemLimits` and are enforced by a new decode
  generation.** `SystemLimits` gains `max_contract_code_state_transition_size: Option<u64>`
  (`None` on V1 to V4 and the mocks; `Some(33_554_432)`, 32 MiB, on `SYSTEM_LIMITS_V5`, amended in
  place per the unreleased-table rule) and `max_contract_code_bundle_bytes: Option<u64>`
  (`Some(16_777_216)`, 16 MiB, on V5: the sum of the canonical module bytes one bundle may carry).
  Enforcement is `decode_raw_state_transitions_v1` (new; `DRIVE_ABCI_METHOD_VERSIONS_V11`, new,
  referenced by `PLATFORM_V17`; `v0/` stays byte-identical): the raw length is compared with the
  family cap decided by a prefix peek (D6) before any decode, then decoded through the new
  `StateTransition::deserialize_from_bytes_in_version` path with the family's bincode limit (D7).
  `max_state_transition_size` keeps its value and meaning for every other family. The doc comment
  on it changes from "must equal `max-tx-bytes`" to "the Tenderdash `max-tx-bytes` must be at
  least the largest family cap" (D11).
- **D6. Family detection is a bounded prefix decode, not a full decode.** The `StateTransition`
  discriminant is the bincode big-endian varint of the variant index (u32 encoding: one byte for
  indices below 251), followed by the inner enum's variant index. `dpp` gains
  `StateTransition::peek_envelope_kind(bytes) -> Result<StateTransitionEnvelopeKind,
  ProtocolError>` that reads at most the first 6 bytes with `bincode::decode_from_slice::<u32>`
  twice and returns `Ordinary` or `ContractCodeCapable { family }` for `DataContractCreate::V1`
  and `DataContractUpdate::V1` (variant indices 0 and 4 outer, 1 inner). Anything else, including
  an unknown index or a truncated prefix, is `Ordinary`, so it is bounded by 20 KiB and fails
  decode as it does today. The V0 forms stay at 20 KiB. A unit test in `dpp` pins the byte
  prefixes of all four variants so a reordering of the enum cannot silently move the cap.
- **D7. Two bincode limits on the state transition.** The derive's const `limit = 100000` becomes
  two entry points: the derive keeps generating `deserialize_from_bytes` with the const limit, and
  `dpp` adds `StateTransition::deserialize_from_bytes_with_limit(bytes, limit: usize)` as a hand
  written method (bincode's `with_limit` is a const generic, so the method matches the four caps
  it can be called with: the two `SystemLimits` values are read into a `usize` and mapped onto a
  fixed set of const limits, `20_480`, `100_000` and `33_554_432`, through a small `match`; a
  value outside the set is a `ProtocolError::CorruptedCodeExecution`, unreachable while the tables
  hold those numbers, and pinned by a test over every `PLATFORM_VERSIONS` entry). Serialization
  keeps the const 100,000 limit for `serialize_to_bytes`; the V1 builders in `dpp` and the SDKs
  use the existing `serialize_consume_to_bytes` path through a new
  `StateTransition::serialize_to_bytes_with_limit` mirror. `deserialize_from_bytes_in_version`
  becomes the dispatcher: it peeks the kind (D6), picks the cap from `platform_version`, and calls
  the limited decode, so every caller that already passes a `PlatformVersion` (block decoder,
  CheckTx, tests) gets the family cap for free.
- **D8. The bundle type and its bounds.** In `dpp`,
  `state_transition/state_transitions/contract/code_bundle/{mod.rs, v0/mod.rs}`:
  `CodeBundleSubmission { V0(CodeBundleSubmissionV0) }`, `CodeBundleSubmissionV0 { modules:
  Vec<CodeModuleSubmission> }`, `CodeModuleSubmission { V0(CodeModuleSubmissionV0) }`,
  `CodeModuleSubmissionV0 { name: String, canonical_hash: [u8; 32], code: Vec<u8> }`. Bounds
  (provisional, register rows "Canonical WASM" and "Module structure"; every number lives in
  `SystemLimits` next to the two above, `Some` only on V5): at most 16 modules per bundle
  (`max_contract_code_modules_per_bundle: Option<u16>`), names 1 to 64 bytes of lower-case ASCII
  alphanumerics and underscore, unique and strictly ascending (canonical order, so two
  encodings of one bundle cannot both be valid), every `code` non-empty, the sum of `code`
  lengths at most `max_contract_code_bundle_bytes`. `canonical_hash` is SHA-256 over
  `b"dashvm-canonical-module-v0" || code` (domain separated; R08-01's `CanonicalHash` uses the
  same construction and the constant moves to `dashvm-validation` when that crate lands; until
  then it lives in `dpp::state_transition::code_bundle::canonical_hash`). The hash is carried on
  the wire so that a later reference-by-hash form (R06-04 dedup, "existing-blob references" in
  DVM-01) and the readiness report can name a module without re-hashing, and so the manifest
  (R08-03) can bind it. No manifest, bindings, entries, ABI or profile identifiers here: those are
  R08-03 and R08-04 fields, appended to `CodeBundleSubmissionV0` or a `V1` when they land.
- **D9. Validation tiers.** Basic structure (CheckTx and block, stateless): a new
  `basic_structure/v3` for create and `v2` for update, cloned from the previous generation, that
  after the existing checks validates the envelope: bundle present only if
  `contract_code_bundle` is `Some` (else `CodeBundleNotSupportedError`), module count, name
  grammar and order, non-empty code, total bytes (`CodeBundleTooLargeError`,
  `CodeModuleNameError`, `TooManyCodeModulesError`). Selected by
  `DRIVE_ABCI_VALIDATION_VERSIONS_V11` (new, referenced by `PLATFORM_V17`): create basic
  `Some(3)`, update basic `Some(2)`. Transform into action (block only, paid): the Drive
  transformers `try_from_transition` for V1 hash every module and compare with `canonical_hash`;
  a mismatch is `ProtocolError::ConsensusError(CodeModuleHashMismatchError)`, which the existing
  transform v0 already maps to a bump-nonce action plus the error. The hash is deliberately not
  checked in CheckTx: it costs up to 50 ms per transaction at the cap and the admission rule (DVM-01
  phase 3) is "structural and affordability checks without guest execution"; the mempool is
  protected by the byte cap and the hashing fee. Recorded in the PR body as a provisional
  interpretation; FIX-06 may move it if measurements say otherwise. Signature and nonce tiers
  are unchanged. No state validation change: nothing is stored yet (D2).
- **D10. Costs.** The V1 transformer records `ProtocolValidationOperation::CodeModuleHash(bytes)`
  per module (new variant, priced through `fee_version.hashing.single_sha256_base` and
  `sha256_per_block` with the 64-byte block count computed with checked arithmetic) plus one
  `ProtocolValidationOperation::CodeBundleAdmission` priced by a new
  `FeeDashVmVersion.code_bundle_admission_base_fee` (provisional 100,000 processing credits,
  register "deployment validation 100,000 processing credits plus 20 per canonical WASM byte";
  the per-byte and per-operator components are R08-02/R12-03's once a WASM parser exists). Both
  are added in the transformer, which runs in CheckTx and in the block, so
  `validate_fees_of_event` sees them; the hash work itself runs only in the block (D9), the
  operation is recorded in both so the estimate is never below the actual. The signature hash
  over up to 32 MiB is already paid by the existing `SignatureVerification` operation only at the
  key type's flat rate; the V1 transformer adds `ValidationOperation::DoubleSha256(blocks)` for
  the signable bytes length so the hashing of a large envelope is charged proportionally (block
  count from `signable_bytes().len()` divided by 64, checked). `FEE_VERSION3` and
  `FEE_DASHVM_VERSION1` (R06-01) are amended in place; `fee_version_number` stays 1 (no storage
  rate changes). `calculate_min_required_fee` for the two families adds
  `code_bundle_admission_base_fee` when a bundle is present so the CheckTx balance pre-check
  reflects it.
- **D11. Tenderdash sizes are protocol state, pushed by Drive.** The block byte cap is a consensus
  parameter (`ConsensusParams.block.max_bytes`); the only way every validator agrees on it at the
  same height is for Drive to return it in `consensus_param_updates` when the protocol version
  changes. `ConsensusVersions` gains `block_max_bytes: Option<u64>` and `block_max_gas:
  Option<i64>` (`None` on v1 to v14 and the mocks; `Some(37_748_736)`, 36 MiB, and
  `Some(57_631_392_000)`, the existing value, on the 5.0 version so the update does not zero the
  gas limit: `UpdateConsensusParams` copies both fields whenever `Block` is present).
  `consensus_params_update_v2` (new; `DriveAbciEngineMethodVersions.consensus_params_update = 2`
  in `DRIVE_ABCI_METHOD_VERSIONS_V11`) emits `block: Some(BlockParams { max_bytes, max_gas })`
  when the new version's values are `Some` and differ from the old version's, keeps the v1
  version-params behaviour otherwise, and `init_chain` sends them at genesis of a new network.
  36 MiB leaves 4 MiB for commit, evidence and header on top of one maximal transaction; the
  proposer already trims to `request.max_tx_bytes`. `max-tx-bytes` (mempool, node-local) and
  `max-body-bytes` (RPC, node-local) become dashmate options `platform.drive.tenderdash.mempool.
  maxTxBytes` (default 33,554,432) and `platform.drive.tenderdash.rpc.maxBodyBytes` (default
  50,000,000: base64 inflates the 32 MiB transaction to 44.7 MB inside the JSON-RPC body), with a
  config migration under the next dashmate version key; genesis `block.max_bytes` in the dashmate
  defaults stays 2 MiB because Drive raises it at the protocol boundary (a fresh 5.0 devnet gets
  it from `init_chain`).
- **D12. Node-local transport caps follow the largest family cap plus envelope overhead.**
  rs-dapi: `MAX_PLATFORM_DECODING_BYTES` becomes 34 MiB, applied only to the Platform service as
  today (the comment already states the invariant); `broadcast_state_transition` pre-filters with
  the family cap through the same `peek_envelope_kind` (unchanged behaviour for ordinary
  transitions); `wait_for_state_transition_result` needs nothing (the Drive client already allows
  64 MiB). Drive's gRPC server (`server.rs`) sets `max_decoding_message_size(34 MiB)` on the
  Platform, DriveInternal and ABCI CheckTx services (today tonic's 4 MiB default would reject a
  large CheckTx before Drive saw it). `getProofs` v0 is left as is and a `proofs_query = 1`
  generation decodes through `deserialize_from_bytes_in_version` with the active version. Envoy:
  the gateway buffers 32 KiB per connection and streams, so no body limit is hit; the Platform
  route timeout (60 s) covers a 32 MiB upload at 1 MB/s. `rs-dapi-client` and `js-dapi-client`
  need no cap change to send (only receive caps are set); the Rust and JS builders get the new
  serialize path (D7). Dashmate p2p `sendRate`/`recvRate` defaults rise to 20,480,000 bytes per
  second, provisional, recorded for R14-04.
- **D13. Consensus errors.** Basic, DataContract band, appended to `BasicError` and
  `codes.rs`: `CodeBundleNotSupportedError` 10277, `CodeBundleTooLargeError` 10278 (actual,
  max), `TooManyCodeModulesError` 10279 (count, max), `CodeModuleNameError` 10280 (position,
  reason), `CodeModuleHashMismatchError` 10281 (position, expected, actual), `EmptyCodeModuleError`
  10282 (position). State transition band: `StateTransitionFamilyMaxSizeExceededError` 10604
  (family name, actual, max), used by the v1 decoder for the contract families so the message
  names the cap that applied; ordinary families keep 10602. Each is its own file under
  `errors/consensus/basic/data_contract/` or `basic/state_transition/` with the standard derive
  stack and the ordering banner. `wasm-dpp/src/errors/consensus/consensus_error.rs` gets the
  seven arms (exhaustive match; generic mapping). `wasm-dpp2/src/consensus_error.rs` is untouched
  (it mirrors only the codes JavaScript branches on).
- **D14. What stays byte-identical.** Every shipped `vN` module: `decode_raw_state_transitions/
