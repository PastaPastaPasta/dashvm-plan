# PLAN R12-01: repair and test fee-registry numbering, lookup, persisted round trips and historical storage-table compatibility

Working artifact. Never staged, never committed. Delete when the task ships.

Base: `v4.2-dev` at `d02072827f` (branch `dashvm/r12-01`). Release target 4.3-dev (workstream 43-FEES, issue 4675). Single part. Tier stays xhigh.

## 1. Acceptance, restated

The owner policy (section 12.1) says: every registered fee number must resolve to the intended table, persisted state must round-trip its number, storage refunds must use the appropriate historical rates, and allocation and repair must preserve existing history. The DIP draft (DVM-07, "Fee version integrity") adds: identifiers round-trip between persisted numbers, registry lookup and every PlatformVersion reference; unknown identifiers are errors, not a fallback to the current table or an array index; old records keep their storage flags and refund rates; replay stored fee IDs through every registry entry and reject unknown IDs. The workstream issue narrows this task to: fix fee-registry numbering and persisted version lookup, and reject unknown fee versions in existing tooling. Completion criteria: existing fee tables and old protocol results remain reproducible; any consensus-visible correction needs an explicit version boundary; nothing rewrites historical fees.

Deliverables, in my words:

1. The fee registry resolves a `fee_version_number` by number, never by array position, and rejects 0 and any unregistered number with an error on every entry point (`get`, `get_optional`, `as_static`). No panic path remains for an unknown number.
2. Every `PLATFORM_V*` (and the two mock test versions) references a schedule whose number is registered, and the registered entry agrees with that schedule on every value the fee-history map can be asked for (`KnownCostItem`).
3. A stored platform state whose fee-history map holds a number this build does not know fails to load with a descriptive error instead of aborting the process. The `drive-abci verify` subcommand and the checkpoint loader inherit this because they use the same deserialize path.
4. The persisted number round-trips: for every registered number, a saved state containing that number loads back to the registered entry; the map the epoch-change hook builds in memory and the map reloaded from disk agree on every `KnownCostItem` for every epoch.
5. Historical storage-table compatibility: a refund computed with a fee history that changes storage rate at epoch E uses the pre-E rate for epochs before E and the post-E rate at and after E; schedules with number 1 keep the legacy empty-map refund path; the two legacy on-disk formats (`PlatformStateForSavingV0` from the 1.x line, `V1` from 1.4 onward) still load and their entries resolve to number 1 with the shipped storage rates.
6. Everything that shipped stays byte-identical: every `FEE_VERSION*` constant, every fee-group constant, every `PLATFORM_V*`, `consume_to_fees_v0`, `EpochCosts::active_fee_version`, `upgrade_protocol_version_on_epoch_change_v0`, both `PlatformStateForSaving` structs and their bincode encodings, and the V0 legacy mapping to the first fee version.

No capability requirements are attached to this task (related capabilities: none recorded).

## 3. Design decision: do not renumber `FEE_VERSION2`

Considered: give `FEE_VERSION2` `fee_version_number: 2` and register it, so `get(2)` returns the schedule protocol versions 9 to 14 reference. Rejected, with evidence:

- `consume_to_fees_v0` (`op.rs:280`) branches on `fee_version_number == 1`. Renumbering flips protocol versions 9 to 14 onto the map-driven refund path for every historical block, which is a replay-affecting change inside shipped code, and the block-lifecycle callers listed above pass `None` history, so the flip would surface `CorruptedCodeExecution` on a withdrawal document cleanup or an epoch change. That is the caller audit R12-02 owns.
- The conventions chapter (which outranks this plan) states the number keys persisted fee history and storage-refund behaviour and is changed only when storage rates change. Storage rates did not change between the two schedules.
- The completion criteria forbid consensus-visible corrections without an explicit version boundary. A renumbering would belong to a new schedule referenced only by an unreleased protocol version, after R12-02.

Chosen: `fee_version_number` is the identifier of a fee-history generation (the set of values `KnownCostItem` can read: storage, processing, hashing, signature). `FEE_VERSIONS` is the registry of those generations keyed by number. A schedule referenced by a PlatformVersion must carry a registered number, and the registered entry must agree with the schedule on every `KnownCostItem`. `FEE_VERSION1` and `FEE_VERSION2` both satisfy this with number 1 because they differ only in `data_contract_registration`, which the history map never serves. The repair is to the lookup (by number, total, error on unknown), to the load path (error instead of abort), and to the tests that pin these invariants so a future schedule with new storage rates cannot be added without registering a new number. This goes in the PR body as the chosen interpretation.

## 4. Approach by crate and file

### 4.1 `packages/rs-platform-version/src/version/fee/mod.rs` (VERSION module)

- Keep `FEE_VERSIONS: &[FeeVersion] = &[FEE_VERSION1]` (content unchanged). Add a doc comment stating what the registry is (fee-history generations keyed by `fee_version_number`), that entries are ordered by number starting at 1, and that a schedule with changed storage rates must be registered under a new number.
- `FeeVersion::get(version)`: resolve by number match (`FEE_VERSIONS.iter().find(|fee_version| fee_version.fee_version_number == version)`), returning `PlatformVersionError::UnknownVersionError(format!("no fee version {version}"))` for 0 and for any unregistered number. Same message text as today so existing callers see no change.
- `FeeVersion::get_optional(version)`: same lookup, `Option`.
- `FeeVersion::as_static(&self)`: return `Result<&'static FeeVersion, PlatformVersionError>` (no `expect`). Doc comment: returns the registered fee-history entry for this schedule's number; it agrees with this schedule on every value the history map serves but is not necessarily the same schedule constant.
- `first()` / `latest()`: back them with a compile-time non-empty assertion (`const _: () = assert!(!FEE_VERSIONS.is_empty(), "...")`) so the `expect` is provably unreachable; keep signatures. Optionally add a `const fn` well-formedness check (numbers contiguous from 1) under a `const _: () = assert!(...)`; if the const evaluation of field reads through a slice does not compile on the workspace toolchain, keep it as a unit test instead.
- `FeeVersionFieldsBeforeVersion4` and its `From` (number 1): unchanged.
- Tests (new `#[cfg(test)] mod tests` at the bottom of `fee/mod.rs`):
  - `should_resolve_every_registered_number_to_the_entry_with_that_number` (for each entry, `get(n)` is the same entry by value and `get_optional(n)` is `Some`).
  - `should_reject_zero_and_unregistered_numbers` (`get(0)`, `get(len + 1)`, `get(u32::MAX)` are `Err`; `get_optional` is `None`).
  - `should_keep_registered_numbers_unique_and_contiguous_from_one` (structural guard so a future entry cannot be appended with a duplicate or skipped number).
  - `should_register_the_number_every_platform_version_references` (iterate `PLATFORM_VERSIONS`; `get(pv.fee_version.fee_version_number)` succeeds and `storage`, `processing`, `hashing`, `signature` are equal to the referenced schedule's groups). Under `#[cfg(feature = "mock-versions")]` also cover `TEST_PLATFORM_V2` and `TEST_PLATFORM_V3`.
  - `should_keep_fee_version_one_storage_rates_frozen_for_replay`: pins `get(1).storage` to `27000 / 400 / 20 / 10 / 2000` with a replay rationale comment (a historical freeze test, explicitly allowed by the conventions).
  - `should_return_the_registered_entry_from_as_static` and `should_error_from_as_static_for_an_unregistered_number` (construct a `FeeVersion` with number 0 or 99 by struct update from `FEE_VERSION1`).

## 5. Versioning consequences

- New `vN` method generations: none. No versioned method's behaviour changes.
- `SystemLimits`, fee schedules, `FEE_VERSION*`, fee-group constants: untouched.
- Protocol-version tables (`PLATFORM_V1` to `PLATFORM_V14`, mocks): untouched.
- Consensus error codes: none. The new failure is an internal load error (`ExecutionError::CorruptedCachedState`), not a consensus error.
- Proto, SDK, wasm, FFI surfaces: none. Public Rust API changes inside the workspace: `FeeVersion::as_static` becomes fallible; `PlatformStateForSavingV1 → PlatformState` becomes `TryFrom`. Both have one in-tree caller each; no client crate uses them.
- Byte-identical: every shipped fee constant and platform version constant; `consume_to_fees_v0`; `active_fee_version`; `upgrade_protocol_version_on_epoch_change_v0`; `PlatformStateForSavingV0`/`V1` layouts and encodings; the legacy V0 to number 1 mapping. Replay from genesis and saved-state load produce the same refunds as before this PR at every protocol version.
- Storage layout, proofs, verify cut: untouched (no `src/verify/**` change, no verify-only build needed).

## 8. Findings handed to later tasks (recorded in the PR body, no code change here)

- R12-02 (refund caller audit): the block-lifecycle callers listed in section 2 pass `None` fee history to Drive. Safe while every registered number is 1; any schedule registered under a new number makes `consume_to_fees_v0` require history on those paths. The tests in 4.4 pin that requirement.
- R12-02 (replay versus saved state, historical rates): `FeeRefunds::from_storage_removal` prices removed bytes at the fee version active at the current epoch, not at the storage epoch. The test in 4.3 pins the current behaviour by name so a deliberate change has a baseline and an explicit version boundary.
- FIX-08 (5.0, refund-owner encoding and old fee versions): `CachedEpochIndexFeeVersions` holds `&'static FeeVersion`; the registry-entry-versus-schedule distinction documented in 4.1 is the seam a typed owner encoding must respect.
