# R08-01 plan: DashVM runtime abstraction, engine dispatch, deterministic configuration, compiled cache

Working artifact. Never staged or committed. Delete when the task ships.

Base: `v5.0-dev` at `5f1e0ccdce` (worktree branch `dashvm/r08-01`). Tier: xhigh (VM boundary, protocol version tables). Three sequential parts, all on `v5.0-dev`.

## 1. Acceptance restated

R08-01 delivers the engine layer of DashVM as two library crates plus the protocol table that selects their behaviour, and it specifies (in code, tests and one book chapter) how compiled artifacts are keyed, stored, trusted, retained and rebuilt for executable versions and historical replay.

Concretely the task is done when:

1. `packages/rs-dashvm-validation` (Cargo `dashvm-validation`) turns submitted canonical WASM for a whole named-module bundle into validated, instrumented, prepared WASM plus metadata, deterministically, with no Wasmtime, Drive, DPP or ABCI dependency. It rejects features outside the admitted profile, enforces structural bounds, injects the portable logical-stack accounting, validates its own output, and preserves canonical and prepared hashes separately.
2. `packages/rs-dashvm` (Cargo `dashvm`) pins upstream Wasmtime 36.0.14 with Cranelift, builds a deterministic engine from a protocol-selected profile, compiles prepared modules into local native artifacts, caches them under a compatibility key, links the entry module's dependency closure of a bundle (separate memories and tables, one shared logical stack, one shared computation budget, one shared memory reservation), initialises that closure in a deterministic order with metered initialisation work, invokes an entry through a small host envelope, classifies every outcome, and reports consumption in computation units.
3. `packages/rs-platform-version` carries the new `dashvm` table (`PlatformVersion.dashvm: Option<DashVmVersion>`): `None` in every shipped protocol version and mock, `Some(DASHVM_VERSION_V1)` on the 5.0 protocol version. Engine profile, preparation generation, metering generation, runtime limits and metering weights all live there; the crates project them, never define them.
4. A real Rust-compiled two-module guest bundle prepares, compiles, links, initialises and executes end to end under the pinned engine, with identical outputs and computation counts on x86_64 (Linux CI) and aarch64 (macOS CI). Runtime scaffolding alone does not satisfy the acceptance; the fixture must run.
5. Compiled-cache behaviour is specified and implemented: key binding, atomic storage, integrity checks before the unsafe deserialise, corruption handling, retention groups (runnable, pending, historical), eviction limited to historical artifacts, rebuild from canonical code, and profile-per-protocol-version selection for replay.

Out of scope, delivered by dependents: exact caps and complete opcode weight table (R03-04, R03-07, FIX-05, R12-04), the full typed guest ABI, handles and context encodings (R08-04, R13-01), contract-level version resolution and the active contract stack (R10-10, R10-11, in `rs-drive-contracts`, which this task does not create), readiness, restart and cache-loss orchestration in ABCI (R08-06, R11-06), consensus error codes and fee integration (R12-07, R08-05), adversarial corpus and differential tooling (R03-01, R08-08, R11-09), state transitions and any protocol activation gate (R08-11).

## 3. Design decisions

### 3.1 Engine pin and profile (allocation A04, provisional)

Pin `wasmtime = "=36.0.14"` with `default-features = false, features = ["runtime", "cranelift", "std"]`. No `gc`, `threads`, `component-model`, `async`, `pooling-allocator`, `cache`, `profiling`, `coredump`, `debug-builtins`, `winch`, `parallel-compilation`. Rationale: the only supported line that compiles on the pinned toolchain, LTS to August 2027, every 2026 advisory patched. Upgrade path: the 48.x LTS needs Rust 1.95; when the workspace toolchain moves, a new engine profile version (`profile::v1`) and a new protocol version select it (R11-08 owns that change; this plan only records the path).

`dashvm::engine::profile::v0` builds the `wasmtime::Config` from `DashVmVersion` and returns an `EngineProfile` descriptor whose canonical string is part of the artifact key:

| Setting | Value | Consensus-relevant | Why |
| --- | --- | --- | --- |
| strategy | Cranelift | yes | confirmed engine |
| target | host triple passed explicitly (`x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`, ...) with no `cranelift_flag_enable` calls | yes | explicit target disables host CPU feature inference; baseline ISA per architecture is the CPU feature policy |
| opt level | Speed | no (output-preserving) | pinned anyway, in the artifact key |
| NaN canonicalization | on | yes | Q04 |
| fuel | on | yes | metering generation 0 |
| epoch interruption | off | yes | no wall-clock influence |
| features on | mutable globals, sign-ext, saturating float to int, multi-value, bulk memory, reference types (funcref only) | yes | Rust 1.92 defaults |
| features off | SIMD, relaxed SIMD, threads, memory64, multi-memory, tail calls, extended const, function references, GC, exceptions, custom page sizes, wide arithmetic, stack switching, component model | yes | Q04 and the DIP first feature set |
| max_wasm_stack | 4 MiB | no, but see native headroom | must exceed what the logical limit can reach |
| memory reservation / guard | 4 GiB / 32 MiB, `memory_may_move(false)`, guard before memory on | no | explicit so artifacts and trap behaviour do not depend on platform defaults |
| signals-based traps | on | no | trap classification identical either way |
| backtraces, unwind info, address map, debug info | off | no | smaller artifacts, no nondeterministic metadata |

A `LocalRuntimeConfig { cache_dir, in_memory_capacity_bytes }` is separate and documented as local policy that cannot change outcomes.

### 3.2 Protocol table (Part 1)

New module `packages/rs-platform-version/src/version/dashvm_versions/{mod.rs, v1.rs}`:

```rust
pub struct DashVmVersion {
    /// Selects dashvm::engine::profile::v{N}: Wasmtime release, Cranelift flags, feature set.
    pub engine_profile: FeatureVersion,
    /// Selects dashvm_validation admission + instrumentation generation v{N}.
    pub preparation: FeatureVersion,
    /// Selects the computation schedule: 0 = Wasmtime fuel, one unit per metered operator.
    pub metering: FeatureVersion,
    pub limits: DashVmLimits,
    pub weights: DashVmMeteringWeights,
}
```

`DashVmLimits` (all provisional, from the allocation register): canonical module bytes 16 MiB; modules per bundle 16; module name bytes 64; functions 50,000; types 10,000; params 128; locals 1,024; exports 1,024; decoded operators 2,000,000 total and 100,000 per function; basic blocks per function 4,096; nesting 512; instrumented bytes 64 MiB; initial memory pages 256 (16 MiB); memory pages per instance 2,048 (128 MiB); memory pages per invocation 4,096 (256 MiB); table elements 65,536; logical stack bytes 1 MiB; activation depth 512; host calls per invocation 10,000; argument bytes 256 KiB; return bytes 64 KiB; data segment bytes per module 16 MiB (bounded by module size).

`DashVmMeteringWeights` (provisional): host entry 100 units; copied byte 1; initialised byte 1; memory growth page 65,536; instance base 1,000.

`PlatformVersion.dashvm: Option<DashVmVersion>`; `None` in `v1.rs` to `v14.rs`, `v15.rs`, `v16.rs`, both mocks; `Some(DASHVM_VERSION_V1)` in `v17.rs`. If R06-01 has not merged when Part 1 is opened, Part 1 creates `v15.rs`/`v16.rs` placeholders and `v17.rs` in exactly R06-01's stated shape (`PlatformVersion { protocol_version: N, ..PLATFORM_V(N-1) }`, `LATEST_VERSION = 17`) and R06-01 rebases; if it has merged, Part 1 amends `v17.rs` and extends R06-01's "5.0 differs from its predecessor only in these tables" test to include `dashvm`. `ComputationUnits`: if R06-01's `system_limits::smart_contract::ComputationUnits` exists, `dashvm` re-exports it; otherwise `dashvm::metering` defines `pub type ComputationUnits = u64` and the second PR to land switches to the re-export (same type either way).

No `SystemLimits`, fee schedule, consensus error code, proto or SDK change in this task. No `feature_initial_protocol_versions` constant yet: nothing reads it until R08-11/R10-01 add transitions; that is where it goes.

### 3.3 Admission and preparation (dashvm-validation, Part 1)

`validate_and_prepare_bundle(inputs, bindings, entries, &PreparationProfile) -> Result<PreparedBundle, PreparationError>` with `PreparationProfile: From<&DashVmVersion>`.

Per module, in order and cheap checks first: byte bound; `wasmparser::Validator::new_with_features(admitted)` full validation; structural counting during validation (functions, types, params, locals, exports, imports, operators per function and total, nesting via `control_stack_height`, basic blocks by counting block-starting operators, max operand height via `operand_stack_height` after each operator); exactly one defined 32-bit memory with `min <= initial pages` and `max` either absent or `<= per-instance pages`, exported as `memory`; no memory or table imports; at most one funcref table, defined, `<= table elements`; no `start` section (provisional under A08: Rust guests do not emit one, and rejecting is the strict reading of "starts require explicit validation"); imports only from `dash_host` (host envelope, section 3.6), or `dash:<module-name>` for internal bindings; a submitted module importing `dash_vm.*` is rejected; required exports `dash_alloc` and at least one entry export; custom sections stripped so the prepared bytes are canonical.

Instrumentation (portable logical stack, prototype for FIX-05): inject imports `dash_vm.stack_bytes` (mutable i32), `dash_vm.stack_depth` (mutable i32), `dash_vm.trap(i32)`; per function compute `frame_bytes = 32 + 4 * (i32|f32 params, locals, max operand slots) + 8 * (i64|f64 ...)`; at every direct `call` site wrap the call with add/check/sub on both counters using the callee's frame cost; functions reachable through a table or exported get a thunk that performs the same accounting around an inner call (the wasm-instrument stack-limiter design, which keeps `return` inside bodies correct); on exhaustion call `dash_vm.trap(code)` so the host can distinguish stack exhaustion from a guest `unreachable`. Index shifting for the three new imports goes through the `Reencode` hooks. The transformed module is re-validated with the same feature set, re-measured, bounded by instrumented bytes, and hashed (`PreparedHash`). Canonical bytes are hashed before any transform (`CanonicalHash`, SHA-256, domain-separated).

Bundle checks: module names bounded, ASCII lower-case alnum plus underscore, unique, sorted; bindings resolve `dash:<target>`/`export` to an existing export of the exact signature; graph is a DAG (Kahn's algorithm, canonical-name order); entries name existing exports with the entry signature; a bundle digest (SHA-256 over the canonical encoding of names, hashes, bindings, entries) is produced for the artifact key.

Descriptor types (`bundle.rs`): `ModuleName`, `CanonicalHash`, `PreparedHash`, `BundleDigest`, `ModuleInterface`, `PreparedModule`, `BundleBinding`, `EntryRef`, `PreparedBundle`, `StructuralMeasurements`, `InitializationMeasurements`. These are the provisional home; R08-03/R08-04 move manifest-facing parts into `dashvm-abi`.

### 3.4 Compilation and the compiled cache (Part 2; the S08-02 specification)

Artifact key (`cache/key.rs`): SHA-256 over `b"dashvm-artifact-v1"` || prepared hash || canonical hash || preparation generation || metering generation || engine profile canonical string (includes `36.0.14`, target triple, every consensus-relevant setting) || the bytes of a SHA-256 `Hasher` fed with `Engine::precompile_compatibility_hash()` (covers Cranelift flags, ISA flags and tunables). Bundle digest is part of the *bundle* entry, not the per-module artifact, so unchanged modules are shared across versions and bundles.

Disk layout (`cache/disk.rs`): `<cache_dir>/<key[0..2]>/<key>.cwasm` written as temp file plus rename; a 96-byte header (magic `DVMA`, format 1, key, SHA-256 of the body, body length) precedes the `Engine::precompile_module` output. Load path: header parse, key equality, length, checksum, then the single `unsafe { Module::deserialize }` with a written safety argument (only bytes this process wrote from `precompile_module`, verified unchanged, under an engine whose compatibility hash is in the key). Any mismatch or IO error discards the entry and reports `ArtifactMissing`; the caller rebuilds from canonical code. Nothing supplied by peers is ever deserialised. Deserialisation is not on the invocation path: `Runtime::load` returns `None` when an artifact is missing and callers treat that as a node readiness condition, never a paid guest failure.

Retention (`cache/memory.rs`): an in-memory table `ArtifactKey -> Arc<CompiledModule>` plus `RetentionGroup { Runnable, Pending, Historical }` per bundle reference. `retain(bundle, group)` and `release(bundle)` are the only API; an artifact stays while any runnable or pending bundle references it; only `Historical` artifacts are subject to the local byte cap and are rebuilt on demand for replay. Eviction never touches canonical bytes (they are Drive state, not this crate's concern) and never changes any outcome or charge.

Historical replay: `engine/registry.rs` maps `engine_profile` version to a profile constructor. A replay of a block under an older protocol version builds that version's engine; its artifacts have a different key and coexist. Within one binary a single Wasmtime crate is linked, so "retain historical engine behaviour" means every profile version stays constructible from the pinned crate; an engine crate bump is a new profile version selected by a new protocol version, never an edit of `profile::v0`.

### 3.5 Linking, initialisation and shared resources (Part 3; allocation A08, provisional)

One `wasmtime::Store<InvocationState>` per outer invocation. The entry module's dependency closure is computed from the bindings (bundle-level DAG already validated), instantiated in topological order with canonical-name tie-break, one `Instance` per module, each with its own memory and table. Internal bindings are satisfied by importing the target instance's exported `Func` directly (typed wasm-to-wasm call, no host hop) for scalar signatures; byte payloads across memories go through the host copy primitive `copy_between_memories(src, ptr, len, dst, ptr)` metered per byte, which R08-04's typed internal-call envelope builds on. Raw pointers never mean anything outside their own instance; a test proves a pointer from module A dereferenced in module B reads B's memory, not A's.

Shared accounting: the two logical-stack globals and `dash_vm.trap` are host-created objects imported by every instance, so one counter covers all modules and recursion A -> B -> A exhausts it exactly like local recursion. Fuel is per store, so one computation budget covers all modules. The store's `ResourceLimiter` sees every memory in the store and enforces both the per-instance and the per-invocation page caps deterministically (`memory_growing` returns `false`, the guest observes `memory.grow == -1`). `memory_grow_failed` (host allocation failure below the logical cap) sets a node-fault flag and traps; the outcome classifier reports `NodeFault`, never a guest failure. Instance count per invocation is bounded by modules per bundle.

Initialisation cost is charged before instantiating each module: `instance base + initialised byte weight * (active data segment bytes + 8 * element count)` deducted from fuel; insufficient budget is `OutOfComputation` before any instance exists. No `start` functions exist (rejected at preparation), so initialisation is memory, table and global setup only. No instance state survives to the next outer invocation.

### 3.6 Host envelope and invocation (Part 2; names provisional under A07)

Imports in module `dash_host`: `host_call(op: i32, in_ptr: i32, in_len: i32) -> i64` (response handle or negative fault), `response_len(handle: i32) -> i32`, `response_read(handle: i32, out_ptr: i32, out_cap: i32) -> i32`, `response_release(handle: i32)`. Guest exports: `memory`, `dash_alloc(len: i32) -> i32`, and entry exports of signature `(args_ptr: i32, args_len: i32) -> i64` returning packed `(ptr << 32 | len)`. R08-04 renames and extends in one constants module (`dashvm_validation::abi_names`).

`HostCalls` trait (runtime-owned, implemented above the runtime): `fn dispatch(&mut self, op: HostOpId, input: &[u8], meter: &mut HostMeter) -> Result<Vec<u8>, HostCallError>`. Input is copied out of guest memory first (bounded by argument bytes and metered), the guest borrow ends before dispatch, output is copied back on `response_read`. `HostCallError::Fault` poisons the invocation whatever the guest does with the return; `HostCallError::NodeFault` becomes `DashVmError`. Nested contract calls are not the runtime's concern: a host implementation that needs one opens a fresh `Runtime::invoke` with the remaining budget (`meter.remaining()`, read from the store's fuel through `Caller::get_fuel`), and the returned consumption is deducted with `set_fuel`; the DIP's "one outer budget" holds without sharing stores.

Metering (`metering/`): `Budget` wraps store fuel; host entry, copies, growth and initialisation deduct through checked arithmetic; `HostMeter` counts host calls against the per-invocation cap. Schedule generation 0 is "one unit per Wasmtime-metered operator"; it is deterministic because fuel is charged at translation from the operator stream, independent of target and optimisation, and the trapped-case parity is asserted on both CI architectures. Weighted per-opcode schedules are R03-07's generation 1 (validation-time instrumentation), reachable through `metering` in the table without touching generation 0.

Native stack headroom (`limits/native_stack.rs`): invocation runs on a dedicated scoped thread with a 32 MiB stack (local policy, precedent `rs-sdk-ffi` `BigStackRuntime`), `max_wasm_stack` 4 MiB; a test drives recursion to the logical limit on both architectures and asserts the outcome is `LogicalStackExhausted`, never `Trap::StackOverflow`. If `StackOverflow` ever surfaces it is classified `NodeFault` (the limit was too loose for that target), logged, and by construction the corpus must show it cannot happen at the shipped limits.

Outcome (`outcome.rs`): `InvocationReport { outcome, computation_consumed: ComputationUnits, host_calls, peak_memory_pages, result: Option<Vec<u8>> }` with `Outcome::{Completed, GuestFault(GuestFaultKind), HostFault(HostFaultKind)}` and `Err(DashVmError)` for node faults. `GuestFaultKind` maps traps: `OutOfFuel -> OutOfComputation`; `dash_vm.trap(code) -> LogicalStackExhausted | ...`; `UnreachableCodeReached, IntegerOverflow, IntegerDivisionByZero, BadConversionToInteger, MemoryOutOfBounds, HeapMisaligned, TableOutOfBounds, IndirectCallToNull, BadSignature -> Trap(kind)`; `InvalidPointer`, `ArgumentTooLarge`, `ReturnTooLarge`, `HostCallLimit`, `MemoryLimit` from the envelope; `StackOverflow`, `Interrupt`, `AllocationTooLarge` and every GC or component variant -> `DashVmError::UnexpectedTrap` (node fault, must be unreachable under the profile). Guest faults are deterministic and paid; the settlement rules are R12-07's.

### 3.7 What stays byte-identical

Every existing `vN` implementation module; `PLATFORM_V1` to `PLATFORM_V14` except the added `dashvm: None` line; all `SYSTEM_LIMITS_V*`, `FEE_VERSION*`, drive, dpp, drive-abci, SDK and proto sources; the mocks except `dashvm: None`. No shipped behaviour changes because nothing outside the new crates reads the new table yet.

## 5. Provisional values and interpretations (go in every PR body)

1. Engine pin 36.0.14 (LTS) selected by toolchain compatibility and advisory state; upgrade to 48.x LTS as a new profile version once the toolchain is 1.95 or later (A04, owner R08-01).
2. Baseline ISA per architecture (explicit `target`, no host feature inference) as the CPU feature policy (A04).
3. Numeric limits and metering weights in `DASHVM_VERSION_V1` are the allocation register's starting values; measurement and revision belong to R03-04, FIX-05, R03-07, R12-04.
4. Metering generation 0 equals Wasmtime fuel (one unit per metered operator); weighted schedules are generation 1 under R03-07.
5. `start` sections rejected in preparation generation 0 (A08, strict reading of "bounded starts").
6. Internal bindings for scalar signatures are direct wasm-to-wasm calls; byte payloads cross memories only through the metered host copy primitive (A08; R08-04 builds the typed envelope on it).
7. Logical stack is two shared host globals (bytes and depth) with the frame formula in section 3.3; both limits provisional (A06/FIX-05).
8. Host envelope and guest export names (`dash_host.*`, `dash_alloc`, `memory`, entry signature) are placeholders until A07 (R08-04) allocates the final ABI; they are isolated in `abi_names.rs`.
9. `PlatformVersion.dashvm` is an `Option` sub-table, `Some` first on the 5.0 protocol version (17). The activation gate for state transitions is separate (R08-11).
10. Bundle descriptor types live in `dashvm-validation` until R08-03/R08-04 move them to `dashvm-abi`.
11. Dedicated 32 MiB invocation thread and 4 MiB `max_wasm_stack` are local resource policy; R11-06 may replace the thread-per-invocation with a pool.
12. Artifact header format and cache directory layout are local (not consensus) and may change without a protocol version.
