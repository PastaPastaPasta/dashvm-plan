# R13-03 plan: contract configuration mirrors across Rust, WASM/TypeScript, Swift and Kotlin

Working artifact. Never staged, never committed. Delete when the task ships.

Base: `v5.0-dev` at `5f1e0ccdce` (protocol version 14 latest). Branch `dashvm/r13-03`. One PR.

## 1. Acceptance, restated

The issue row (S13-04) and DVM-10 ("Rust SDK, Wasm SDK/JavaScript and Swift/Kotlin wrappers must
preserve optional version/receipt/policy fields and structured errors in persistent application
models"; "keep one canonical vector corpus for schemas ... values ... errors") reduce to four
obligations in this tree:

1. Every client mirror of `DataContractConfig` (TypeScript type in wasm-dpp2, Swift value type,
   Kotlin value type) has exactly the fields rs-dpp serialises, with the same wire keys, the same
   `$formatVersion` discriminator and the same defaults, for every shipped config generation
   (V0 and V1).
2. One canonical vector corpus, owned by rs-dpp, is consumed by conformance tests in all four
   languages, so that adding a config field (the future policy, executable-version and receipt
   fields) fails a test in every language until every mirror is updated. This is the
   "keep consistent" mechanism the title asks for; the fields themselves arrive with R08-03,
   R10-03, R11-14 and R07-02 and ride this path (R07-07 is the first dependent that extends it).
3. The mobile persistent models (SwiftData `PersistentDataContract`, Room `DataContractEntity`)
   preserve the whole config object, including fields their typed columns do not project, and the
   typed projection reads the config from where the FFI actually puts it. Today both platforms
   read the flags from the JSON root while the FFI nests them under `config`, so every fetched
   contract persists default flags. That is a real bug this task fixes.
4. The FFI producers of contract JSON that Swift and Kotlin consume agree on the protocol version
   they serialise at, so both mobile SDKs see the same shape.

Capability requirements: none listed on the task. "Schema" in the title is read as the document
schemas carried verbatim inside the contract envelope on every mirror (`documentSchemas`); the
corpus contract vectors round-trip them, no new schema mirror is built. Provisional readings are
listed in section 9.

## 3. Design decisions

D1. **Corpus is owned by rs-dpp and read by everyone.** Path:
`packages/rs-dpp/src/tests/payloads/data_contract_config/vectors.json`. Rust includes it with
`include_str!`; wasm-dpp2 imports it (`import corpus from '../../../rs-dpp/src/tests/payloads/data_contract_config/vectors.json' with { type: 'json' }`);
Swift locates the repo root from `#filePath` (precedent `SwiftTests/SwiftDashSDKIntegrationTests/Support/IntegrationTestEnv.swift`, honour `PLATFORM_REPO_ROOT`);
Kotlin walks up from `user.dir` (precedent `GateCoverageLintTest.findSdkMainSources`). The
cross-language golden precedent already in the tree is `rs-unified-sdk-jni/src/pubkey_rows.rs`
including `kotlin-sdk/sdk/src/test/resources/golden/registration_pubkeys_v1.bin`.

D2. **The Rust test proves the corpus, it does not generate it at test time.** For each config vector: typed
struct built from the vector fields, `serde_json::to_value` equals the vector JSON; `serde_json::from_value`
of the vector JSON equals the typed struct; bincode (`bincode::config::standard()`) encodes to the vector's
`bincodeHex` and decodes back. For each contract vector: `DataContract::from_json(json, true, PlatformVersion::latest())`
succeeds and `try_into_platform_versioned(latest)` re-serialises to the identical JSON value, and the embedded
config equals the named config vector. A new field on `DataContractConfigV1` therefore fails this test until the
corpus changes, and a corpus change fails the TS, Swift and Kotlin conformance tests until their mirrors change.
That chain is the deliverable.

D3. **Every mirror is the versioned union, like Rust.** TS: `DataContractConfigV0 | DataContractConfigV1`
discriminated on `$formatVersion`. Swift: `enum DataContractConfig { case v0(DataContractConfigV0), case v1(DataContractConfigV1) }`
with flat accessors. Kotlin: `sealed class DataContractConfig` with `V0`/`V1` data classes and the same
accessors. `sizedIntegerTypes` reads `false` on V0 exactly as `DataContractConfigGettersV1` does.
`StorageKeyRequirements` mirrors as an integer-backed enum (`unique = 0`, `multiple = 1`,
`multipleReferenceToLatest = 2`); unknown values fail decoding.

D4. **Wire faithfulness rules the mobile codecs.** Rust serialises `None` as `null` with the key present, so
Swift `encode(_:forKey:)` (not `encodeIfPresent`) and Kotlin `JsonNull` on encode; on decode accept both
`null` and missing (serde `default`). Missing boolean keys decode to the DPP defaults (`canBeDeleted` false,
`readonly` false, `keepsHistory` false, `documentsKeepHistoryContractDefault` false,
`documentsMutableContractDefault` true, `documentsCanBeDeletedContractDefault` true, `sizedIntegerTypes` true).
`$formatVersion` is the string `"0"`/`"1"` on the wire.

D5. **No store schema bump on either mobile platform.** The canonical form (the FFI JSON) is already persisted
verbatim in `serializedContract` on both, so every present and future config field is preserved without a
migration. The typed mirror is a computed accessor decoded from that blob (Swift precedent: `parsedContract`,
`schema`, `groups` computed properties on the same model). The six existing projection columns are kept and
corrected. Reasons: no query or predicate needs a new column; a SwiftData column means re-freezing the 24-model
component for schema V5; a Room column means version 12 plus a regenerated exported schema, and a Room migration
cannot be exercised by this lane (no JDK or Android SDK is readable by this user). A future task that needs a
queryable policy column adds it with the freeze pattern then.

D6. **FFI producers pin the SDK network version.** `fetch_json` and `fetch_many` switch to the same
`try_into_platform_versioned(wrapper.sdk.version())` path `fetch_with_serialization` already uses, through one
helper in `data_contract/util.rs`. No C signature changes, so Swift, JNI and Kotlin bindings are untouched.

D7. **Scope fence.** No new `vN` generation, no `SystemLimits`, fee, protocol-table, consensus-error, proto,
Drive or proof change. `packages/rs-dpp/src/data_contract/config/**` implementation stays byte-identical
(only a `#[cfg(test)] mod` line is added). No Swift document-type mirror work (`DPPDataContract.DocumentType`
drifts too, but the title covers configuration; noted for the PR body). No FFI history-shape change.

## 4. The corpus

`packages/rs-dpp/src/tests/payloads/data_contract_config/vectors.json`:

```json
{
  "description": "Canonical DataContractConfig vectors. Owned by rs-dpp (config/mirror_vectors.rs). Consumed by wasm-dpp2, swift-sdk and kotlin-sdk conformance tests. Add a vector when a config field or generation is added; every consumer test fails until its mirror matches.",
  "configs": [
    { "name": "v0-defaults", "json": { "$formatVersion": "0", "canBeDeleted": false, "readonly": false, "keepsHistory": false, "documentsKeepHistoryContractDefault": false, "documentsMutableContractDefault": true, "documentsCanBeDeletedContractDefault": true, "requiresIdentityEncryptionBoundedKey": null, "requiresIdentityDecryptionBoundedKey": null }, "bincodeHex": "<generated>" },
    { "name": "v0-all-set", "json": { "$formatVersion": "0", "canBeDeleted": true, "readonly": true, "keepsHistory": true, "documentsKeepHistoryContractDefault": true, "documentsMutableContractDefault": false, "documentsCanBeDeletedContractDefault": false, "requiresIdentityEncryptionBoundedKey": 0, "requiresIdentityDecryptionBoundedKey": 2 }, "bincodeHex": "<generated>" },
    { "name": "v1-defaults", "json": { "$formatVersion": "1", ...v0 defaults..., "sizedIntegerTypes": true }, "bincodeHex": "<generated>" },
    { "name": "v1-all-set", "json": { "$formatVersion": "1", ...flags flipped, "requiresIdentityEncryptionBoundedKey": 1, "requiresIdentityDecryptionBoundedKey": null, "sizedIntegerTypes": false }, "bincodeHex": "<generated>" }
  ],
  "contracts": [
    { "name": "contract-v1-config-v1", "protocolVersion": 14, "config": "v1-history-defaults", "json": { "$formatVersion": "1", "id": "...", "config": {...}, "version": 1, "ownerId": "11111111111111111111111111111111", "schemaDefs": null, "documentSchemas": { "note": { "type": "object", "properties": { "message": { "type": "string", "maxLength": 100, "position": 0 } }, "additionalProperties": false } }, "createdAt": null, "updatedAt": null, "createdAtBlockHeight": null, "updatedAtBlockHeight": null, "createdAtEpoch": null, "updatedAtEpoch": null, "groups": {}, "tokens": {}, "keywords": [], "description": null } },
    { "name": "contract-v1-config-v0", "protocolVersion": 14, "config": "v0-all-set", "json": { same envelope, config = v0-all-set } }
  ]
}
```

Rules for the file:
- The Rust test is the authority on byte content: the implementer first writes the test, runs it, pastes the
  generated `bincodeHex` and the exact `serde_json` output of the contract envelope (dpp's `serde_json` has
  `preserve_order`, so key order is struct order; `null` keys are present, `groups`/`tokens` are `{}`,
  `keywords` is `[]`).
- Contract-level vectors must pass `try_from_schema` v3 validation at PV14, including the keep-history versus
  deletable contradiction check from #4218. Use a config named `v1-history-defaults`
  (`documentsKeepHistoryContractDefault: true`, `documentsCanBeDeletedContractDefault: false`, others default)
  inside the contract vectors and keep `v1-all-set` for the struct-level round trip only. Add `v1-history-defaults`
  to `configs` too.
- `ownerId` all-ones base58, `id` a fixed base58 identifier; `from_json` does not re-derive ids.
- The V0-config contract vector models a contract registered before PV11 that is still readable from state.
