# R13-03 plan: contract configuration mirrors across Rust, WASM/TypeScript, Swift and Kotlin

Working artifact. Never staged, never committed. Delete when the task ships.

## 1. Acceptance, restated

The contract configuration (`DataContractConfig`, the `config` block of a
serialized data contract) has one canonical wire shape, defined by `rs-dpp`
serde. Every client mirror of that shape must agree with it, and the mobile
persistence layers must keep every field the wire carries, including the
format version tag, so that a field added to the Rust model (the DashVM
policy, executable-version and receipt fields that later 5.0 tasks add)
cannot silently go missing in a client.

Concretely, after this task:

1. One canonical vector corpus for contract configuration exists, generated
   from and verified by `rs-dpp`, and is replayed by the wasm-dpp2 tests, the
   `rs-sdk-ffi` tests, the Swift SDK tests and the Kotlin SDK tests. Every
   mirror decodes the same vectors to the same typed values and rejects or
   ignores the same things.
2. The wasm-dpp2 TypeScript type for the config matches the runtime shape
   (format tag, `sizedIntegerTypes`, nullable key requirements).
3. The FFI JSON emitters render the contract at the SDK's protocol version,
   the same way `fetch_with_serialization` already does, through one shared
   helper.
4. The Swift and Kotlin SDKs each carry a typed configuration mirror that is
   decoded from the persisted canonical contract JSON, and the two example
   apps project the nested `config` block into the typed row columns they
   already have. Today both apps read the flags at the wrong JSON level and
   persist defaults for every downloaded contract.
5. A field-set guard in `rs-dpp` fails the moment a config field is added or
   renamed without the vectors being regenerated; its failure message lists
   every mirror surface that has to move with it. The SDK parity manifest
   records the mirror capability and its tests on both mobile hosts.

Native capability requirements: none are listed on this task.

### 1.1 Interpretation of "new policy, version and receipt fields" (provisional)

No DashVM configuration field exists in `rs-dpp` on `v4.2-dev`, `v4.3-dev`
or `v5.0-dev`, and none of the open DashVM PRs adds one (`#4717` adds
envelope kinds and size limits; `#4712` adds the DashVM protocol table;
`#4705` computation limits; `#4716`, `#4784`, `#4789`, `#4790` are Drive or
fee work). The fields are allocated to other tasks: contract kind, module
references and executable version to R08-03 (allocation A02/A07), receipt
policy and retention to R10-03 (A18), freeze policy to the governance tasks.
Inventing a `DataContractConfigV2` here would preempt those allocations.

This task therefore delivers the mirror discipline and its enforcement for
every field that exists, plus a forward-compatibility proof: a vector whose
config carries an unknown extra key must still decode in every mirror, must
be dropped identically by the Rust re-serialization, and must survive in the
persisted canonical JSON on both mobile hosts. When R08-03 and R10-03 add
their fields, the guard test tells them which surfaces to extend, and the
vector corpus is where their round-trip evidence goes. This reading is
recorded as provisional in the PR body and points at the register.

## 3. Base branch: `v4.2-dev` for both parts

The task is allocated to 5.0-dev and nothing in this plan depends on 5.0
work. Two facts make `v4.2-dev` the right target:

- The release allocation's carry-forward rule says fixes go to the earliest
  applicable development branch and are carried forward, never implemented
  as independent copies. Items 2, 3 and 4 above are defects in shipped
  client code on the current release line (mobile rows never carry the
  contract's real configuration).
- `v5.0-dev` is a stale cut, 115 commits behind `v4.2-dev`, and lacks the
  Swift schema generator that any later persistence change will need. The
  machinery lands once on `v4.2-dev` and reaches `v4.3-dev`, `v4.4-dev` and
  `v5.0-dev` through the maintainers' forward merges.

The DashVM tasks that add configuration fields run on `v5.0-dev` and will
find the vectors, the guard and the mirrors there after the forward merge.
R07-07 (guard schema and configuration mirrors) reuses the same pattern.

  ```json
  {
    "description": "Canonical contract configuration vectors. Regenerate with DASH_WRITE_CONTRACT_CONFIG_VECTORS=1 cargo test -p dpp data_contract::config::vectors",
    "cases": [
      {
        "name": "v1_defaults",

          "sizedIntegerTypes": true
        }
      }
    ]
  }
  ```

  Cases, all valid contracts with one minimal document type (`note` with one
  string property at position 0), fixed identifiers (`id` from 0x11 bytes,
  `ownerId` from 0x22 bytes), `version` 1:

  | name | contract format | config | notes |
  | --- | --- | --- | --- |
  | `v1_defaults` | 1 | V1 default | the shape every new contract has |
  | `v1_all_set` | 1 | V1, every flag inverted, encryption `Unique` (0), decryption `MultipleReferenceToLatest` (2), `sizedIntegerTypes` false | proves nothing is read from a default |
  | `v0_defaults_in_v1_envelope` | 1 | V0 default | a pre-v11 contract loaded from state |
  | `v0_key_requirements` | 1 | V0, encryption `Multiple` (1), decryption `Unique` (0) | V0 has no `sizedIntegerTypes`; `expect.sizedIntegerTypes` is null |
  | `v0_envelope` | 0 | V0 default | the historic envelope |
  | `v1_unknown_field_is_ignored` | 1 | V1 all set plus `"futurePolicy": {"kind": 1}` | `contract` keeps the key, `canonical` does not; every mirror ignores it, persistence keeps it |

  `canonical` equals `contract` for every case except the last. The
  `platformVersion` is the version the case was generated at; consumers
  decode at that version. `expect` values are explicit, so a mirror that
  merely echoes its input cannot pass.

- `mod.rs` (compiled only under `#[cfg(test)]`, declared as
  `#[cfg(test)] mod vectors;` in `config/mod.rs`): loads the file with
  `include_str!`, and holds:
  - `vectors_round_trip_through_rs_dpp`: for each case, `DataContract::from_json(contract, true, PlatformVersion::get(pv))`
    succeeds; `to_value(pv)` re-serialized to `serde_json::Value` equals
    `canonical`; the decoded `config()` matches `expect` field by field
    through the enum getters (`sized_integer_types()` returns `false` for
    V0, so the test compares against `expect.sizedIntegerTypes.unwrap_or(false)`
    and separately asserts `config.version()` equals the tag).
  - `vectors_are_the_generators_output`: rebuilds every case
    programmatically (`DataContractInSerializationFormatV1 { ... }` and the
    V0 envelope for `v0_envelope`), serializes with `serde_json::to_value`,
    and asserts structural equality with the file's `canonical`. With
    `DASH_WRITE_CONTRACT_CONFIG_VECTORS=1` it rewrites the file with
    `to_string_pretty` instead of asserting, the same shape as the Swift
    fixture-store writer. The `contract` field of the unknown-key case is
    written as `canonical` plus the extra key.
  - `config_field_sets_are_mirrored`: collects the keys of
    `serde_json::to_value(DataContractConfigV0::default())` and of the V1
    default (tag included) and asserts the exact lists. The failure message
    names the mirror surfaces: this vector file; the TS interface in
    `packages/wasm-dpp2/src/data_contract/model.rs`; `DataContractConfig` in
    `packages/swift-sdk/Sources/SwiftDashSDK/DPP/DPPDataContract.swift` and
    the parser projection in `DataContractParser.swift`;
    `packages/kotlin-sdk/sdk/src/main/kotlin/org/dashfoundation/dashsdk/contracts/DataContractConfig.kt`
    and the entity projection in the example app's `ContractDownloader.kt`;
    `docs/sdk/sdk-parity-manifest.json`. This is a mirror-contract pin,
    same kind as the envelope-key pin that already exists, not a
    version-table restatement.

  Tests follow the `should`-free naming already used in that module's test

1. The DashVM policy, version and receipt configuration fields are added by
   the tasks that own their allocations (R08-03, R10-03, governance tasks);
   this task delivers the mirror discipline, the vectors and the guard they
   must extend. Points at the allocation register entries A02, A07 and A18.

   binds them; every field, including future ones, is carried by the

   schema version is spent on a display-only column.

   generator test re-encodes `v1_all_set` at `PlatformVersion::latest()` as
