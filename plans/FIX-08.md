## 1. Acceptance, restated

Confirmed policy (section 8 of the Fable resolutions; DVM-07 "Typed refund ownership and conservation"; Q26):

1. A versioned `RefundOwner` with explicit `Identity(id)` and `ContractBucket(contract_id, bucket)` cases is what storage records as the refund owner of stored bytes. The host records it when bytes are stored. The kind is never inferred from a 32-byte identifier.
2. Old untagged records keep their historical identity interpretation and their fee epoch: every byte already on chain decodes exactly as before, and its refund is priced with the fee history at its storage epoch (R12-01 and R12-02 machinery).
3. Refunds go to the recorded owner. An identity owner is credited whether or not it may spend (a frozen owner receives bookkeeping credits, no key or permission is consulted). A contract-bucket owner is credited on the dedicated contract credit path (R04-01's bucket sum tree) without running guest code or checking bucket spending rules.
4. A wiped owner's later refunds go to the current epoch's processing pool (Q26). A missing destination is an invariant failure (an error that halts), never a silent burn or mint.
5. Contract balances and refund routing appear exactly once in the versioned credit conservation formula, and conservation holds on every path that frees storage: state transitions, block lifecycle cleanup (vote poll settlement), and the storage layer's own delete and shrink paths, including historical epochs and deletion after the owner changed status.

Not in scope, with the owning task: the writers that store contract-bucket-owned bytes (contract calls, receipts, jobs, canonical code: CAP-08, R10-02, R10-03, R12-09) and their cost estimation; the wipe that flips a live credit tree to the wiped wrapper and moves its live credits to the pool (R11-15, FIX-07); scheduled-job prefund refunds (R12-10, they use the prefunded ledger, not storage flags); the network freeze of a contract (R11-10, no native marker exists yet; "frozen" for this task means a live owner whose spending is restricted, which the refund path never consults anyway); capability matrices (CAP-11, CAP-16).

## 4. Design decisions

D1. **The typed owner is encoded in the element flags by a new type byte, in a Drive-owned codec; no grovedb change.** GroveDB never parses flags (section 3.1): only Drive's batch-apply closures do. So `packages/rs-drive/src/util/storage_flags/` stops re-exporting the crate type and defines Drive's own `StorageFlags` with the crate's four variants kept name- and shape-identical (`SingleEpoch`, `MultiEpoch`, `SingleEpochOwned`, `MultiEpochOwned`, so the 379 call sites and every test literal compile unchanged) plus two new ones: `SingleEpochContractBucket(BaseEpoch, ContractId, ContractCreditBucketPosition)` (type byte 4, layout `[4][contract_id 32][position u16 BE][base_epoch u16 BE]`, 37 bytes) and `MultiEpochContractBucket(BaseEpoch, BTreeMap<EpochIndex, BytesAddedInEpoch>, ContractId, ContractCreditBucketPosition)` (type byte 5, the same header followed by the crate's epoch-map encoding). Type bytes 0 to 3 serialize and deserialize through the crate (`grovedb_epoch_based_storage_flags`), so their bytes cannot drift; a first byte above 5 is `DeserializeUnknownStorageFlagsType`. The Drive type exposes the crate's whole API under the same names (`new_single_epoch`, `map_*_element_flags_*`, `to_element_flags`, `from_element_flags_ref`, `approximate_size`, `serialized_size`, `owner_id` (identity only), `base_epoch`, `epoch_index_map`, `combine_*`, `split_storage_removed_bytes`, `update_element_flags`, `split_removal_bytes`, `into_optional_cow`, `Display`) so the shipped v0 closures and every reader keep their text. Two groups differ in what they accept: the parse helpers (`from_element_flags_ref`, `map_*_element_flags_*`, `deserialize`) decode all six types, so the shipped readers (`fetch_contract`, `delete_document_for_contract_operations`, the update walkers, `query_documents_with_flags`) carry bucket flags through at 5.0 without a new generation; the two batch-closure entry points with shipped names (`update_element_flags`, `split_removal_bytes`) hand the raw bytes to the crate, so they reject type bytes 4 and 5 with the crate's unknown-type error and the shipped v0 closures fail closed by construction. The typed closure entry points are `update_element_flags_typed` and `split_removal_bytes_typed` (D5); the eight files importing `grovedb_epoch_based_storage_flags::StorageFlags` directly switch to `crate::util::storage_flags::StorageFlags`. New constructors: `new_single_epoch_for_owner(epoch, Option<RefundOwner>)`, `refund_owner() -> Option<RefundOwner>`. Errors reuse the crate's `StorageFlagsError` (already wrapped by `drive::error::Error`). Rationale: the owner is bound to the bytes it pays for where the epoch already is, GroveDB carries it through replace, shrink and delete unchanged, and the type byte is the declared kind the policy asks for. Rejected: a Drive-side owner registry (a second write per store and a read per removal); widening the 32-byte owner id (type 2 is 35 bytes on chain); a new type byte for identity owners (types 2 and 3 already mean identity by history and by the confirmed policy, so new identity-owned writes keep them and nothing on chain moves).

D2. **The in-memory removal carrier stays grovedb's 32-byte-keyed map; the typed owner rides alongside it in a recorded map, never inferred.** `grovedb_costs::storage_cost::removal::StorageRemovalPerEpochByIdentifier` is matched in about ten non-test sites of merk and grovedb and pinned by four release branches, so changing its key is a cross-repo re-pin for every branch. Instead `RefundOwner::removal_key(&self) -> [u8; 32]` (DPP, D3) gives each owner one carrier key: an identity's key is its id (so untagged historical records, new identity records and the payer lookup `calculate_refunds_amount_for_identity` all keep working unchanged); a contract bucket's key is `hash_double(REFUND_OWNER_CONTRACT_BUCKET_DOMAIN ‖ contract_id ‖ position_be)` with a fixed domain string. Drive's v1 split closure (D5) computes the sectioned removal under that key through the crate's own split logic and records `(key, RefundOwner)` for every owned removal, identities included, in a map captured by the closure. The map travels with the cost: new `LowLevelDriveOperation::CalculatedCostOperationWithRefundOwners { cost: OperationCost, refund_owners: BTreeMap<[u8; 32], RefundOwner> }`, pushed by `push_drive_operation_result_with_refund_owners`. `operation_cost()` returns `CorruptedCodeExecution` for it so the v0 and v1 decoders (which reach it through their `_ =>` arm) fail closed; `combine_cost_operations` sums its cost. The kind is therefore always read from the map that the type byte produced; a typed cost whose sectioned key has no map entry is an invariant failure. A collision between a bucket key and a real identity id inside one batch would merge two owners' bytes; both are outputs of SHA-256 over domain-separated preimages, so this is recorded as negligible in the PR body, not defended. Combine logic (`combine_added_bytes`, `combine_removed_bytes`) for the new variants maps each side to the crate's owned variant with its removal key, runs the crate combine, and maps the resulting owner id back through the two inputs; the crate compares owner ids for equality only, so typed owners of different kinds never merge silently and `UseTheirs` transfers ownership across kinds (D10).

D3. **DPP owns `RefundOwner` and `FeeRefunds` carries recorded owners.** `packages/rs-dpp/src/fee/refund_owner/mod.rs` (new, unconditional): `RefundOwner { Identity(Identifier), ContractBucket { contract_id: Identifier, position: ContractCreditBucketPosition } }` with `Encode, Decode, Serialize, Deserialize, Clone, Copy, Debug, Eq, Ord, Hash`, `removal_key()`, `as_identity()`, and the domain constant. Not wrapped in a `$formatVersion` enum: it is never persisted by DPP (storage persists it through the flag type byte, which is its version) and its wire use is inside consensus-internal fee results; recorded as provisional. `FeeRefunds` becomes `FeeRefunds(pub CreditsPerEpochByIdentifier, pub RefundOwnersByIdentifier)` with `RefundOwnersByIdentifier = BTreeMap<[u8; 32], RefundOwner>`: field 0 is the unchanged carrier so the shipped `execute_event/v0` (`fee_refunds.0.is_empty()`) and R12-02's v0 primitive (`iter()`) keep their text; the eight tuple constructors are tests. `from_storage_removal` (untyped keys, the shipped identity-flag path used by `consume_to_fees_v0` and `v1`) keeps its name and signature and records `Identity(key)` for every key explicitly; `from_typed_storage_removal(removal, owners, ..)` (v2) records from the map and returns `ProtocolError::CorruptedCodeExecution` on an unmapped key. `checked_add_assign` merges owners and errors when one key carries two different owners. New accessors `owner_of(&key)`, `iter_typed()` (yields `(RefundOwner, &[u8; 32], &CreditsPerEpoch)`), `calculate_all_refunds_except_owner(&RefundOwner) -> BTreeMap<RefundOwner, Credits>`. `calculate_all_refunds_except_identity` and `other_refunds()` keep returning `BTreeMap<Identifier, Credits>` for the shipped `apply_balance_change_from_fee_to_identity_v0`; under that shipped generation a bucket key would reach `add_to_identity_balance_operations` and halt with `CorruptedCodeExecution("there should always be a balance")`, which is the fail-closed outcome for a generation that predates typed owners and is unreachable because bucket-owned bytes exist only from the 5.0 version, where R12-02 part 3's v1 is selected (section 2).

D4. **Decode generation: `consume_to_fees_v2` and `calculate_fee` v2, selected only by the 5.0 drive table.** v2 copies R12-02's v1 and adds the arm for `CalculatedCostOperationWithRefundOwners`: `[0; 32]` bytes go to `removed_bytes_from_system`, every other key resolves through the map (D3) and is priced by `from_typed_storage_removal` with the required fee history. A plain `CalculatedCostOperation` carrying a `SectionedStorageRemoval` is `CorruptedCodeExecution` in v2 ("an owner-attributed removal reached the fee decoder without its recorded owners"): at 5.0 every sectioned removal comes out of the v1 closures, and non-batch deletes only ever report `BasicStorageRemoval` (section 3.1), so nothing legitimate hits that arm. v0 and v1 are byte-identical. `drive.methods.fees.calculate_fee: 2` in the 5.0 drive table only. Historical decoding: typed and untyped removals price each storage epoch through the same `previous_fee_versions` lookup, so old records refund at their storage epoch's schedule and a bucket-owned record refunds at the schedule of the epoch it was stored in.

D5. **The batch-apply closures are versioned so typed splitting activates only at 5.0.** `grove_apply_batch_with_add_costs` v1 and `grove_apply_partial_batch_with_add_costs` v1 (`grove_methods.apply.grove_apply_batch: 1`, `grove_apply_partial_batch: 1` in a new `DRIVE_GROVE_METHOD_VERSIONS_V2`, a copy of V1 referenced only by the 5.0 drive table) use `StorageFlags::update_element_flags_typed` (the crate's logic re-expressed over the Drive type, same `UseTheirs` strategy on replace) and `StorageFlags::split_removal_bytes_typed(flags, key_bytes, value_bytes, &mut refund_owners)`, then push the typed cost operation. v0 keeps calling the delegating `update_element_flags` and `split_removal_bytes`, which route through the crate and therefore reject type bytes 4 and 5, which no block below the 5.0 version can contain (their only writers gate on 5.0 tables). Replay safety is structural. The partial-batch v0 inline closures are copied into v1 and switched; the duplication is the accepted cost.

D6. **Routing lives in `credit_storage_refunds_to_owners_operations` v1.** Copy R12-02's v0 and iterate `iter_typed()`. `Identity(id)`: unchanged (balance element present: `add_to_previous_balance`, no key or permission consulted; absent: `routed_to_processing_pool`). `ContractBucket { contract_id, position }`: `fetch_contract_credit_tree_state_operations(contract_id)`; `None` or `Some(Live)`: `add_to_contract_credit_bucket_operations(contract_id, position, credits, previous_batch_operations = Some(&mut drive_operations), ..)` and record under the typed key in `credited`; `Some(Wiped)`: add to `routed_to_processing_pool` (Q26). Every sum is checked; any error other than the wiped refusal propagates as the invariant failure it is (never a burn, never a mint). `StorageRefundCreditOutcome.credited` becomes `BTreeMap<RefundOwner, Credits>`; the outcome type is a plain struct in `structs/`, not a generation, but the key change forces one mechanical edit inside R12-02's shipped v0 (`Identifier::from(*owner_id)` becomes `RefundOwner::Identity(Identifier::from(*owner_id))` at the single insert) and in its test literals; behaviour is identical and the edit is called out in the PR body as the exception a type change forces. Rejected: a second `credited_buckets` field, which forces the same one-line edit (the v0 literal must name the field) while leaving two maps for one concept. `skip_owner: Option<[u8; 32]>` keeps its type: it is compared against the carrier key, which is the id for an identity payer and `removal_key()` for a future bucket payer. Slot `credit_storage_refunds_to_owners: Some(1)` in the 5.0 identity table (R12-02 part 3's `DRIVE_IDENTITY_METHOD_VERSIONS_V4`, amended in place). Both consumers (state transitions through R12-02 part 3's `apply_balance_change_from_fee_to_identity` v1; vote poll settlement through R12-02 part 2's method) already call the dispatcher, so neither changes.

D7. **Frozen owners.** No native "frozen contract" marker exists on `v5.0-dev`; R11-10 owns the network freeze. The refund path consults only the credit tree lifecycle (Live or Wiped) and the presence of an identity balance element, never spending or deposit rules, keys or any freeze marker, so a frozen-but-existing owner is credited by construction. Tests pin it with an identity whose keys are all disabled (R12-02 has one) and with a bucket whose rules are `CreditBucketDepositPolicy::NoOne` (the refund path does not evaluate deposit rules). When R11-10 lands a freeze marker it must not touch this path; recorded in the PR body.

D8. **Conservation gains no new term.** A bucket refund raises `total_in_contract_credits` (R04-01's sixth term) while the pending refund entry lowers `total_in_pools`; a pool route is a move inside the pools tree; a wiped tree's retained buckets are excluded by the `NotSummed` wrapper, so a pool-routed refund for a wiped owner cannot double-count. The task adds the `refund_conservation` vectors (section 6): every route in one block, and one block mixing an identity refund, a live-bucket refund, a wiped-bucket refund, a state transition refund and an epoch change, each checked with `calculate_total_credits_balance().ok()`.

D9. **Estimation.** `StorageFlags::approximate_size(has_owner_id, ..)` is unchanged; `approximate_size_for_owner(Option<&RefundOwner>, ..)` returns the 37-byte header for a bucket owner. No existing estimation site changes (they size identity-owned documents); the bucket-owned writers (CAP-08, R10-03, R12-09) use the new helper. Stateless batches never emit sectioned removals (`grovedb/src/batch/estimated_costs/*` report `NoStorageRemoval`), so the typed path never runs in estimation.

D10. **Ownership transfer across kinds is allowed by the replace rule.** The batch `update_element_flags` merges with `UseTheirs`, so a replace whose new flags name a different owner transfers the bytes; with typed owners that covers identity to bucket and back. CAP-08's transfer paths get it for free; recorded.

D11. **Rejected: changing grovedb's removal carrier or the flags crate.** It would give a typed key without the recorded map, but it means a grovedb PR, a re-pin on four release branches (each pinned to a different rev today) and touching about ten merk and grovedb match sites for a type GroveDB never interprets. Recorded as the alternative in the PR body; the recorded map (D2) is the provisional design and A16 stays open until the owner reviews the encoding.

D12. **Later refunds of a wiped contract are FIX-08's; the wipe itself is R11-15's.** R11-15 flips the credit tree to the wiped wrapper and moves its live total to the pool once; it must not route storage refunds itself. Any cleanup path that frees a wiped owner's bytes (R11-15's bounded physical cleanup, FIX-07's token cleanup) prices the removal through `calculate_fee` and settles through the primitive, which is how "credits money a second time" is ruled out: the pool write is one operation per settlement and the pending refund entry is recorded once.
