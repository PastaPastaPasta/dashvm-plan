# R06-01 plan: protocol-versioned smart-contract computation limits and their gas representation

Working artifact. Never staged, never committed. Delete when the task ships.

Base branch `v5.0-dev` (tip `5f1e0ccdce`, identical protocol tables to `v4.2-dev` and `v4.3-dev`: `LATEST_VERSION = 14` on all three). Single part, single PR. Tier stays `xhigh`: the change adds fields to the consensus limit table and the fee schedule and introduces the 5.0 protocol version scaffold.

## 1. Acceptance, restated

Q40 delegates: keep one protocol-versioned allocation register, supply provisional numeric limits and prices now, measure before activation, allocate identifiers from the real registries, and leave the engine/profile pin and unmeasured native costs explicitly open.

For this task that means, concretely:

1. **Per-call limit.** A protocol-versioned number: the computation units one outer contract invocation may consume, covering every nested call, predicate, module initialisation and host entry it causes (one counter, DVM-07 "one contract-only computation counter").
2. **Per-block limit.** A protocol-versioned number: the computation units all contract invocations in one block may consume together, ordinary and scheduled. Separate from every existing native budget (the proposer wall-clock timer, `withdrawal_transactions_per_block_limit`, `max_shielded_transition_actions`, Tenderdash `max_gas`); none of those change.
3. **Gas representation.** What a computation unit is (a deterministic count, never wall-clock), how it becomes credits (a protocol-versioned price in the fee schedule, checked arithmetic), and how it reaches the Tenderdash-facing gas fields (through `FeeResult.processing_fee`, so `gas_used` and `gas_wanted` stay credits and no unit equivalence with Tenderdash gas is introduced). R04-08 verifies the compatibility later; this task defines the mapping.
4. **Protocol versioning.** `None` on every shipped protocol version (1 to 14) and on the 4.3/4.4 placeholders; `Some(provisional)` only on the 5.0 protocol version. Nothing reads the values on a shipped version, and no shipped table changes behaviour.
5. **Per-block ledger.** The deterministic accounting type both proposal creation and proposal validation will share (R06-02 wires it in): reserve an invocation's admitted bound against the block, settle the actual consumption, release the unused part, never overflow, never spend a reservation twice.
6. **Explicitly not here.** Opcode weights and the metering generation (R03-07, R08-01's `DashVmVersions`), the remaining price rows of the register (deployment validation, readiness verification, host entry, per-byte copy: R12-03 amends the fee group), enforcement in the block loop and CheckTx (R06-02, R08-05, R11-04), scheduled-work admission (R06-09), consensus error codes for exhaustion (R12-07), and any native-event budget change (rejected by policy).

## 3. Decisions

- **D1. Limits live in `SystemLimits`, as one nested optional group.** `SystemLimits.smart_contract_computation: Option<SmartContractComputationLimits>` with two fields, `max_computation_units_per_invocation` and `max_computation_units_per_block`. Conventions: numbers go in `SystemLimits`, `None` for versions that predate the rule. One nested group (the catalog's `system_limits/smart_contract.rs`) instead of two flat `Option<u64>` fields so consumers pass one value and later limits from the register (host calls per invocation, returned read bytes, and so on, owned by other tasks) extend the group rather than the flat table. Not R08-01's `DashVmVersions`: that table carries generations and runtime-enforced shape limits; the computation budget is an input to the runtime, not a property of the engine profile.
- **D2. Units are a type alias in platform-version.** `pub type ComputationUnits = u64;` next to the limits struct, in the same style as `ProtocolVersion` and `FeeVersionNumber`. It sits in the lowest crate so the future `rs-dashvm` (which must not depend on `dpp`) can take the budget in `invoke()` and report consumption in the same unit. `mod system_limits` becomes `pub mod system_limits` so the alias and the struct are nameable from `dpp`, `drive-abci` and the engine crates (today nothing outside the crate names any `system_limits` path, verified by grep).
- **D3. Price lives in the fee schedule as a new optional group.** `FeeVersion.dashvm: Option<FeeDashVmVersion>` (catalog: `fee/dashvm/mod.rs`) with one field now, `credits_per_computation_unit: u64`. `FEE_VERSION1` and `FEE_VERSION2` carry `None`; the new `FEE_VERSION3` (`fee/v3.rs`) carries `Some(FEE_DASHVM_VERSION1)`. `Option`, not zeros, so a version without contract pricing cannot price computation at zero by accident (the zero-fee precedent in `FEE_DATA_CONTRACT_REGISTRATION_VERSION1` is for fees that were genuinely free; free computation is never intended). R12-03 amends `FeeDashVmVersion` and `FEE_DASHVM_VERSION1` in place with the remaining register rows.
- **D4. `fee_version_number` stays 1 and `FEE_VERSION3` is not registered in `FEE_VERSIONS`.** Storage, processing, hashing and signature rates are unchanged, so the persisted fee history keys nothing new. This is exactly the rule PR #4703 documents ("a schedule that only changes a group the history never serves keeps the number of the generation it agrees with"); after that PR merges forward, its registry tests pass unchanged for `FEE_VERSION3`.
- **D5. Provisional numbers, from the register.** Per invocation 25,000,000 units; per block 250,000,000 units; 1 credit per unit. Each carries a `// provisional` comment pointing at the shared allocation register (rows A06/A15 and the "Compute" and "Provisional price" entries) and the PR body names them provisional. A compile-time assertion on the 5.0 table pins the only invariant that must hold whatever the final numbers are: both limits are non-zero and the per-block limit is at least the per-invocation limit.
- **D6. Protocol versions 15, 16 and 17 are introduced; 17 is the 5.0 version.** Register (issue summary): PV15 = 4.3, PV16 = 4.4, PV17 = 5.0. `PLATFORM_VERSIONS` is indexed by number, so 17 needs 15 and 16 to exist. `v15.rs` and `v16.rs` are placeholders written with const struct update (`PlatformVersion { protocol_version: PROTOCOL_VERSION_15, ..PLATFORM_V14 }`, verified to compile on this tree) rather than file copies: when 4.3 and 4.4 forward-merge their real `v15.rs`/`v16.rs`, the add/add conflict is resolved by taking the incoming file, and `v16`/`v17` inherit every inherited table change without a second edit. `v17.rs` is also struct update over `PLATFORM_V16`, overriding only `system_limits` and `fee_version`, with a doc comment listing the two changes. `LATEST_VERSION = PROTOCOL_VERSION_17`, `LATEST_PLATFORM_VERSION = &PLATFORM_V17`, and all three appended to `PLATFORM_VERSIONS`. Provisional: if the register renumbers, the rename is mechanical. Nothing else in the tree hard-codes 14 as latest (tests pin `PlatformVersion::get(14)` explicitly, which stays valid; `wasm-sdk`, `wasm-dpp2` and `rs-sdk` derive the number from `latest()`).
- **D7. Not `!`.** Introducing the versions and the fields forks nothing: every shipped table gains only `None`, no method version changes, and no code path reads the new values yet. PV14's own introduction (`2d324d80f1`) shipped as `feat(platform)` without `!`. Title: `feat(platform): define protocol-versioned smart-contract computation limits and their gas representation`.
- **D8. Units to credits is a pure `dpp` function over the fee table, not a versioned method.** `dpp::fee::smart_contract_computation::computation_units_to_credits(units, &FeeVersion) -> Result<Credits, ProtocolError>`: `checked_mul` by the schedule price, `ProtocolError::Overflow` on overflow, `ProtocolError::CorruptedCodeExecution` when the schedule has no `dashvm` group (same shape as `daily_withdrawal_limit_v2` reading a missing `Option`). The table is the versioned part; a formula change later earns a `DPPMethodVersions` slot then, not now.
- **D9. Tenderdash gas stays credits.** The contract computation charge enters `FeeResult.processing_fee` (settlement is R12-05/R11-04) and therefore `gas_used` through `total_base_fee()`. No new gas unit, no conversion of computation units into Tenderdash gas, no change to `max_gas`. Documented in the type docs, the book and the PR body; no code beyond D8.
- **D10. The per-block ledger is a plain `drive-abci` type with move-only reservations.** `execution/types/block_computation_budget.rs`: `BlockComputationBudget::for_platform_version(&PlatformVersion) -> Option<Self>` (`None` before activation so callers skip the whole path), `reserve(bound) -> Result<ComputationReservation, BlockComputationBudgetExceeded>` (admission outcome, not an error: the proposer delays the transition, the validator rejects the block; wired by R06-02), `settle(reservation, actual) -> Result<ComputationUnits, Error>` (returns the released remainder; `actual > bound` is `ExecutionError::CorruptedCodeExecution`, because the runtime cannot legally exceed the budget it was given), `remaining()`, `consumed()`. `ComputationReservation` is `#[must_use]`, not `Clone`, consumed by `settle`, so a reservation cannot be spent twice. Reserving the full admitted bound (not the actual) means per-block exhaustion is never a mid-execution paid failure and an invocation's outcome does not depend on its position in the block. Every operation uses checked arithmetic. No `vN` enum wrapper: the ledger is per-block in-memory state, never serialised.
- **D11. Per-invocation counting is the runtime's.** The engine (R08-01, `rs-dashvm`) takes `max_computation_units_per_invocation` (or a smaller declared bound) as the budget in `invoke()`, meters guest and host work against that one counter, and reports consumption as `ComputationUnits`. This task does not add a second counter in `dpp` or `drive-abci`; the interface contract is stated in the limits struct docs.
- **D12. Nothing enforces yet.** No `NotExecutedReason` variant, no `BlockExecutionContextV0` field, no CheckTx change, no consensus error, no `feature_initial_protocol_versions` constant. R06-02 adds `NotExecutedReason::BlockSmartContractComputationExhausted` (maps to `TxAction::Delayed` like the timer) and places the ledger on the block execution context so scheduled phases share it; R12-07 allocates the exhaustion consensus error against the real code registry.

## 5. Versioning consequences

- New protocol versions 15 (placeholder), 16 (placeholder) and 17 (5.0, provisional number from the register). `LATEST_VERSION` 14 to 17. `DESIRED_PLATFORM_VERSION` follows. No `transition_to_version_*` hook is needed for any of them (no state migration). `consensus_params_update` sees the same `tenderdash_consensus_version` and emits nothing.
- `SystemLimits` gains one optional field; `SYSTEM_LIMITS_V1` to `V4` and the `v2_test` mock carry `None`; `SYSTEM_LIMITS_V5` is new and referenced only by `PLATFORM_V17`.
- `FeeVersion` gains one optional group; `FEE_VERSION1`, `FEE_VERSION2` and the pre-1.4 conversion carry `None`; `FEE_VERSION3` is new, `fee_version_number: 1`, unregistered (D4). The `Encode`/`Decode` derives change shape, which matters nowhere: saved state V1 stores numbers, saved state V0 decodes the separate legacy struct. PR #4648's reduced platform state also stores numbers.
- No method version bump in any table. No `DPPMethodVersions` slot (D8). No consensus error codes. No proto, DAPI, SDK, wasm, FFI, Swift or Kotlin surface: clients that expose "latest protocol version" read it from `PlatformVersion::latest()` and simply report 17.
- No `feature_initial_protocol_versions` constant: the `Option` in the tables is the gate.

## 6. What stays byte-identical

`PLATFORM_V1` to `PLATFORM_V14` behaviour (their tables gain only `None` fields); `FEE_VERSION1` and `FEE_VERSION2` on every value the fee history serves; `FEE_VERSIONS`; every `vN` method module in `dpp`, `drive` and `drive-abci`; `process_raw_state_transitions`, `check_tx`, `execution_result.rs` (Tenderdash gas fields); `BaseOp`; `BlockExecutionContextV0`; `NotExecutedReason`; every native budget (proposer timer, withdrawal and shielded per-block caps, Tenderdash `max_gas` in dashmate). Replay of every block at protocol versions 1 to 14 is unchanged because no shipped table changes a non-`None` value and no code path reads the new fields.

## 7. Tests and where they live

`packages/rs-platform-version/src/version/system_limits/mod.rs` (`#[cfg(test)] mod tests`):
- `smart_contract_computation_limits_and_pricing_activate_together`: for every entry in `PLATFORM_VERSIONS`, `system_limits.smart_contract_computation.is_some() == fee_version.dashvm.is_some()`; every `Some` limits value passes `is_well_formed()`; every `Some` price is non-zero; and every version below `PROTOCOL_VERSION_17` is `None`. This is a cross-table invariant (limits without a price or a price without limits would let an activated version either meter for free or reject every invocation), not a restatement of a single literal.
- `mock_platform_versions_have_no_smart_contract_computation_limits` (`mock-versions`): the mock registry stays `None`, the same shape as the existing documents-batch mock test.

`packages/rs-dpp/src/fee/smart_contract_computation.rs`:
- `should_price_computation_units_at_the_schedule_rate` (`PlatformVersion::latest()`; 25,000,000 units at the provisional rate).
- `should_price_zero_units_as_zero_credits`.
- `should_fail_with_overflow_when_the_charge_does_not_fit_in_credits` (a `FeeVersion { dashvm: Some(FeeDashVmVersion { credits_per_computation_unit: 2 }), ..latest.fee_version.clone() }` with `u64::MAX` units).
- `should_report_corrupted_code_execution_when_the_schedule_has_no_smart_contract_pricing` (`PlatformVersion::get(14)`).

`packages/rs-drive-abci/src/execution/types/block_computation_budget.rs`:
- `should_not_exist_before_the_5_0_protocol_version` (`get(14)` gives `None`; `latest()` gives the per-block limit as `remaining`).
- `should_reserve_up_to_the_exact_remaining_budget` (exact-limit fits; one more unit is `Exceeded` with the right `requested`/`remaining`, and the ledger is unchanged after the failure).
- `should_settle_actual_consumption_and_release_the_unused_bound` (reserve 1,000, settle 600: consumed 600, remaining limit minus 600, released 400).
- `should_reject_settling_more_than_the_reserved_bound` (`CorruptedCodeExecution`; ledger unchanged).
- `should_account_many_reservations_without_double_spending` (a sequence of reserve/settle pairs; `consumed + remaining == limit` after every step; a reservation moved into `settle` cannot be used again, by type).
- `should_keep_the_budget_of_an_unsettled_reservation_held` (an outstanding reservation reduces `remaining` until settled; a dropped reservation is a caller bug documented on the type, and `remaining` stays reduced, so R06-02's rollback path must settle with zero rather than drop).
- `should_use_checked_arithmetic_at_the_top_of_the_range` (a ledger built from a hand-made limits value at `u64::MAX`).

Nothing at the strategy-test level: no behaviour changes on any block path (R06-03 owns the block-level tests once R06-02 enforces).
