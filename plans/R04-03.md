# R04-03 plan: contract-only document create/replace/delete authorization

Working artifact. Never staged, never committed. Delete when the task ships.

Base: `v5.0-dev` at `5f1e0ccdce` (the exact commit the issue's architecture guide
inspected, so its file references have no drift). Branch `dashvm/r04-03`.
Tier: xhigh, confirmed (new consensus validation generations, a new protocol
version table set, a new consensus error code; no fee, storage layout, proof or
VM boundary change, so not max).

## 1. Acceptance in my words

Confirmed policy (section 4.2, capability appendix, storage DIP, guards DIP):

- A data contract may declare document types "whose create/replace/delete
  actions can only be initiated through the contract's rules".
- "An ordinary signed document transition cannot bypass a declaration that
  requires contract execution. The implementation must add that contract-only
  authorization route; today's `OwnerOnly` restriction is not an equivalent
  substitute."
- "Ordinary contracts are not identities ... introduce no keyless contract
  identity model." "Contracts are their own native owners, not ordinary
  identities without keys." "Keep signer, caller contract and resource owner
  distinct."
- Architecture: "Extend existing native action families with typed contract
  ownership/asset-subject information. Do not fabricate an identity or signed
  state transition for a contract." Native origin lives in
  `rs-drive::validation::context`, constructed natively, never decoded from
  guest bytes. Ordinary and contract operations must reach the same versioned
  validator.
- Q36: reject unsupported or conflicting declarations instead of ignoring them.
- Q18: reuse the existing versioned index/config update rules; no migration.

So the task delivers, at protocol version 17 only:

1. A document-type declaration (`contractOnly: true`) that native validation
   understands.
2. Rejection, as a paid consensus error visible at mempool admission, of every
   ordinary signed `create`, `replace` and `delete` transition targeting such a
   type, regardless of which identity signed it.
3. A typed native origin (`Identity` versus `Contract`) and one versioned Drive
   check that both the existing ABCI validators and the future contract host
   call, so that the contract's own code (a contract principal, identified by
   its contract id, never by an identity) is the only initiator these types
   accept.
4. Evidence that documents held and written by a contract principal (owner id =
   contract id, no identity record) round-trip through the existing Drive
   document insert, update, delete, query and proof paths unchanged.
5. Freezing the declaration across contract updates and rejecting the
   declaration combinations this generation does not support.

Out of scope (owned elsewhere): the contract executor and host adapters that
construct a `Contract` origin (CALLS, HOST, NATIVE tasks), extraction of the
remaining stateful document validators from ABCI into Drive (CAP-03), typed
refund owners on storage flags (FIX-08, PR #4789), ACL-based authorization
(INT-ACL), native guards and predicates (GUARDS).

## 3. Design

### 3.1 The declaration (DPP)

New document-type keyword **`contractOnly`** (boolean, default `false`),
provisional name taken from the owner's own phrase "contract-only". Meaning:
create, replace and delete of documents of this type can only be initiated by
the declaring contract's own code. Ordinary signed batch transitions carrying
those three actions on the type are rejected. `documentsMutable` and
`canBeDeleted` keep governing whether replace and delete are possible at all
(for the contract too); `contractOnly` only narrows who may initiate them.

Explicit decisions (all provisional, repeated in the PR body):

- `contractOnly: true` with `creationRestrictionMode` other than 0 is rejected
  at parse time: the contract-only rule already restricts creation, and
  stacking an owner-only rule on top would need a second authorization vocabulary
  for the contract route.
- `contractOnly: true` with `indexOnly: true` is rejected in this generation.
  Index-only types delete through the `indexOnlyDelete` action, which would
  need its own gated generation; rather than ship an unguarded fourth action,
  the combination is refused and can be admitted by a later generation.
- `transferable`, `tradeMode` and the transfer/purchase/updatePrice actions are
  untouched: they are separately declared native actions, the guards DIP asks
  for explicit action scopes rather than wildcards, and the confirmed text
  names create/replace/delete only. A contract-only type that also declares
  `transferable: 1` therefore still allows an owner-signed transfer. Documented
  in the book chapter and tested.
- No contract-level default (unlike `documentsMutable`); the keyword is per
  document type only.
- The keyword is frozen across contract updates (cannot be added, removed or
  flipped), like every other document-type switch.

DPP surface:

- `packages/rs-dpp/src/data_contract/document_type/mod.rs`: property name
  constant `CONTRACT_ONLY = "contractOnly"`; `pub mod contract_only;`.
- New `packages/rs-dpp/src/data_contract/document_type/contract_only/mod.rs`:
  `DocumentWriteAction { Create, Replace, Delete }` (`Encode`, `Decode`,
  `Display`, `Copy`), the vocabulary shared by the Drive check and the error.
  It deliberately does not reuse `DocumentTransitionActionType`, which is
  behind the `state-transitions` feature while consensus errors are compiled
  unconditionally.
- `DocumentTypeV2` gains `contract_only: bool`; both `From` conversions set
  `false`. `DocumentTypeV2Getters::contract_only()` and
  `DocumentTypeV2Setters::set_contract_only()` on the struct, `DocumentType`,
  `DocumentTypeRef` and `DocumentTypeMutRef` (V0 and V1 variants return
  `false`, exactly as `index_only()` does).
- New consensus error `DocumentActionRequiresContractExecutionError`
  (`packages/rs-dpp/src/errors/consensus/basic/document/document_action_requires_contract_execution_error.rs`):
  fields `data_contract_id: Identifier`, `document_type_name: String`,
  `action: DocumentWriteAction`; standard derive stack, private fields,
  `new()`, getters, ordering banner, `From` into `ConsensusError::BasicError`.
  Appended at the tail of `BasicError`; code **10419** (next free in the basic
  document band, provisional, renumbered on rebase if a sibling takes it).
  Mirrored with one `generic_consensus_error!` arm in wasm-dpp. wasm-dpp2 needs
  nothing (generic code passthrough).

### 3.2 The native origin and the shared check (Drive)

New module tree `packages/rs-drive/src/validation/` (server feature), the seed
of NATIVE_VALIDATE:

- `validation/mod.rs`: module docs, `pub mod context; pub mod documents;`.
- `validation/context/mod.rs`: `AuthenticatedOrigin` (name from the
  architecture guide), an internal, non-serialized enum:
  `Identity { identity_id: Identifier }` for an ordinary signed transition and
  `Contract { contract_id: Identifier, signer_id: Identifier }` for an action
  initiated by a contract's code on behalf of the transaction signer. No serde
  or bincode derives, so it can never be decoded from guest bytes. Caller and
  delegation facts are appended by the CALLS/AUTH tasks; the enum is internal
  so that is not a wire change.
- `validation/documents/mod.rs` and
  `validation/documents/write_authorization/{mod.rs, v0/mod.rs}`:
  `validate_document_write_authorization(document_type: DocumentTypeRef,
  action: DocumentWriteAction, origin: &AuthenticatedOrigin, platform_version)
  -> Result<SimpleConsensusValidationResult, Error>`. Dispatcher reads
  `platform_version.drive.methods.validation.document_write_authorization`
  (`OptionalFeatureVersion`): `None => Err(DriveError::VersionNotActive)`,
  `Some(0) => v0`, other => `UnknownVersionMismatch`. v0 rule:
  - type not `contract_only()` -> valid (existing rules apply downstream);
  - `Identity` origin -> `DocumentActionRequiresContractExecutionError`;
  - `Contract { contract_id, .. }` with `contract_id ==
    document_type.data_contract_id()` -> valid;
  - `Contract` naming another contract -> the same error (only the declaring
    contract's code initiates these actions).
  The check is pure (no GroveDB read, no billing). It is versioned through the
  table rather than left as a plain helper because the contract host will
  dispatch to it through the same slot, and because NATIVE_VALIDATE keeps
  version dispatch for every extracted check.
- A contract principal acting on a type that is not contract-only is, for this
  check, simply allowed; downstream rules then see the contract id where an
  identity id would be (creation restriction, document owner comparison). No
  caller constructs a `Contract` origin in this PR; the rule is stated so the
  host tasks inherit one definition.

Tables: new `packages/rs-platform-version/src/version/drive_versions/drive_validation_method_versions/{mod.rs, v1.rs, v2.rs}`
with `DriveValidationMethodVersions { document_write_authorization:
OptionalFeatureVersion }`; `DRIVE_VALIDATION_METHOD_VERSIONS_V1` is `None`
(referenced by `DRIVE_VERSION_V1..V9` and the `mocks/v2_test.rs` literal),
`V2` is `Some(0)` (referenced by `DRIVE_VERSION_V10`). `DriveMethodVersions`
gains `pub validation: DriveValidationMethodVersions`, added above
`platform_state`/`group` with the other method groups.

### 3.3 Enforcement on ordinary signed transitions (Drive ABCI)

New generations only; every shipped `vN` stays byte-identical.

- Create: `document_create_transition_action/advanced_structure_v2/mod.rs`,
  a copy of v1 (including the testnet epoch 2080 carve-out and the contest
  cross-check) that, right after the document type lookup, calls the Drive
  check with `AuthenticatedOrigin::Identity { identity_id: owner_id }` and
  `DocumentWriteAction::Create`, returning its errors. Dispatcher arm `2`,
  `known_versions [0, 1, 2]`.
- Replace: `document_replace_transition_action/advanced_structure_v1/mod.rs`,
  a copy of v0 with the check before the `documents_mutable` test. The
  dispatcher trait `validate_structure` gains `owner_id: Identifier` (first,
  before `platform_version`); the `0 =>` arm ignores it and calls the

- Delete: `document_delete_transition_action/advanced_structure_v2/mod.rs`,
  a copy of v1 with the check before the deletability test; signature

  conventions chapter forbids threading a parameter through a shipped
  generation even when the old behaviour is unchanged; the alternative (edit
  two call sites in v0) was rejected for that reason.

  `creationRestrictionMode`, so CheckTx rejects the transition at mempool

### 3.5 Contract-held documents (Drive evidence)

Drive's insert, update, delete, query and proof paths take an owner id as bytes
and never consult the identity tree, so a contract id already works as a
document `$ownerId`. The plan adds tests proving it end to end (insert with
owner = contract id, update, delete, query result carries the contract id,
`verify_proof` round trip) so the "contracts rather than keyless identities"
model has a regression guard before the host tasks build on it. Storage flag
owner for such writes stays the raw 32 bytes until typed refund owners (FIX-08)
land; that PR does not touch these paths and this one does not touch storage
flags.

alone: with no parser admitting the keyword, `contract_only()` is `false` for
every contract in existence, so the new generations behave exactly like the
old ones for all real inputs. Part 2 depends on part 1's field, getters and
error.

## 6. Provisional choices for the PR body

- Keyword name `contractOnly`, boolean, per document type, no contract default.
- Actions covered: create, replace, delete. Transfer, purchase and price
  updates keep their own declarations and authorization.
- Rejected declaration combinations in generation 4: with
  `creationRestrictionMode` other than 0, and with `indexOnly`.
- Error `DocumentActionRequiresContractExecutionError`, code 10419.
- Origin model `AuthenticatedOrigin::{Identity, Contract}` and the rule that
  only the declaring contract's code initiates writes on its contract-only
  types; a contract principal elsewhere is treated as an acting identifier
  equal to the contract id.
- Contract-held documents carry the contract id as `$ownerId`; refund owner
  typing is FIX-08's.
- Protocol version 17 for 5.0 with placeholder 15 and 16, per the allocation
  register.
- New `validation` method group in `DriveMethodVersions` as the home of
  extracted native checks.

  a real emission of `contractOnly: true` once part 2 lands.
