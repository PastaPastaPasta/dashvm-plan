## 1. Acceptance, restated

Owner policy (section 12.1, confirmed): storage refunds use the appropriate historical rates; allocation and repair preserve existing history; a consensus-visible correction needs an explicit version boundary. DVM-07 "Fee version integrity": audit all deletion and refund callers, including scheduled and block lifecycle cleanup, for required historical context; unknown identifiers are errors, never a fallback to the current table. DVM-07 "Typed refund ownership and conservation": refunds follow the recorded owner; a wiped owner's later refunds go to the current processing pool; a frozen but existing owner receives native bookkeeping refunds without spending permission (Q26, confirmed, this task's acceptance); incremental cleanup cannot credit a balance twice; conservation is tested across identities, prefunds and pools separately. DVM-07 "Backward compatibility": historical replay and old fee formats are preserved on replay-from-genesis and saved-state upgrade paths. Workstream item: test replay-from-genesis versus saved-state refunds across affected boundaries; document the agreed invariant in the DIPs.

Deliverables in my words:

1. An audit table of every Drive fee-returning call site and every block-lifecycle Drive application, stating whether the path can free owner-flagged bytes and what fee history it passes (section 2; goes into the part 1 PR body).
2. Under PV15, Drive's fee calculation refuses to price an owner-attributed (sectioned) storage removal without fee history and consults the history on every fee version number (never the empty-map shortcut). Every shipped protocol version keeps `calculate_fee` v0 byte-identical, and for every shipped schedule v1 produces the same credits as v0, proved by tests.
3. Every production path that frees owner-flagged bytes passes the block's fee history and settles the refunds in the block that removes the bytes. Today the only such path that does neither is the vote poll end cleanup. Its new generation computes the fee result with the block's fee history, credits each recorded owner, routes a refund whose owner has no balance to the current epoch's processing pool (Q26's native form), and records the refunds in pending epoch refunds against their storage epochs. No spending permission is consulted on any route.
4. Replay from genesis, restart from saved state and the PV14 to PV15 activation boundary produce the same lifecycle refunds and the same resolved fee history, proved by unit tests with exact credits and by strategy tests that restart mid-chain and upgrade across an epoch.
5. The state transition refund path applies the same owner rule (part 3): another owner's refund goes to that owner when a balance exists and to the current processing pool when it does not, instead of halting.
6. The invariant is written into DVM-07 (dashpay/dips PR 190 branch, via the part 3 PR body) and the book's fee chapter.

## 3. Design decisions

D1. **The storage-epoch refund rate is R12-01's change and is not duplicated.** `consume_to_fees_v1` calls the existing `FeeRefunds::from_storage_removal`. If R12-01 has merged into the base when part 1 lands, `v1` prices each removed epoch at its storage-epoch schedule; if not, it prices at the removal epoch until R12-01 lands, and every shipped input is identical either way. Part 1's implementer checks `git log --oneline origin/<base> -- packages/rs-dpp/src/fee/fee_result/refunds.rs` for R12-01's commit ("price storage refunds at the rate active when the bytes were stored"); when present, part 1 adds the storage-epoch pricing test named in section 4; when absent, that one test is deferred to part 2 and the PR body says so. Rationale: the release rules forbid independent copies of the same fix, and R12-01's plan review already settled the in-place form.

D2. **Fee history is required and always consulted under PV15.** `Drive::calculate_fee` gains `v1` (drive table slot `fees.calculate_fee: 1`) calling `consume_to_fees_v1`: the `SectionedStorageRemoval` arm takes the system bucket, then `previous_fee_versions.ok_or(CorruptedCodeExecution("a storage refund needs the fee history of the block that removes the bytes"))?` on every fee version number, then `from_storage_removal` with that history. No empty-map shortcut. `v0` stays byte-identical. Equality: for every entry of `PLATFORM_VERSIONS` and every history the epoch-change hook could build from them, `v1` credits equal `v0` credits, because every shipped schedule shares number 1 and the same storage rates (pinned by test). This is the explicit version boundary section 12.1 asks for: below PV15 nothing changes; at PV15 a missing history halts instead of silently pricing at the first generation.

D3. **One Drive primitive credits recorded owners and reports what it could not route.** New versioned method `credit_storage_refunds_to_owners_operations` under `drive/identity/update/methods/` with slot `drive.methods.identity.update.credit_storage_refunds_to_owners: OptionalFeatureVersion` (`None` in `DRIVE_IDENTITY_METHOD_VERSIONS_V1` and `V2`, `Some(0)` in the new `V3` referenced by `DRIVE_VERSION_V10`). Input: `&FeeRefunds`. For each owner: sum its per-epoch credits with checked arithmetic; `fetch_identity_balance_operations(owner, apply = true)`; if `Some`, push `add_to_identity_balance_operations(owner, credits)`; if `None`, add the credits to `unrouted`. Output `StorageRefundCreditOutcome { credited: BTreeMap<Identifier, Credits>, routed_to_processing_pool: Credits }`. The primitive does not write the processing pool and does not record pending refunds; the caller does both, so a block issues exactly one processing-pool write (section 2.1, write-collapse row) and the pending-refund recording stays with the existing versioned methods. No key, signature or permission is consulted on any route: this is the native form of "a frozen but existing owner receives bookkeeping refunds without spending permission", and "an owner without a balance element" is the native proxy for "a wiped owner" until FIX-08 types the owner encoding (this proxy is provisional and flagged in the PR body).

D4. **The awarded document stays as shipped; every contested element is refunded to its recorded owner, the winner's included.** Rejected: moving the winner's contested storage flags onto the awarded document (the second pass's D4). The contested copy's index entries under the vote poll tree are also flagged with the winner and are deleted by the cleanup, so the winner would be refunded for those bytes at poll end and again when the awarded document's index references (carrying the moved flags) are deleted later: a double refund, and the two byte counts are not equal, so "moved" is not exact. Also rejected: inserting the awarded document flagged at the award epoch, which would charge nobody but refund the winner later for a fee never paid. Chosen: the contested copy is storage the winner paid for and no longer exists, so it is refunded like any other removed owner-attributed bytes; the awarded document is a protocol-written record with no recorded owner, exactly as `award_document_to_winner` v0 writes it today. `award_document_to_winner` is not versioned by this task. The policy consequence (an awarded name is unpaid and unrefundable) is unchanged from today and recorded for FIX-08 and R12-09.

D5. **Vote poll cleanup v2 computes and settles refunds in the same block.** `clean_up_after_contested_resources_vote_polls_end_v2`: build the operation list for all ended polls with the existing v0 builder; apply it through `apply_batch_low_level_drive_operations` collecting the cost operations; `Drive::calculate_fee(None, Some(cost_ops), &block_info.epoch, epochs_per_era, platform_version, Some(previous_fee_versions))`; take `fee_result.fee_refunds`; `credit_storage_refunds_to_owners_operations` into a second operation list; empty prefunded specialized balances exactly as v1 does, adding their credits and `routed_to_processing_pool` into one total; push one `add_epoch_processing_credits_for_distribution_operation(block_info.epoch, total)` when non-zero; merge `fee_refunds.sum_per_epoch()` with on-disk pending refunds (`fetch_and_add_pending_epoch_refunds_to_collection`) and push the update (`add_update_pending_epoch_refunds_operations` into a `Vec<DriveOperation>`, its `GroveDBOpBatch` mapped to `LowLevelDriveOperation::GroveOperation`); apply the second list. Conservation holds after each batch (section 2.1). The fee history is `block_platform_state.previous_fee_versions()`, threaded through new generations (D6). Debug-level tracing of credited owners and the pool amount.

D6. **No shipped generation is edited.** Threading the fee history means new generations of `check_for_ended_vote_polls` (v1, a copy of v0 whose final call passes `block_platform_state.previous_fee_versions()`), `clean_up_after_vote_polls_end` (v1) and the contested cleanup (v2). Dispatchers gain `previous_fee_versions: &CachedEpochIndexFeeVersions` placed with the context items (after `clean_up_testnet_corrupted_reference_issue`, before `transaction`); the v0 and v1 arms do not forward it. `run_dao_platform_events` v0 is untouched: the `check_for_ended_vote_polls` dispatcher already receives `block_platform_state`. The 2022 precedent (`c6feb5b4dc`) threaded `block_info` through shipped v0 callers; the conventions chapter now forbids that, hence the copies.

D7. **Protocol version 15 is amended if present, introduced if not.** PR 4648 (state sync, base `v4.2-dev`) introduces `v15.rs` (`DRIVE_VERSION_V9`, `DRIVE_ABCI_METHOD_VERSIONS_V11`, `FEE_VERSION2`), and the register says PV15 = 4.3, so both tasks share one activation. At lane start the implementer reads `LATEST_VERSION`: if 15, part 1 sets `drive: DRIVE_VERSION_V10` in the existing `v15.rs` and part 2 bumps the voting slots in the existing `DRIVE_ABCI_METHOD_VERSIONS_V11` (the conventions' corollary: amend the unreleased version's tables, never add a table nobody references); if 14, part 1 introduces `v15.rs` as a copy of `v14.rs` with `DRIVE_VERSION_V10`, and part 2 introduces `DRIVE_ABCI_METHOD_VERSIONS_V11` as a copy of `V10` with the voting slots bumped. Textual conflicts with PR 4648 (two new `DriveMethodVersions` fields to backfill in `v10.rs`, the `v15.rs` doc comment) are resolved by whichever rebases second. PV15 keeps `FEE_VERSION2` (storage rates unchanged, so no new schedule and no `fee_version_number` change).

D8. **Part 3 gates on the 5.0 protocol version.** Register: PV16 = 4.4, PV17 = 5.0. If no lane has introduced the 5.0 version when part 3 starts, part 3 introduces the missing `v16.rs` and `v17.rs` as copies (register order) and says so in the PR body. Provisional: an owner decision that 5.0 activates a different number, or that 4.4 has no activation, overrides it, and the allocation register (A01, owned by R05-03) is the source of truth. Part 3 cannot gate on PV15: 4.3 will ship PV15 with `apply_balance_change_from_fee_to_identity: 0`, and a frozen version's tables must not differ between branches even for a natively unreachable path.

D9. **Strictness over leniency.** A missed production path under D2 halts the chain instead of mispricing silently. ## 8. The invariant (for DVM-07 and the book)

> **Storage refund invariant.** A storage refund is priced with the storage schedule that was active in the epoch the bytes were written (the epoch recorded in the element's storage flags) and scaled by the unpaid share of that epoch's perpetual distribution; the epoch that removes the bytes selects only the share, never the rate. Every path that removes owner-attributed bytes, including block lifecycle cleanup, prices its refunds with the fee history of the block that removes them and settles them in that block: the recorded owner's balance is credited, and the refund is recorded against its storage epoch's pending refunds. An owner that no longer exists (a wiped contract, once contracts exist; natively, an owner without a balance element) is settled into the current epoch's processing pool. A frozen but existing owner is credited without any spending permission being consulted. A record written by the protocol itself (an awarded contested document) has no recorded owner and is neither refunded nor charged. Removing owner-attributed bytes without fee history is an error, never a fallback to the current schedule. A replay from genesis, a restart from saved state and a state-synced node resolve the same fee history for every epoch: persisted history stores schedule numbers, and every number must resolve to its registered schedule.
