## 1. Acceptance, restated

Owner policy (section 12.1, confirmed): storage refunds must use the appropriate historical rates; allocation and repair must preserve existing history; a consensus-visible correction needs an explicit version boundary. DIP DVM-07 "Fee version integrity": audit all deletion/refund callers, including scheduled and block lifecycle cleanup, for required historical context; preserve historical storage flags and refund rates on old records; unknown identifiers are errors, not a fallback to the current table. DVM-07 "Typed refund ownership and conservation": refunds follow the recorded owner; wiped-owner refunds go to the current processing pool; a frozen but existing owner may receive native bookkeeping refunds without spending permission (Q26, confirmed, this task's acceptance text); incremental cleanup cannot credit a balance twice; test conservation across identities, prefunds and pools separately. DVM-07 "Backward compatibility": preserve historical replay and old fee formats on both replay-from-genesis and saved-state upgrade paths. Workstream item: test replay-from-genesis versus saved-state refunds across affected boundaries; document the agreed invariant in the DIPs.

Deliverables in my words:

1. An audit table of every Drive fee-returning call site and every block-lifecycle Drive application, stating whether the path can free owner-flagged bytes and what fee history it passes. This is section 2 and goes into the part 1 PR body.
2. Under the new protocol version, Drive's fee calculation refuses to price a sectioned (owner-attributed) storage removal without fee history (`CorruptedCodeExecution`, never a silent fallback to the current schedule), and prices each removed byte at the storage schedule active in the epoch the bytes were written. Under every shipped protocol version the shipped behaviour stays byte-identical, and for every shipped schedule the new pricing produces the same credits as the old (all shipped schedules share storage rates), proved by tests.
3. Every production path that can free owner-flagged bytes passes the block's fee history. Today that is: state transitions (already correct), masternode identity updates (already correct), block fee processing (already correct), and the vote poll end cleanup (does not compute fees at all today). The cleanup gets a new generation that computes the fee result with the block's fee history and settles it in the same block: recorded owners are credited, refunds are recorded in pending epoch refunds against their storage epoch, and an owner that has no balance is settled into the current epoch's processing pool (Q26's native form). The awarded document keeps the winner's original storage flags so a later deletion refunds exactly what was paid.
4. Replay-from-genesis, saved-state restart and the PV14 to PV15 activation boundary produce the same refunds and the same fee history, proved by unit tests with exact credit amounts and by strategy tests that restart a node mid-chain and upgrade across an epoch.
5. The state transition refund path applies the same owner rule (part 3): a recorded owner without a balance is settled into the processing pool instead of halting, without consulting any spending permission; conservation is asserted for every route.
6. The agreed invariant is written into DVM-07 (dashpay/dips PR 190 branch) and into the fee chapter of the book.

## 3. Design decisions

D1. **Refunds are priced at the storage epoch's schedule.** New dpp helper `FeeRefunds::from_storage_removal_with_historical_rates` (same signature as `from_storage_removal`) uses `Epoch::new(storage_epoch_index)?` for the rate lookup. `from_storage_removal` stays byte-identical for `consume_to_fees_v0`. This is the "appropriate historical rate" of section 12.1 and DVM-07; the removal epoch selects only the unpaid share.

D2. **Fee history is required where a sectioned removal appears.** `Drive::calculate_fee` gains a `v1` (drive method version `fees.calculate_fee: 1`) calling `consume_to_fees_v1`: no `fee_version_number == 1` special case; the history map is always used when present; a `SectionedStorageRemoval` with `None` history is `DriveError::CorruptedCodeExecution("a storage refund needs the fee history of the block that removes the bytes")`. `v0` stays byte-identical. Equality proof: for every entry of `PLATFORM_VERSIONS` and every history built from them, `v1` credits equal `v0` credits, because every shipped schedule carries the same storage rates (pinned by test).

D3. **Lifecycle refunds settle in the same block through one Drive primitive.** New versioned Drive method `settle_storage_refunds_operations` (slot `drive.methods.fees.settle_storage_refunds_operations: OptionalFeatureVersion`, `None` in shipped tables, `Some(0)` from the new drive table). For each `(owner, credits per storage epoch)` in a `FeeRefunds`: sum with checked arithmetic; if the owner has a balance element (`fetch_identity_balance_operations(owner, apply = true)` returns `Some`) push `add_to_identity_balance_operations`; otherwise accumulate into a processing-pool amount; after the loop push `add_epoch_processing_credits_for_distribution_operation(current epoch, amount)` when non-zero; then merge `fee_refunds.sum_per_epoch()` with on-disk pending refunds (`fetch_and_add_pending_epoch_refunds_to_collection`) and push the update as low-level `GroveOperation`s (map the `GroveDbOpBatch` operations). Returns a small outcome struct (credited per owner, routed to pool). Conservation holds immediately (section 2.1, last two rows). This is Q26's native form: the recorded owner is credited, no spending permission is consulted, and an owner that no longer exists is settled into the current processing pool. FIX-08 later widens "owner" to a typed encoding (contract bucket); this primitive is the seam it extends.

D4. **The awarded contested document keeps the winner's storage flags.** `award_document_to_winner` v1 reads the winner's contested element (path `vote_poll.documents_storage_path_vec()`, key = document id), takes its `StorageFlags` (epoch and owner as written at contest creation), deletes the contested copy and inserts the awarded copy with those flags in one uncharged system batch. The cleanup then finds only losers' documents. Reason: settling the winner's contested-copy refund while re-inserting an unflagged copy would refund bytes that still exist, and inserting a flagged copy at the award epoch would let a later deletion claw back a distribution that never happened. A move with preserved flags keeps "written data records its owner" true and keeps every later refund equal to what was paid.

D5. **Vote poll cleanup v2 settles losers' refunds and the creator's end-date refund.** `clean_up_after_contested_resources_vote_polls_end_v2` processes polls one at a time: build the v1 operation list for that poll, apply it collecting cost operations, `Drive::calculate_fee(None, Some(cost_ops), &block_info.epoch, epochs_per_era, platform_version, Some(fee_history))`, then `settle_storage_refunds_operations` and apply the settlement batch. Prefunded balance emptying stays as in v1. The fee history is `block_platform_state.previous_fee_versions()`, threaded down through new generations (D6).

D6. **No shipped generation is edited.** Threading the fee history into the cleanup means new generations of `check_for_ended_vote_polls` (v1, copy of v0 that calls the widened `clean_up_after_vote_polls_end`), `clean_up_after_vote_polls_end` (v1) and the cleanup (v2); `run_dao_platform_events` v0 is untouched because the `check_for_ended_vote_polls` dispatcher signature already carries `block_platform_state`. Dispatchers widen their signatures; v0 arms ignore the new argument.

D7. **Protocol version 15 is introduced by part 1 if absent.** Register (issue section 01): PV15 = 4.3, PV16 = 4.4, PV17 = 5.0. `LATEST_VERSION` is 14 on every branch. `v15.rs` is a copy of `v14.rs` with a new drive table (`DRIVE_VERSION_V10`) and, from part 2, a new drive-abci method table (`DRIVE_ABCI_METHOD_VERSIONS_V11`); every other field identical. Provisional: if the register moves PV15 elsewhere before part 1 lands, use whatever number the register assigns to 4.3. Precedent: `2d324d80f1 feat(platform): introduce protocol version 14` (3 files, 80 lines).

D8. **Part 3 gates on the 5.0 protocol version.** If no lane has introduced it when part 3 starts, part 3 introduces the missing `v16.rs`/`v17.rs` as copies (register order) and says so in the PR body. This is provisional and flagged for the operator: an owner decision that 5.0 activates a different number, or that 4.4 has no activation, overrides it.

D9. **Strictness over leniency.** A missed production path under D2 halts the chain instead of mispricing silently. Mitigation is the audit (section 2), the exhaustive lifecycle table in the PR body, and tests that run every lifecycle path at the latest version with sum-tree verification. The lenient alternative (treat `None` as the current schedule) is the fallback the owner rejected.

D10. **Rejected: reading the fee history from the epoch tree.** Each epoch tree stores its protocol version (`credit_pools/epochs/operations_factory.rs:194`), so a schedule per epoch could be derived from consensus state. Rejected for now: it adds a metered read per refund epoch inside fee calculation and changes admission estimates; the cached map plus the number round trip already agree on both paths. Recorded for FIX-08.

D11. **DIP text lives in dashpay/dips PR 190's branch.** The CLI only allows `master` as a dips base and parts carry no repository, so part 3 puts the exact paragraph (section 8) in its PR body and the operator applies it to `codex/dashvm-dip-drafts` (or the lane opens a PR against that branch once the operator allows the base). This is flagged in the structured result.

## 8. The invariant (for DVM-07 and the book)

> **Storage refund invariant.** A storage refund is priced with the storage schedule that was active in the epoch the bytes were written (the epoch recorded in the element's storage flags) and scaled by the unpaid share of that epoch's perpetual distribution; the epoch that removes the bytes selects only the share, never the rate. Every path that removes owner-attributed bytes, including block lifecycle cleanup, prices its refunds with the fee history of the block that removes them and settles them in that block: the recorded owner's balance is credited and the refund is recorded against its storage epoch's pending refunds. An owner that no longer exists (a wiped contract, once contracts exist; natively, an owner without a balance) is settled into the current epoch's processing pool. A frozen but existing owner is credited without any spending permission being consulted. A document moved by the protocol (a contest award) keeps its recorded owner and storage epoch, so it is neither refunded nor re-charged. Removing owner-attributed bytes without fee history is an error, never a fallback to the current schedule. A restart from saved state and a replay from genesis resolve the same fee history for every epoch: the persisted history stores schedule numbers, and every number must resolve to the registered schedule.
