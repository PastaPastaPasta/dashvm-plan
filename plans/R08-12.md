## 1. Acceptance in my words

**Q10.** One evonode, one report per round; the count tree under the round (keyed by
`pro_tx_hash`) holds the raw distinct count and is never treated as eligibility proof. Whenever
the raw count could satisfy the threshold under the block's agreed active membership
(`n > 0 && 5*raw >= 4*n`, checked in `u128`), the block event walks the round's reports in
bounded pages against that single view, deletes reports whose voter is not in it, and records a
crossing only when a walk completed against one view yields `5*Y >= 4*n`. A membership change
reconsiders every pending round even without a new report (a smaller `n` can cross; a banned or
removed voter can un-cross a raw count), and the reconsideration is durable: each round carries
the view and raw count it was last judged against, so a backlog larger than one block's bound is
finished in later blocks and survives a restart. A paged walk that cannot finish in one block
persists a cursor bound to the view; a different view discards it, and no crossing is ever
committed from a partial or stale scan.

**Q11.** Every timestamp is `block_info.time_ms` of the block that commits the fact. The
membership view is the HPMN list of `block_platform_state` after `update_core_info` applied the
block's core-chain-locked height, identified by that core height, so every node judges the same
round against the same Core view after the same membership-update phase. The crossing records
`T = crossing_ms - accepted_at_ms`, `wait = clamp(T, 120 s, 3600 s)` (the bounds are
`SystemLimits` fields), `deadline = crossing_ms + wait` (checked), and queues the deadline. The
activation boundary itself is R08-13's.

**Named-module scope.** A report can only be stored under a round, and a round binds the
contract, the version, the complete bundle digest and the preparation profile; there is no
per-module vote and no per-module activation, so a partial bundle cannot cross. The digest is
`dashvm-validation`'s `BundleDigest`, computed over every module's canonical and prepared hash,
every binding, every entry and both generations, so it is only computable by a node that ran the
whole bundle through admission, ABI-name validation and binding resolution. Nothing in this task
executes guest code, and the validator that produces the digest rejects start sections. The two
enforcement points that turn the binding into a rule are outside this task and named in the PR
body: the report transition rejects a report whose digest, version or profile differ from the
round's (FIX-09), and the preparation service reports only after compiling every module and
checking every binding (R08-06, once R08-01 parts 2 and 3 exist).

## 3. Design

### 3.1 Storage and models (part 1, adopted)

Exactly the FIX-09 part 1 commits. Layout, all keys provisional under allocation A09:

```text
112 Votes
 └─ r  Readiness
     ├─ 0  contracts / contract_id / { c: pointer -> round_id, round_id / { 0 record, 1 reports CountTree keyed by pro_tx_hash, 2 scan cursor } }
     ├─ 1  deadlines / encode_u64(deadline_ms) / contract_id -> round_id
     ├─ 2  evaluation cursor (last contract id the event visited)
     └─ 3  retired rounds / round_id -> contract_id
 40 PreFundedSpecializedBalances (SumTree)
 └─ 129 readiness funds (SumTree) / fund_id -> SumItem
```

Why under `Votes` and not under the contract's smart namespace (`64 / contract_id / 2 EXEC`, the
location the architecture catalog proposes for readiness records): the smart namespace and its
two-Merk-application layout do not exist yet (R06-04, R08-03, both blocked), the deadline queue
and the fairness cursor are global anyway, and a round is transient vote state of the same kind
as a contested vote poll. Recorded as a provisional layout choice; because protocol 17 is
unreleased, R06-04 may still move the per-round records under EXEC before release if the owner
prefers, with the same Drive API.

### 3.2 Membership view (part 2; allocation A10, provisional native predicate)

`platform_events/readiness/membership_view/{mod.rs, v0/mod.rs}`:

```rust
pub(in crate::execution) struct ReadinessMembershipView {
    core_height: u32,               // block_info.core_height: the Core view the block references
    members: BTreeSet<[u8; 32]>,    // pro_tx_hash of every active evonode in that view
}
impl ReadinessMembershipView {
    fn n(&self) -> u32; fn contains(&self, pro_tx_hash: &[u8; 32]) -> bool; fn core_height(&self) -> u32;
}
impl<C> Platform<C> { fn readiness_membership_view(&self, block_platform_state, block_info, platform_version) -> Result<ReadinessMembershipView, Error> }  // dispatch on drive_abci.methods.readiness.membership_view
```

v0 predicate: an entry of `block_platform_state.hpmn_masternode_list()` with
`state.pose_ban_height.is_none()`. This is byte-for-byte the predicate of `hpmn_active_list_len`,
the native "active evonode" count the protocol upgrade tally already uses, which is what the DIP
asks the binding to be ("bound to the current native evonode eligibility implementation"). A
platform node id or platform ports are **not** required (Core requires a node id on every Evo
registration, and requiring it here would make `n` smaller than the native active count); this
differs from the FIX-09 plan and is called out as provisional. A test pins `view.n() ==
state.hpmn_active_list_len()` on a fixture with banned and unbanned evonodes. The view is built
once per block, only when at least one pending round exists (the rounds page read comes first),
and is identified by `core_height`: the HPMN list is a pure function of the block's
core-chain-locked height because `update_core_info` runs before this event and is a no-op when
the height is unchanged.

### 3.3 The block event (part 2; phase position provisional under A11, ratified by R08-13)

`run_dao_platform_events` **v1** (copy of v0) calls, after `check_for_ended_vote_polls`,
`self.process_compilation_readiness(block_platform_state, block_info, transaction, platform_version)`.
That is the single defined boundary: after the block's membership update, before this block's
transitions, so a report accepted in block `H` counts from the event of block `H + 1` (the DIP's
convention). v0 stays byte-identical apart from pinning its two tests to `PlatformVersion::get(16)`.

`process_compilation_readiness` **v0** (`platform_events/readiness/process_compilation_readiness/{mod.rs,
v0/mod.rs, v0/tests.rs}`, dispatch on the new `drive_abci.methods.readiness.process_compilation_readiness:
OptionalFeatureVersion`, `None => Err(ExecutionError::VersionNotActive)`). Every step is bounded
by a table constant, every read and write goes through the part 1 Drive API, every credit
arithmetic is checked, and an `Err` is a node fault exactly like the vote poll event (no per-round
swallow). Per block:

1. **Fairness walk.** Read the evaluation cursor `[112, r, 2]`; `fetch_readiness_rounds_page(after,
   maximum_readiness_rounds_to_evaluate_per_block)`; when fewer come back than the bound, wrap once
   from the start (never visiting a contract twice in one block); store the last visited contract
   id (or `None` when the walk wrapped to the end) as the cursor. No pending round: nothing else
   runs, no view is built.
2. **Per visited contract:** `fetch_readiness_round`; skip when absent or not `Pending`. Read
   `raw = fetch_readiness_round_raw_count`. Build the view on first need.
3. **Skip rule.** `needs_work = round.last_evaluated() != Some(ReadinessEvaluation { core_height:
   view.core_height, raw_count: raw }) || (round.awaiting_funding() && fund_can_pay_one_page)`.
   Otherwise the round costs exactly the two reads above.
4. **Cheap gate.** `if view.n() == 0 || 5u128 * raw < 4u128 * n`: clear any scan cursor, write the
   mark (`set_evaluation(.., awaiting_funding: false)`), done. Nothing is charged.
5. **Paged validation, paid by the fund.** Load the scan cursor; it is valid only when its
   `core_height == view.core_height` and `hpmn_len == n` (else discard, restart from the first
   report). Pages of `fetch_readiness_reports_page(.., after, page_len)` with `page_len =
   min(remaining block budget, u16::MAX)` where the block budget is
   `maximum_readiness_reports_to_validate_per_block` shared by all rounds visited in the block.
   Before each page: `fee = page_len_actual * membership_lookup_fee` (checked); if
   `fetch_readiness_fund(funding_id)` is below `fee + round_cleanup_reserve`, write the mark with
   `awaiting_funding: true`, persist the cursor as it stands, stop this round (a later fund top-up
   resumes it through the skip rule). Otherwise `deduct_from_readiness_fund_operations(funding_id,
   fee, round_cleanup_reserve)` and one `add_readiness_pool_credit_operation(block_info, fee_total)`
   for the round's batch (credited to the epoch processing pool, so conservation holds). Each
   examined report is eligible (`view.contains`) or pruned (`prune_readiness_reports_operations`
   with the page's ineligible keys). A page shorter than requested ends the walk.
6. **Outcome.** Walk unfinished (budget exhausted): store the cursor with the counts so far,
   write the mark, round stays `Pending`. Walk finished: `Y = eligible_so_far`; if `5*Y >= 4*n`
   (`n > 0`), `record_readiness_crossing_operations(&mut round, block_info.time_ms,
   readiness_additional_wait_min_ms, readiness_additional_wait_max_ms)` (status `Crossed`, deadline
   queued), clear the cursor; else clear the cursor and write the mark with the new (pruned) raw
   count. Either way pruned voters are gone from the count tree, so the next block's gate sees the
   corrected raw count and an unchanged view never re-walks the same round.
7. **Retired-round cleanup.** One `cleanup_retired_readiness_round_operations(first queued round,
   maximum_readiness_cleanup_deletes_per_block)` step per block (nothing in this task retires a
   round in production; the step exists so the first producer, R08-13's activation or R08-14's
   replacement, drains automatically).

Batching: each round's operations are applied as their own batch through
`apply_batch_low_level_drive_operations` (the part 1 pool credit is an absolute rewrite, one per
batch), the cursor store is its own small batch, the cleanup step its own. Rounds are visited in
contract id order, reports in key order, so every node performs identical work.

Restart safety: the mark, the scan cursor and the evaluation cursor are Drive state written in
the block's transaction; a node restarted between blocks resumes from them (tested by reopening
the platform from its tempdir between two blocks).

Activation of a `Crossed` round at its deadline, the `on_readiness_round_activated` hook and the
`maximum_readiness_activations_per_block` bound are **R08-13's** and are added to this same v0 in
place (v0 is selected only by protocol 17, unreleased). Replacement and cancellation are
**R08-14's** (the part 1 Drive primitives exist). The report transition is **FIX-09's**.

## 5. Provisional values and interpretations (the PR body repeats the ones it uses)

1. Storage under `[112, r]` with inner keys `0..3`, pointer `c`, per-round `0..2`; readiness funds
   at `[40, 129]`; fund id domain `dashvm-readiness-fund-v1`; round id
   `hash_double(network_magic || contract_id || version || bundle_digest || accepted_at_height)`
   (A09, part 1). Location under `Votes` rather than the contract's EXEC namespace (3.1).
2. Active-eligibility predicate = HPMN and not PoSe-banned, identical to `hpmn_active_list_len`;
   no node id or port requirement; view identified by the block's core-chain-locked height (A10).
3. Phase: inside `run_dao_platform_events` after ended vote polls, before ordinary transitions;
   reports accepted in block `H` count from `H + 1` (A11, R08-13 ratifies).
4. Threshold `n > 0 && 5*Y >= 4*n` in `u128`; the raw gate uses the same inequality on the count
   tree value; a crossing is committed only from a walk completed against one view.
5. Constants: 8 rounds evaluated, 512 reports validated, 512 cleanup deletes per block; 120 s and
   3,600 s wait bounds are confirmed policy, only their `SystemLimits` placement is a choice.
6. Fees: 100 credits per examined report from the round's fund to the epoch processing pool; a
   1,000,000 credit cleanup reserve the walk never spends (A15). Rates unbenchmarked, register
   values.
7. A scan cursor is invalidated by any change of the block's core height or of `n`, a stricter
   reading of "one coherent membership view" than diffing the set; a restarted walk is charged
   again; an unchanged round (same view, same raw count) is never re-scanned or re-charged.
8. A round whose fund cannot pay for one page waits (`awaiting_funding`) with no free scan and no
   expiry; a later top-up resumes it automatically.
9. Pruned reports are deleted from the count tree (the count tree tracks eligible-so-far under the
   last view, not history); an evonode that becomes eligible again reports again.
10. The retired-round cleanup step runs one bounded step per block from this task on, ahead of any
    producer of retired rounds.
11. The fee group carries only the rows this task reads; siblings append theirs.
