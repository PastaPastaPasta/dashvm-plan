# R06-08 plan: paged, bounded current-state range queries over GroveDB path elements

Working artifact. Never staged, never committed. Delete when the task ships.

Base: `v5.0-dev` at `5f1e0ccdce`. Worktree branch `dashvm/r06-08`. Tier: xhigh (proof soundness, new wire surface, client verification).

## 1. What this task delivers, in my words

Section 6.3 (confirmed policy): reuse GroveDB's existing query, proof and validation; add or expose range, paging and projection support where the code and balance APIs need it, after checking current coverage; bound response bytes; verify requested ranges, effective limits and absence correctly across SDKs; current state only.

Current coverage, checked on this tree:

- `getPathElements` V0 (`packages/rs-drive-abci/src/query/system/path_elements/v0/mod.rs`) fetches or proves an explicit key list under one path. No ranges, no limit, no direction, no response byte bound (only request bounds: 256 path components, 255 bytes per component, 64 KiB aggregate, 100 keys). `Drive::fetch_elements_v0`, `Drive::prove_elements_v0`, `Drive::verify_elements_v0` are keys-only. The client (`drive_proof_verifier::types::Elements`, `KeysInPath`) has the same shape. The wasm-drive-verify `verifyElements` export is a stub that returns an error; its note file claims `Element` is not available under the verify feature, which is stale (`verify_elements_v0` compiles under `verify` and returns `Element`).
- Document, token, identity and address queries have range and paging but are typed to their own trees. Nothing generic exists for "give me the first N elements at or after key K under path P, proven, within a byte budget".
- GroveDB at the pinned revision (`6fc7e1e8`, 5.0.1) already has everything needed: ten `QueryItem` range shapes, `SizedQuery.limit`, `left_to_right`, `prove_query`, `verify_query_with_options` with succinctness, and `start_snapshot_read_transaction` for a single committed snapshot across two reads. No GroveDB change is needed.

No smart-contract namespace (`64/contract_id/2..4`), contract credit tree or contract token holder branch exists yet (`packages/rs-drive/src/drive/contract/` has no `exec`, `packages/rs-drive/src/verify/` has no `smart_contract`). Those layouts belong to R06-04, R04-01 and R10-02. Typed code, version, bucket and receipt query families over them belong to R06-04 (queries), R06-06 (proof and client handling for code and versions) and CAP-12 (the proof and result compatibility matrix). This task therefore delivers the generic facility they all sit on, plus its verification contract and its client parity tests:

1. A versioned `getPathElements` V1 request: one path, an explicit list of query items (keys and ranges in every GroveDB shape), a limit, a direction, a `prove` flag.
2. A V1 response carrying the served page (key and serialized Element pairs, or a proof), response metadata, and the effective page size the server actually served after applying its response byte cap.
3. A Drive query type with one path-query constructor shared by the fetcher, the prover and the verifier, so the proof bytes and the verification bytes cannot drift.
4. Server bounds: request budgets (as V0), effective limit rules mirroring document queries, a response byte cap read from the version tables, one committed snapshot for the fetch-then-prove pair.
5. Client verification in `drive-proof-verifier` with the soundness rules written down: a page verifies against the smaller of the requested and served limit; a page shorter than that limit is an authenticated statement that the range is exhausted; a full page says nothing about what follows; explicit keys missing from a non-full page are proven absent; a proof for another path, range, direction, limit, root or version fails closed.
6. `rs-sdk` and `wasm-sdk`/`js-evo-sdk` surfaces, sharing one canonical Element projection, with a vector corpus that both clients are tested against.
7. Tests for paging, empty ranges, inverted ranges, request and response byte caps, effective limits, tampering (bytes, path, range, direction, limit, root, version) and projection parity.

The gate: V1 is accepted only from the 5.0 protocol version's query table. All shipped protocol versions keep answering V1 with `UnsupportedQueryVersion`.

Provisional interpretations (repeat in the PR bodies):

- P1. "Required current-state code/balance queries" is read as the generic bounded range facility of section 6.3; the typed families are built on it by R06-04, R06-06 and CAP-12. This task's `enables` edges (R06-07, R09-03, R09-08) are satisfied by the facility: R06-07 tests code retention through range proofs, R09-03 resolves host reads over the same GroveDB range primitives and bounds, R09-08 tests tampered and wrong-root proofs against the verifier contract written here.
- P2. Response byte cap: 1 MiB per page, from the allocation register row "Returned read bytes: 1 MiB per query page". Lives in the drive-abci query version table next to `max_returned_elements`, not in `SystemLimits`, because it bounds a query response and not consensus.
- P3. A single element is never split. If the first element alone exceeds the cap the page contains exactly that element (`effective_limit = 1`). Storage-side element size bounds (code chunking) are R06-04's decision; DAPI's 32 MiB encode cap stays the hard transport bound.
- P4. Effective limit rules mirror document queries: absent or zero limit means `max_returned_elements` (100); a larger limit is rejected with `InvalidLimit`.
- P5. Element projection parity is tested between the two supported application clients, `rs-sdk` (native) and `wasm-sdk`/`js-evo-sdk` (WASM), through one canonical projection type. The mobile FFI JSON formatter (`rs-sdk-ffi`) and `wasm-drive-verify` keep their current output; their alignment is CLIENT scope (R09-04, CAP-13) and is named as follow-up in the PR body.

## 2. Wire surface

File: `packages/dapi-grpc/protos/platform/v0/platform.proto`. Register in `packages/dapi-grpc/build.rs`: move `GetPathElementsRequest` to `VERSIONED_AT_V1_REQUESTS` and `GetPathElementsResponse` to `VERSIONED_AT_V1_RESPONSES` (the derive macro then generates `proof()`/`metadata()` arms for `V0` and `V1`; array lengths change from 1 to 2). No new RPC. `impl_transport_request_grpc!` for the request already exists in `packages/rs-dapi-client/src/transport/grpc.rs`.

```proto
message GetPathElementsRequest {
  message GetPathElementsRequestV0 { /* unchanged */ }

  // Paged read of one GroveDB subtree: explicit keys and/or key ranges,
  // served in key order up to `limit` elements and the response byte cap.
  message GetPathElementsRequestV1 {
    message RangeItem {
      optional bytes start = 1;      // absent: unbounded below
      bool start_exclusive = 2;      // true: strictly after `start`
      optional bytes end = 3;        // absent: unbounded above
      bool end_inclusive = 4;        // true: `end` included
    }
    message QueryItem {
      oneof item {
        bytes key = 1;
        RangeItem range = 2;
      }
    }
    repeated bytes path = 1;
    repeated QueryItem items = 2;    // at least one
    optional uint32 limit = 3;       // absent or 0: server default (100); above the default: rejected
    bool descending = 4;             // default ascending
    bool prove = 5;
  }

  oneof version {
    GetPathElementsRequestV0 v0 = 1;
    GetPathElementsRequestV1 v1 = 2;
  }
}

message GetPathElementsResponse {
  message GetPathElementsResponseV0 { /* unchanged */ }

  message GetPathElementsResponseV1 {
    message KeyedElement {
      bytes key = 1;
      bytes element = 2;             // GroveDB Element, Element::serialize(grove_version)
    }
    message Elements { repeated KeyedElement elements = 1; }

    oneof result {
      Elements elements = 1;
      Proof proof = 2;
    }
    ResponseMetadata metadata = 3;
    // Page size the server actually served. Equals the effective requested
    // limit unless the response byte cap cut the page, in which case it is the
    // number of elements that fit (at least 1). Clients verify the proof
    // against min(requested, effective_limit); a page shorter than that is an
    // authenticated end of range.
    uint32 effective_limit = 4;
  }

  oneof version {
    GetPathElementsResponseV0 v0 = 1;
    GetPathElementsResponseV1 v1 = 2;
  }
}
```

`RangeItem` to GroveDB `QueryItem` (complete over the ten shapes):

| start | end | QueryItem |
| --- | --- | --- |
| absent | absent | `RangeFull` |
| s inclusive | absent | `RangeFrom(s..)` |
| s exclusive | absent | `RangeAfter(s..)` |
| absent | e exclusive | `RangeTo(..e)` |
| absent | e inclusive | `RangeToInclusive(..=e)` |
| s inclusive | e exclusive | `Range(s..e)` |
| s inclusive | e inclusive | `RangeInclusive(s..=e)` |
| s exclusive | e exclusive | `RangeAfterTo(s..e)` |
| s exclusive | e inclusive | `RangeAfterToInclusive(s..=e)` |

Rejected as `InvalidArgument` (server) and as a query construction error (client, fail closed): `start_exclusive` with absent start; `end_inclusive` with absent end; `start > end`; `start == end` unless both bounds are inclusive (that is a one-key range); empty `items`; more than `max_returned_elements` items; any path component, key or bound over 255 bytes; more than 256 path components; aggregate raw bytes of path plus all keys and bounds over 64 KiB (the V0 constants, shared).

Generated JS clients under `packages/dapi-grpc/clients/` are not regenerated locally (Docker socket is not usable in this environment). The two most recent proto changes on this branch (`a0a67fa953`, `fba1a257a4`) also shipped without regenerating them and CI's "Build JS" regenerates from the proto. State this in the PR body.

## 3. Drive (`packages/rs-drive`)

### Query type

New `packages/rs-drive/src/query/path_elements_query.rs`, gated `#[cfg(any(feature = "server", feature = "verify"))]`, exported from `query/mod.rs`:

```rust
pub struct DrivePathElementsQuery {
    pub path: Vec<Vec<u8>>,
    pub items: Vec<QueryItem>,   // grovedb QueryItem, already validated shapes
    pub limit: u16,              // effective requested limit, never 0
    pub left_to_right: bool,
}
impl DrivePathElementsQuery {
    pub fn construct_path_query(&self) -> Result<PathQuery, Error>;  // the one builder
    pub fn with_limit(self, limit: u16) -> Self;
}
```

`construct_path_query` builds `Query::new_with_direction(left_to_right)`, inserts the items through `insert_item` (GroveDB merges overlaps deterministically; both sides run the same code), wraps in `SizedQuery { limit: Some(limit), offset: None }`. It rejects empty items, zero limit and inverted ranges with `QuerySyntaxError` variants (`NoQueryItems`, `InvalidLimit`, a new `InvalidRange(String)` appended to the enum). A `RangeItem`-like plain struct for wire conversion is not needed in Drive; the handler and the SDK convert proto to `QueryItem` directly with a shared helper placed in `query/path_elements_query.rs` (`QueryItem` construction from `(Option<start>, exclusive, Option<end>, inclusive)`), so the server and the client use the same mapping table.

### Verify (verify feature)

`packages/rs-drive/src/verify/system/verify_path_elements/{mod.rs, v0/mod.rs}`: `DrivePathElementsQuery::verify_proof(&self, proof: &[u8], platform_version) -> Result<(RootHash, Vec<(Vec<u8>, Element)>), Error>`. Uses `GroveDb::verify_query_with_options` with `absence_proofs_for_non_existing_searched_keys: false`, `verify_proof_succinctness: true` (padded proofs fail), `include_empty_trees_in_result: true` (an empty subtree is still an element to a namespace reader, as in V0). Elements come back in proof order. Dispatch slot `DriveVerifySystemMethodVersions::verify_path_elements` (new, 0 in `DRIVE_VERIFY_METHOD_VERSIONS_V1`; V2 inherits by struct update; `mocks/v2_test.rs` references the V1 constant).

Absence semantics the verifier relies on and the doc comment must state: Merk's `execute_proof` requires the proof to cover every query item until the limit is consumed, so for a page shorter than `limit` every explicit key not returned is proven absent and every range is proven exhausted; for a full page nothing past the last returned key is established.

Must compile with `cargo check -p drive --no-default-features --features verify`. The query type uses only `grovedb::{Element, PathQuery, Query, SizedQuery}` and `grovedb_query::QueryItem`, all verify-available.

## 4. Query server (`packages/rs-drive-abci`)

### Dispatcher

In Part 1 every table has `max_version: 0`, so V1 is answered with `UnsupportedQueryVersion` at every protocol version; Part 2 flips the 5.0 table.

### Handler

New `packages/rs-drive-abci/src/query/system/path_elements/v1/mod.rs`:

1. Validate the request (section 2 rules) with the V0 constants moved to `path_elements/mod.rs` so V0 and V1 share them. Errors: `QueryError::InvalidArgument` for shape and byte budgets, `QueryError::Query(QuerySyntaxError::InvalidLimit)` for limit.
2. Effective requested limit: `limit.unwrap_or(0)`; `0` means `max_returned_elements`; above it is `InvalidLimit`; otherwise the value (fits `u16`).
3. Build `DrivePathElementsQuery` (direction from `descending`).
4. `let snapshot = self.drive.grove.start_snapshot_read_transaction();` and pass `Some(&snapshot)` to both Drive calls so the fetched page and the proof come from one committed root (DIP: one short committed snapshot per multi-part response). Drop it before building the response.
5. `fetch_path_elements` with the requested limit. Walk the elements accumulating `element.serialized_size(grove_version)` plus key length; `k` is the count that fits under `max_path_elements_response_bytes`, at least 1 when the page is non-empty (P3). `effective_limit = if k < elements.len() { k } else { requested }`.
6. `prove`: `prove_path_elements` with `query.with_limit(effective_limit)`; response `Proof` via `response_proof_v0(.., GroveDBToUse::Current)`. Not `prove`: serialize the first `k` elements.
7. `metadata` via `response_metadata_v0(platform_state, CheckpointUsed::Current)`, `effective_limit` as computed.

Fetch-then-prove doubles the GroveDB read for proven pages; the page is bounded to 100 elements so this is acceptable and is what makes the proof's limit equal the served page (a proof generated with the requested limit cannot be verified against a shorter page).

### Transport validation

`packages/rs-drive-abci/src/query/service.rs::validate_path_elements_request` and `packages/rs-dapi/src/services/platform_service/mod.rs::validate_path_elements_request` currently match only `V0`; both become non-exhaustive once `V1` exists and must validate V1 with the same budgets (components, per-component bytes, aggregate bytes, item count against `max_returned_elements`).
