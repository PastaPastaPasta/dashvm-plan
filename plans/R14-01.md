# PLAN R14-01: cross-architecture replay, targeted fuzzing and upgrade tests in CI

Working artifact. Never staged, never committed. Delete when the task ships.

Base: `v5.0-dev` at `5f1e0ccdce` (worktree branch `dashvm/r14-01`). Tier: high (confirmed, not raised: no consensus, fee, storage, proof or VM-boundary code changes). Two sequential parts, both on `v5.0-dev`.

## 1. Acceptance in my words

The workstream issue (#4696) ticks R14-01 when CI:

1. Runs a deterministic execution/replay workload on both supported architectures (x86_64 and aarch64), records what consensus must agree on (application hashes, transition results and fees, protocol version per block, credit totals), and compares the two recordings. A consensus-visible mismatch fails the run; diagnostic values (timings, CPU features, later raw engine fuel) are recorded and reported, never compared.
2. Proves the comparison can fail: the pipeline exercises the mismatch path on every run (a self-test of the comparator plus a deliberately perturbed real artifact) instead of asserting that "the checks pass".
3. Runs the replay across a real protocol upgrade boundary and a node restart (stop, reopen from persisted state, continue), so upgrade and recovery are part of the recorded evidence rather than a separate empty-workload test.
4. Runs targeted fuzzing of the untrusted decoding surfaces (state transition, data contract, document decoders and `check_tx` itself) under an explicit case budget: a small budget inside the normal PR suite, a deeper budget nightly, with a hard time bound.
5. Does all of this within workable bounds: hosted runners, one build per architecture, a job timeout, no new self-hosted runner requirement, no change to the PR fast path's one-simulation gate.

The DashVM-specific corpus clause (canonical NaN bits, protocol-metered trap cost, raw Wasmtime fuel) cannot run on this tree: there is no engine crate on `v5.0-dev`, the engine pin is an open allocation (A04, owned by R08-01), and the corpus itself is owned by R03-01 and R08-08, both of which list R14-01 as their prerequisite. This task therefore delivers the pipeline they plug into: the artifact schema has a `consensus` section (must match), a `diagnostic` section (record only) and a `profile` section (protocol versions must match, target must differ, CPU features recorded), and the comparator enforces exactly the rule the owner recorded: consensus-visible mismatch rejects, diagnostic mismatch is reported. The PR bodies say so in those words and do not claim the corpus was run.

Owner constraints honoured: no audit, funding or deployer-allowlist gate; no new recovery authority; the seven-day shadow window and two-rehearsal target are named as provisional engineering proposals in the book chapter, not encoded as CI gates.

## 2. What the tree looks like (drift from the issue)

- No `packages/rs-dashvm*`, no `wasmtime` in `Cargo.lock`. The `dashvm-validation` crate and protocol versions 15 to 17 exist only on the open sibling lane `origin/dashvm/r08-01` (same base). Nothing here depends on it.
- `LATEST_VERSION` is 14 on `v5.0-dev`. The plan never hard-codes 13/14: the upgrade test uses `PlatformVersion::latest()` and `latest - 1`, so it survives the placeholder versions r08-01 introduces.

## 3. Design

### 3.1 Determinism artifact (Rust, strategy harness)

New file `packages/rs-drive-abci/tests/strategy_tests/determinism_artifact.rs` (module registered in `main.rs`):

```rust
pub struct DeterminismArtifact { schema: u32 /* 1 */, profile: Profile, consensus: Consensus, diagnostic: Diagnostic }
pub struct Profile {
    target_arch: String, target_os: String, pointer_width: u32, endian: String,
    cpu_features: Vec<String>,          // recorded, never compared
    protocol_version_start: u32, protocol_version_end: u32,   // must match
    engine: Option<EnginePin>,          // always None on this tree; reserved for R08-01 (engine build, Cranelift settings, memory guards, NaN canonicalisation)
}
pub struct Consensus {
    workload_seed: u64,
    reopened_at_height: u64,
    blocks: Vec<BlockRecord>,           // height, epoch_index, protocol_version, app_hash (hex), transitions: Vec<TransitionRecord { name, code: u32, fee: i64 }>
    final_root_hash: String,
    total_credits: TotalCreditsRecord,  // fields of dpp TotalCreditsBalance at the last block
    identity_balances: BTreeMap<String, u64>, // hex identity id to credits, sorted
}
pub struct Diagnostic { elapsed_ms: u64, block_count: u64, engine_fuel: Option<()> /* reserved: raw engine fuel per trapping case, diagnostic unless it affects consensus */ }
```

- Serialised with `serde_json` (already a `drive-abci` dependency with `preserve_order`); all maps are `BTreeMap`, all hashes lowercase hex, so the bytes are canonical. A unit test encodes twice and asserts identical bytes, then mutates one app hash and asserts the bytes differ.
- `cpu_features` uses `is_x86_feature_detected!` on x86_64 (sse3, ssse3, sse4.1, sse4.2, popcnt, avx, avx2, bmi1, bmi2, lzcnt, fma) and `std::arch::is_aarch64_feature_detected!` on aarch64 (neon, lse, crc, aes, sha2, dotprod); empty elsewhere. This is the "recorded target-specific CPU settings" the acceptance names; guard settings arrive with the engine pin.
- Written to `$PLATFORM_DETERMINISM_ARTIFACT_DIR/determinism-<target_arch>.json` when that variable is set; otherwise the test only asserts in-process.

### 3.2 The workload: upgrade plus restart (Rust)

New file `packages/rs-drive-abci/tests/strategy_tests/test_cases/determinism_tests.rs` (registered in `test_cases/mod.rs`). Modelled on `upgrade_fork_tests::run_chain_v12_to_v13_locks_in_before_activation` for the upgrade mechanics and on the r05-05 split/reopen recipe for restart.

- Platform starts at `previous = latest - 1` via `TestPlatformBuilder::with_initial_protocol_version(previous)`; `UpgradingInfo { current_protocol_version: previous, proposed_protocol_versions_with_weight: vec![(latest, 1)], upgrade_three_quarters_life: 0.0 }`.
- Config: `epoch_time_length_s: 60`, `block_spacing_ms: 1_000`, `verify_sum_trees: true` (per-block credit conservation), `PlatformTestConfig { store_platform_state: true, ..default_minimal_verifications() }` (checkpoints off, state persisted for the reopen), `independent_process_proposal_verification: true` (proposer versus validator parity every block), `sign_chain_locks: true`.
- Workload: 10 start identities, one start contract (the crypto-card / dashpay style fixture the harness already remaps), document create/replace/delete frequencies, identity inserts and top-ups, credit transfers. No withdrawals and no token operations (they need RPC mocks and TRANSFER keys; see memory notes). Seeded `StdRng`; `start_time_ms` stays at `GENESIS_TIME_MS`.
- Two runs of the same workload and seed:
  - continuous: segment 1 (70 blocks) then segment 2 (60 blocks) on the same open platform;
  - reopened: segment 1, drop the platform, `TempPlatform::open_with_tempdir`, segment 2 with the mutated strategy (start contracts cleared, signer handed over, nonce counters carried).
- Assertions (all in-process, independent of CI):
  - the upgrade locked in before the reopen height and activated after it (protocol version in consensus flips from `previous` to `latest` inside segment 2): the restart sits inside the upgrade window, which is what "upgrade plus recovery" means here;
  - per-block app hashes, transition (code, fee) lists, identity balances and the final root hash are equal between the two runs;
  - the reopened platform resumed at height 70 with the persisted protocol version;
  - `calculate_total_credits_balance` reports a conserving state at the end.
- The artifact is built from the reopened run (it is the more demanding one) and written when the environment variable is set.
- Test names: `should_replay_identically_from_saved_state_across_the_protocol_upgrade` (workload plus artifact), `should_encode_the_determinism_artifact_canonically` (schema unit test). Attribute stack as the neighbours: `#[stack_size(4 * 1024 * 1024)] #[test] async fn`. Not `#[ignore]`: it runs in the push and nightly strategy phase on the self-hosted runners and in the new determinism workflow on hosted runners; the PR fast-path gate is not widened.
- Harness edits: add `pub app_hashes_per_block: BTreeMap<u64, [u8; 32]>` to `ChainExecutionOutcome` (filled in `execution.rs` from `root_app_hash`), so the test does not need to re-derive roots. All 65 existing destructurings use `..`, so no other test changes. Budget: about 15 lines in `strategy.rs` and `execution.rs`.
- Determinism risk to verify during implementation: run the test twice in separate processes on this machine with the environment variable set to two directories and diff the files (`compare-determinism-artifacts.py --allow-same-architecture`). Any `HashMap`-ordered path in the harness would show up here, before CI.

### 3.3 Comparator with built-in failure exercise (Python)

New `.github/scripts/compare-determinism-artifacts.py`:

- `compare A B [--allow-same-architecture]`: loads both, re-serialises `consensus` with sorted keys and compares byte-for-byte; requires `profile.protocol_version_start/end` equal, requires `profile.target_arch` to differ unless the flag is given (guards against comparing one architecture with itself), prints `profile.cpu_features`, `profile.engine` and `diagnostic` side by side as a report, exits 1 on any consensus or profile mismatch with the first differing block height and field named. Exit 2 on malformed input or unknown `schema`.
- `--self-test`: builds artifact dictionaries in memory and asserts: identical consensus passes; one differing app hash fails; one differing transition fee fails; one differing `total_credits` fails; a differing `diagnostic.elapsed_ms` passes with a note; same `target_arch` without the flag fails; differing protocol versions fail; unknown schema exits 2. This is the "exercise failure detection" requirement, executed on every CI run before the real comparison.
- Standard library only (`json`, `argparse`, `sys`), like the existing scripts.

### 3.4 Workflow: `.github/workflows/tests-rs-determinism.yml`

Name: `Determinism: cross-architecture replay`. Triggers: `schedule` (`0 21 * * *`, before the two existing nightlies), `workflow_dispatch`, and `pull_request` restricted with `paths:` to this workflow, the comparator script, `determinism_artifact.rs`, `determinism_tests.rs` and the two harness files, so the PR that introduces or edits the pipeline proves it. `concurrency` as the neighbours. Hosted runners only, so fork PRs are safe.

Jobs:

1. `record` (matrix: `ubuntu-24.04` / `x86_64`, `ubuntu-24.04-arm` / `aarch64`; `timeout-minutes: 90`; `fail-fast: false`): checkout, `./.github/actions/rust`, sccache (step-level `if` so fork PRs without secrets skip it), `./.github/actions/librocksdb` (cache key already includes `runner.arch`, `PORTABLE=1`), then
   ```
   PLATFORM_DETERMINISM_ARTIFACT_DIR="$RUNNER_TEMP/determinism" RUST_MIN_STACK=4194304 \
   cargo test --package drive-abci --test strategy_tests --all-features --locked -- determinism_tests
   ```
   with `ROCKSDB_*` as the nightly and `SNAPPY_STATIC=/usr/lib/$(dpkg-architecture -qDEB_HOST_MULTIARCH)/libsnappy.a` (the nightly hard-codes the x86_64 multiarch path; aarch64 needs `aarch64-linux-gnu`). Upload `determinism-${{ matrix.arch }}` with `actions/upload-artifact@v4`, retention 14 days.
2. `compare` (`ubuntu-24.04`, `needs: record`, `timeout-minutes: 10`): download both artifacts; run `--self-test`; run the real comparison; then copy the x86_64 artifact, flip one byte of one `app_hash` with a three-line Python edit, and assert the comparator exits non-zero against the aarch64 artifact (`if python3 ... ; then echo "::error::comparator accepted a divergent artifact"; exit 1; fi`). Publish the comparator report to `$GITHUB_STEP_SUMMARY`.

Resource bound: one debug build of the `strategy_tests` binary per architecture (the existing nightly does the same build in under 45 minutes with sccache) plus a workload of about 260 simulated blocks. No self-hosted capacity is consumed.

### 3.5 Targeted fuzzing (part 2)

Bounded property tests with `proptest` (dev-dependency `proptest = "1"` added to `packages/rs-dpp/Cargo.toml` and `packages/rs-drive-abci/Cargo.toml`; the lockfile gains dependency edges only). Modules are named `fuzz_tests` so one nextest filter, `test(/fuzz_tests::/)`, selects them everywhere, including future `dashvm-validation` admission fuzzing when that crate merges.

- `packages/rs-dpp/src/serialization/fuzz_tests.rs` (`#[cfg(test)] mod fuzz_tests;` in `serialization/mod.rs`):
  - `should_never_panic_decoding_arbitrary_state_transition_bytes`: `StateTransition::deserialize_from_bytes` on `vec(any::<u8>(), 0..4096)`; only `Ok` or `Err`.
  - `should_never_panic_decoding_mutated_state_transition_bytes`: serialise the identity-create and documents-batch fixtures from `dpp::tests::fixtures`, apply a strategy of byte flips, truncations and insertions, decode.
  - `should_never_panic_decoding_mutated_data_contract_bytes`: `DataContract::versioned_deserialize(mutated, true, PlatformVersion::latest())` from the dashpay contract fixture bytes.
  - `should_never_panic_decoding_mutated_document_bytes`: `Document::from_bytes(mutated, document_type, latest)` from the documents fixture.
- `packages/rs-drive-abci/src/execution/check_tx/fuzz_tests.rs` (`#[cfg(test)] mod fuzz_tests;` next to the existing tests module):
  - `should_never_panic_or_fail_internally_on_arbitrary_check_tx_bytes`: one `TestPlatformBuilder` platform, a `proptest::test_runner::TestRunner` driven manually (the platform is built once, outside the macro), arbitrary and mutated bytes through `Platform::check_tx(raw, FirstTimeCheck, &platform_ref, latest)`; asserts `Ok(_)` (an invalid transition is a `ConsensusValidationResult`, never `Err`; a panic here is a mempool crash). If implementation finds an input class that legitimately returns `Err`, record it in the test's doc comment and in the PR body rather than loosening silently.
- Budget: proptest's default 256 cases run inside the existing workspace nextest phase (dpp and drive-abci are already in its package list), so PRs get the cheap budget for free. Nightly job `fuzz-decoders` in `tests-rs-nightly-long-running.yml` (hosted `ubuntu-24.04`, `timeout-minutes: 45`): `PROPTEST_CASES=20000 cargo nextest run --package dpp --package drive-abci --all-features --locked -E 'test(/fuzz_tests::/)'`. proptest's regression files are not committed (no `proptest-regressions` directories exist in the tree today; keep it that way and let `PROPTEST_CASES` do the work).

## 7. Decisions and provisional values (go in the PR bodies)

1. Engine corpus not included: no engine on the tree; R03-01/R08-08 (dependents of this task) add NaN/trap/fuel cases to the schema's reserved `profile.engine` and `diagnostic.engine_fuel` slots. Consensus-visible mismatch rejects, diagnostic mismatch reports: that rule is implemented now and tested by the self-test.
2. Upgrade boundary is `latest - 1 -> latest` by symbol, not by number, so the test survives the protocol versions 15 to 17 arriving from the engine lane.
3. Completion marker on part 2: after both parts, every acceptance clause that can be exercised on this tree is in CI (cross-architecture replay, comparison, failure detection, upgrade and restart, targeted fuzzing, bounds). The corpus clause is conditional on work that lists R14-01 as its prerequisite, so it cannot gate R14-01; the PR body says which clause is deferred and where it lands.
4. Runner choice: GitHub-hosted `ubuntu-24.04` and `ubuntu-24.04-arm` (already used for the docker release matrix); 90-minute record timeout, 10-minute compare timeout. Provisional; adjust after the first nightly timings.
5. Fuzz budget: 256 cases on PRs (proptest default, already inside the workspace phase), 20,000 nightly with a 45-minute job timeout. Provisional.
6. Nightly cron `0 21 * * *`, one hour ahead of the existing long-running nightly. Provisional.
7. Workload shape excludes withdrawals and token operations to stay free of RPC mocks and TRANSFER-key setup; R08-08's mixed native/contract workload extends it later.
8. `verify_state_transition_results` stays `false` in the determinism workload (proof verification is covered by the comprehensive simulation; it doubles runtime here).
9. New `app_hashes_per_block` field on `ChainExecutionOutcome` instead of recomputing roots; conflicts trivially with r05-05's `state_transitions_per_block` addition, keep both.
10. Seven-day clean shadow comparison and two rehearsals: mentioned as provisional proposals in the book chapter, not gates.
