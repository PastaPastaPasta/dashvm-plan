# PLAN R06-11: results, receipts and proofs (documentation)

Working artifact. Never staged or committed.

Base: `v5.0-dev` at `e40a2ba993` (branch `dashvm/r06-11`). Tier: high (confirmed; documentation only, but it fixes the semantics that proof, receipt and client tasks implement against). Kind: docs. One part.

## Acceptance in my words

1. The repository documents, in one place, the difference between three things a client can hold after a contract call or a query:
   - unproven execution-result text (the outcome bytes and error text a node returns, trusted only as far as the node is trusted);
   - a stored receipt (a record the network wrote into state under the contract, which a proof can show is present under its key at the signed current root, and which is neither a re-execution proof nor a historical-state proof);
   - a current-state proof (an authenticated fact about the current root, bound to the trusted root and the complete path and query).
   The existing `ExecutionProved` versus `AffectedState` distinction for state transition results is preserved and the contract-call outcomes are placed alongside it.
2. Q32 is stated as the binding policy: receipt storage is enabled by default, each contract may disable it, retention is contract-defined, a contract that declares no expiry retains its receipts until an authorized removal (no automatic expiry is invented), and canonical code retention is independent of receipt retention in both directions.
3. The ABI capability surface (what a contract manifest declares about receipts) and the client result semantics (what each result class may claim, what absence means, which SDK APIs return which class) are written as requirements the implementing tasks honour: R08-04 (ABI signatures, register A07), R10-03 (receipt codec and retention, register A18), R10-06 and R13-11 (SDK results), R09-08 and R10-07 (tests).
4. The existing rustdoc on the result types and wait APIs in DPP, the proof verifier and the Rust SDK points at that chapter and states how contract-call results extend them, so the semantics are visible where an implementer reads the code.

## Decision: documentation only, no new Rust types

The task title asks to "reflect default-enabled contract-controlled receipts in ABI capabilities and client result semantics". Reflecting them in code today would mean inventing the ABI receipt-policy descriptor (A07, R08-04) and the receipt result type (A18, R10-03) ahead of their owners, on a branch where the ABI crate does not exist. That would either collide with those PRs or ship an unallocated wire shape. The defensible reading of a `kind: docs` task with no prerequisites is: write the normative chapter those tasks implement against, and anchor it in the rustdoc of the types that already exist. Every requirement in the chapter is phrased so the implementer of R08-04, R10-03 or R10-06 can tick it. If a reviewer wants placeholder Rust types, that is a scope change for R10-03, not this task.

## Approach by file

### 1. New chapter `book/src/sdk/results-receipts-and-proofs.md` (about 190 lines)

Title: "Results, Receipts and Proofs". Sections:

1. **The problem.** A contract call response can carry the guest's returned bytes or error text, a receipt, proof metadata and a GroveDB proof in one message. A valid proof in the response does not make the text proven. Motivation sentence from DVM-10: a result must not be advertised as a proof of execution because the same response includes a valid state proof.
2. **Three result classes.** A table with columns: class, what produced it, what it is bound to, what a client may conclude, what it may not conclude. Rows: unproven execution-result text (`ExecutionOutcome` in the DIP draft), stored receipt (`StoredReceipt`), current-state proof (`VerifiedStateResult`). The three names are the DIP's proposed names and are marked as such; the code will get them from R10-03 and R10-06.
3. **How this extends the existing guarantee tag.** `StateTransitionProofOutcome::ExecutionProved` versus `AffectedState`, the strict and affected-state wait pairs in `BroadcastStateTransition`, `FetchUnproved` and `FromUnproved` for the unproved path. Contract calls fit as follows (provisional interpretation, stated as such in the chapter and the PR body): a wait on a contract call whose contract retains receipts returns the receipt as an `ExecutionProved` result when the receipt key binds the specific outer invocation (owner and nonce); a wait on a call whose contract disabled receipts can only return `AffectedState` over the keys the call declared, so callers of the strict API get `ExecutionNotProved` and must choose the affected-state API deliberately. R10-06 owns the final mapping; the chapter states the invariant it must keep: no path returns `ExecutionProved` without a proof that binds the invocation.
4. **What a receipt proves and does not prove.** Inclusion under its key at the signed current root; the recorded bounded outcome, actual fees and failure class. Not: a re-execution proof, a proof of state at the deployment or execution height, a proof of anything the receipt does not record. A receipt is one per outer invocation with bounded nested outcomes (architecture section 9); speculative retries and node faults write none.
5. **Receipt policy (Q32, confirmed).** Default enabled; the contract may disable; retention is declared by the contract; no declared expiry means retained until authorized removal; no automatic expiry is invented by the node, the SDK or a cleanup job; canonical code retention is independent: disabling receipts, removing receipts, and a wipe's cleanup never delete code or manifests, and permanent code never implies permanent receipts. "Authorized removal" is defined as a removal the contract's own rules authorize, or the bounded cleanup that follows a wipe; both are named as the only removal paths, and the exact transition shape is R10-03's allocation.
6. **Absence is not failure.** Enumerate the reasons a receipt query returns nothing: policy disabled, removed under declared retention, the call was never accepted (rejected at check or never included), the query ran before inclusion, the query used the wrong contract or key. Clients must surface the effective policy and status next to an absence and must never render absence as "call failed". Paid failure is an accepted outcome with a receipt when receipts are on.
7. **Outcome classes a client must keep apart.** Table: accepted success; accepted paid failure (fee charged, nonce consumed, receipt written when enabled, effects rolled back); rejected transition (consensus error, no receipt); transport error; invalid or wrong-root proof. Which of these a proof can establish, and which only the node's text reports.
8. **What each layer returns.** Short table mapping today's APIs (`fetch`, `fetch_with_metadata_and_proof`, `fetch_unproved`, the strict and affected-state waits, the JS `waitForResponse`, `waitForAffectedState`, `fetchUnproved`) to the class they return, so the extension for contract calls has a baseline.
9. **Requirements for the implementing tasks.** A checklist, each item naming the task that ticks it:
   - ABI manifest carries a receipt policy declaration with `enabled` defaulting to true and a retention declaration whose absence means indefinite; the declaration is a capability description and grants nothing (R08-04).
   - Receipt codec is bounded (provisional 64 KiB from the allocation register), versioned, and stores the policy in force at execution so a later policy change does not rewrite history (R10-03).
   - The retention update path can only shorten or lengthen retention going forward and can never delete code (R10-03, R12-09).
   - Client result types are three distinct types; converters preserve optional receipt and policy fields; JSON never collapses them (R10-06, R13-03, R13-11).
   - Tests cover receipt off, removed, retained, tampered and wrong-root, and the absence case of every receipt query (R09-08, R10-07).
   - No client method implies a network preflight or a historical proof service (R10-06).

Style: plain prose, no em dashes, code identifiers only where the reader must go there, tables for the parallel comparisons, mermaid not needed.

Mapping of contract-call waits onto `ExecutionProved` (receipt present and keyed by the invocation) and `AffectedState` (receipts disabled): my provisional interpretation, R10-06 owns the final one; the invariant (never `ExecutionProved` without an invocation-binding proof) is the confirmed part.
