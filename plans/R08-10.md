## 1. Acceptance in my words

The issue row (S08-24, section 8, owner answer Q01) asks for three things:

1. **Track security fixes and advisories for the selected engine dependencies.** The repository
   must name which crates form the DashVM engine set, and something must notice when an
   advisory is published against one of them, without that signal being drowned by the
   base-wide nightly audit (which fails today on rustls, lru, scc and friends, and honours the
   workspace ignore list in `.cargo/audit.toml`).
2. **Apply the execution/fee-equivalence hotfix rule.** State, in a place that lasts, when an
   engine dependency change (patch bump, temporary patch, integration-layer fix) may ship as a
   software-only hotfix and when it must be a protocol upgrade with a new engine profile. The
   criterion is equivalence of guest-visible results, trap classes, metered cost and resource
   outcomes over accepted code and recorded executions, on both architectures. This is the rule
   FIX-04 rehearses, R11-07 integrates with recovery and R11-09 produces evidence for.
3. **No external-audit report, named security owner or closed stage audit is a prerequisite to
   building.** The chapter says so, and the check is mechanical: it does not wait for a human
   sign-off, a subscription or an owner.

Q01 binds: pinned upstream Wasmtime with Cranelift, a small Dash integration layer, fixes
contributed upstream; a temporary patch is an exception, not a standing fork. The plan encodes
"exception" as a declared, justified, dated entry that CI fails once it expires.

Not in scope (owned elsewhere, the chapter points at them): the exact engine pin (A04, R08-01),
drift detection of the pinned configuration (R11-01), the differential and replay tooling that
produces equivalence evidence (R03-01, R03-02, R11-09, R14-01), the rehearsal test (FIX-04), and
external subscriptions or communications (R03-05 says they remain operational actions).

### 3.1 `Cargo.toml` (root): the engine dependency set as workspace metadata

Append after `[workspace.package]`:

```toml
# DashVM engine dependency set (dashpay/platform#4626, section 8). Read by
# .github/scripts/check-engine-advisories.py: every advisory against one of these crates fails
# the engine audit regardless of the workspace-wide ignore list in .cargo/audit.toml, because
# the engine decides consensus results. Names only; versions are pinned where the crates are
# used (the runtime and validation crates) and drift is checked there.
[workspace.metadata.dashvm.engine]
crates = [
    "wasmtime",
    "wasmtime-environ",
    "wasmtime-internal-cranelift",
    "cranelift-codegen",
    "cranelift-frontend",
    "cranelift-native",
    "wasmparser",
    "wasm-encoder",
]
# A scoped acknowledgement hides one advisory from the engine audit until it expires. It must
# say why the advisory cannot reach a node under the pinned profile (for example a Winch or
# component-model bug when neither is compiled in). Renewal is a new entry with a fresh reason.
# acknowledged = [
#     { id = "RUSTSEC-2026-0000", reason = "...", expires = "2026-12-31" },
# ]
# A temporary patch (Q01: an exception, not a standing engine fork) must be declared here with
# the upstream fix it carries and the date by which an upstream release replaces it.
# patches = [
#     { crate = "wasmtime", upstream = "https://github.com/bytecodealliance/wasmtime/pull/0", expires = "2026-12-31" },
# ]
```

Why names only: the exact pin is allocation A04 (R08-01) and pinned-configuration drift is
R11-01; the audit needs to know *which* crates are engine crates, and it audits every version
of them the lockfile resolves (today that is the transitive 0.244 wasm-tools pair, which is
still worth failing on). Crates not in the lockfile are reported as "planned, not in the
lockfile" and skipped, so the check is live today and needs no flip when the runtime lands.
`wat` and `wasmprinter` (R08-01 dev-dependencies) are tooling, not engine, and stay on the
base-wide audit.

Cargo ignores `workspace.metadata` for resolution; `Cargo.lock` does not change (probed on this
tree on 2026-09-22: `cargo metadata --locked` exit 0, the table is exposed under `metadata`,
lockfile hash unchanged). Dates are ISO 8601 strings, not TOML date literals, so `tomllib` and
the cargo JSON expose the same value; the script parses them with `date.fromisoformat`.

### 3.2 `.github/scripts/check-engine-advisories.py` (new, about 330 lines)

Pure-stdlib Python (argparse, json, subprocess, tomllib, datetime, tempfile). Structure:

- `load_manifest(cargo_toml)`: returns the engine set, the acknowledgements, the declared
  patches, plus every `[patch.*]` entry of the root manifest.
- `load_lockfile(cargo_lock)`: `{name: [versions]}` from `[[package]]`.
- `run_cargo_audit(lockfile)`: runs `cargo audit --json --file <abs lockfile>` from a fresh
  temporary directory so `./.cargo/audit.toml` is not found and the workspace ignore list
  cannot hide an engine advisory; accepts exit 0 and 1, treats 2 (or unparsable JSON) as an
  error (exit 2 from the script). Prints the advisory database commit and count from
  `report.database` for the log.
- `evaluate(manifest, lock, report, today) -> (exit_code, lines)`: the pure core.
  - For each engine crate: present versions, or "planned: not in the lockfile".
  - Every vulnerability whose `package.name` is in the set is a failure unless a
    non-expired acknowledgement names its `id`; an acknowledgement without `reason`, without
    `expires`, or expired, is itself a failure (and an acknowledgement for an id no longer
    reported is a notice asking for removal).
  - Every warning of kind `unmaintained`, `unsound` or `yanked` on an engine crate is a
    failure (Q01: upstream-maintained pinned releases; a yanked engine crate cannot be a pin).
    `notice` kind is printed, not failing.
  - Every `[patch.*]` entry in the root manifest whose crate is in the set must have a
    declared patch with `upstream` URL and a non-expired `expires`; otherwise failure. A
    declared patch with no matching `[patch]` entry is a notice ("patch retired, remove the
    declaration").
  - Provisional bound (no register value; marked provisional in code and PR body): neither an
    acknowledgement nor a temporary patch may run more than 90 days from the day it is
    evaluated, so a stale exception fails even if its `expires` was set far out.
  - Output is grouped: failures first, then notices, then a one-line summary. Exit 1 on any
    failure, 0 otherwise.
- `--self-test`: builds manifests, lockfiles and reports in memory and asserts exit codes and
  messages for: clean set; vulnerability on `wasmtime`; the same with a valid acknowledgement
  (passes with notice); expired acknowledgement (fails); acknowledgement over the 90-day cap
  (fails); `unmaintained` warning on `cranelift-codegen` (fails); `yanked` (fails);
  `[patch.crates-io] wasmtime` undeclared (fails); declared with expiry (passes); vulnerability
  on a non-engine crate such as `rustls` (passes, not our scope); engine crate absent from the
  lockfile (notice only). Prints "self-test N of N checks passed", exit 1 if any fails,
  mirroring compare-determinism-artifacts.py.
- `--report <json>`: evaluate a saved cargo-audit report instead of running the tool (used
  locally for positive evidence and by anyone reproducing a CI failure offline).
- `--manifest`, `--lockfile` paths default to the repository root (resolved from the script's
  location, not the cwd).

### 3.6 `book/src/architecture/engine-dependencies-and-hotfixes.md` (new, about 280 lines) and `SUMMARY.md`

Entry under Architecture after Component Pipeline (an add/add hunk with FIX-03's Block Failure
Classes line if that lands first; trivial rebase). Chapter sections, prose in the book's voice
(problem first, then rule, then mechanics), no em dashes, no ticket ids in prose (task ids like
R11-09 are plan references and stay in the closing table only):

1. **Why the engine is a consensus dependency.** Every node compiles the same canonical Wasm
   with the same Cranelift and must produce the same result, trap, metered cost and resource
   outcome. The engine is therefore versioned like any other consensus behaviour: an engine
   profile selected per protocol version (the DashVM table in `platform-version`; the
   implementer words this against whether #4712 has merged), historical profiles retained for
   replay.
2. **The engine policy (owner decision).** Pinned upstream Wasmtime releases from the LTS
   channel with Cranelift; a small Dash integration layer (validation crate, runtime crate);
   fixes go upstream; a temporary patch is an exception with a declared upstream fix and an
   expiry. What "small" means: no forked engine crate in the workspace, no vendored engine
   sources, no local behaviour flags that change compiled code outside the profile.
3. **The selected dependencies.** A table: crate, role (compiler, environment, binary
   format, validator's parser and encoder), where it is pinned, and which advisory source
   covers it (RustSec ids exist for `wasmtime` and `cranelift-codegen`; the wasm-tools crates
   have had none, so upstream release notes are the signal). States that the set is recorded
   in `Cargo.toml` under `workspace.metadata.dashvm.engine` and that the exact release pin is
   an open allocation owned by the runtime crate work, with today's facts as of the writing
   date (36 LTS supported until 2027-08-20, 48 LTS since 2026-08-20) so a reader knows the
   line's lifetime.
4. **How advisories are tracked.** RustSec through cargo-audit, GitHub Security Advisories on
   bytecodealliance/wasmtime as the upstream source of truth, Bytecode Alliance announcements.
   What is automated (the engine audit: nightly, on dispatch, and on pull requests that change
   the lockfile; unmaskable by the workspace ignore list; scoped acknowledgements with a
   reason and an expiry; temporary patches declared with their upstream fix). What stays
   operational and outside the repository (subscriptions, disclosure contacts). The explicit
   statement that no external audit report, named security owner or closed stage audit gates
   building.
5. **Classifying an advisory.** A two-axis table. Reachability under the pinned profile:
   compiled in and reachable from guest code (Cranelift lowering for admitted opcodes, memory
   guards, fuel, host calls); compiled in but not guest-reachable (host API misuse, async
   futures, Linker cloning); not compiled in (Winch, component model, WASI, threads, SIMD,
   memory64, pooling allocator if the runtime does not use it). Consequence: host safety only
   (sandbox escape, out-of-bounds read, panic, leak) versus guest-visible semantics
   (miscompile that changes a result or trap) versus metering (fuel or cost counts) versus
   resources (limits, growth). Worked examples from the April 2026 batch: the aarch64 Cranelift
   load miscompile (Critical, reachable, guest-visible on one architecture: a node on the
   affected build already disagrees with the specification, so the patched engine restores the
   specified behaviour and the differential run over recorded executions must show that no
   committed execution depended on the bug); the x86-64 `f64x2.splat` bug (SIMD, not admitted:
   unreachable, acknowledged with reason until the routine patch bump); Winch and component
   model bugs (not compiled in). Also the filesystem sandbox escape (WASI, not compiled in).
6. **The execution/fee-equivalence hotfix rule.** The normative section.
   - Definition of an engine hotfix: a change to the engine set or the integration layer that
     ships in a node release without a protocol version change.
   - Permitted only with equivalence evidence: for every accepted canonical module (all
     stored contract versions, executable or not), the prepared bytes are unchanged (the
     preparation generation is a separate pin and is never touched by an engine hotfix),
     compilation succeeds, and for every recorded execution and every corpus vector the
     result bytes, trap class, metered computation units and host-call counts, resource
     outcomes (memory, stack, limits) and proposed operations are identical to the recorded
     ones, on x86_64 and on aarch64. Raw Wasmtime fuel must match where it feeds a consensus
     cost or limit; otherwise it is recorded diagnostically (Q41 wording).
   - Anything else is a protocol upgrade: a new engine profile version in the DashVM table,
     the old profile retained for replay of historical blocks, activation through the normal
     upgrade vote, no emergency pause and no new authority (owner decision). A committed wrong
     result is not a hotfix case but an incident under existing recovery.
   - Node-local changes (artifact cache format, compile speed, memory use, diagnostics,
     logging) are never consensus-visible and need only the ordinary tests.
   - Before the first network activates contract execution, the set of accepted modules and
     recorded executions is empty; the rule then reduces to the corpus comparison, so patch
     bumps on the LTS line are routine until activation.
   - Evidence sources and who supplies them: the deterministic corpus, cross-architecture
     replay, the differential tooling over stored versions and recorded executions, the
     rehearsal test, and the release-evidence bundle. Until the differential tooling exists,
     an engine change after activation cannot be declared equivalent and must take the
     protocol-upgrade path; the chapter says this plainly (the containment window FIX-04
     discloses).
7. **Runbook.** Advisory published: the engine audit turns red or a maintainer reads the
   upstream advisory. Classify by the table. Bump to the patched release on the pinned LTS
   line (or declare a temporary patch with its upstream fix and expiry if no release exists
   yet). Produce the equivalence evidence. If equivalent: node release with the advisory named
   in the release notes and the classification recorded. If not: new engine profile, protocol
   upgrade. Remove acknowledgements and patch declarations as they retire. Interaction with
   existing recovery: failing transitions are removed by the proposer, no denylist
   distribution (R11-07 keeps the recovery-side text; this chapter links to it once it exists).
8. **Task map.** A closing table naming the implementing tasks for each evidence source and
   the rehearsal, so a reviewer sees what this chapter promises versus what exists.

## 5. Provisional values and interpretations (all go in the PR body)

1. **90-day cap** on acknowledgements and temporary patches (no register entry; chosen because
   Wasmtime patch releases on the LTS line have shipped at least monthly in 2026, so a
   quarter is long enough to bump and short enough to be noticed). Provisional.
2. **Engine set membership**: `wasmtime`, `wasmtime-environ`, `wasmtime-internal-cranelift`,
   `cranelift-codegen`, `cranelift-frontend`, `cranelift-native`, `wasmparser`,
   `wasm-encoder`. The runtime lane (R08-01 part 2) adjusts the internal crate names to the
   ones the pinned release actually resolves; unknown names cost nothing (they read as planned).
3. **Names, not versions**, in the set: pins live with their consumers, drift detection is
   R11-01, and auditing every resolved version of an engine crate is the safer reading.
4. **Warnings fail**: `unmaintained`, `unsound`, `yanked` on an engine crate are policy
   failures under Q01, not advisories to defer.
5. **The audit runs on pull requests** that touch the lockfile or a manifest, unlike the
   base-wide audit that stays nightly (its TODO is untouched). A red engine audit on a PR is
   the tracking the task asks for; it is not a required check until an operator makes it one.
6. **Pre-activation equivalence is vacuous**: before any network runs contract code, only
   the corpus comparison applies. Stated in the chapter as the reading of "accepted code and
   recorded executions".
7. **Miscompile fixes** are classified as restoring specified behaviour; the differential run
   over recorded executions decides hotfix versus incident. Stated with the aarch64 example.
8. **Chapter placement** under Architecture (next to Block Failure Classes when FIX-03
   lands) rather than a new DashVM section that no chapter on the base yet opens.
